# Linux Pipes: A Simple IPC Mechanism

## What is a Pipe?

A **pipe** is one of the simplest forms of Inter-Process Communication (IPC) in Unix/Linux systems. It's essentially a unidirectional data channel that connects the output of one process to the input of another process.

Think of it as a literal pipe: data flows in one direction, from a writer process to a reader process.

## Simple Shell Example

The most intuitive example is using pipes in the shell:

```bash
# Count the number of files in current directory
ls | wc -l

# Find all .cpp files and count them
ls *.cpp | wc -l

# Search for a pattern and count matches
grep "function" *.cpp | wc -l

# Chain multiple commands
cat file.txt | grep "error" | sort | uniq -c
```

In `ls | wc -l`:
- `ls` writes its output to the pipe
- `wc -l` reads from the pipe and counts lines
- The shell creates the pipe and connects the processes

## How Pipes Work Internally

```
Process A (Writer)    →    PIPE    →    Process B (Reader)
     stdout          →   [buffer]  →        stdin
```

1. **Pipe Creation**: The kernel creates a buffer (typically 4KB-64KB)
2. **File Descriptors**: Two file descriptors are created - read end and write end
3. **Data Flow**: Writer process writes to write-end, reader process reads from read-end
4. **Blocking Behavior**: 
   - If pipe is empty, reader blocks until data arrives
   - If pipe is full, writer blocks until space is available
5. **EOF Handling**: When writer closes its end, reader gets EOF

## Types of Pipes

### 1. Anonymous Pipes (Regular Pipes)
- Created with `pipe()` system call
- Only between related processes (parent-child)
- Exist only in memory
- Unidirectional

### 2. Named Pipes (FIFOs)
- Created with `mkfifo()` or `mknod()`
- Between unrelated processes
- Exist as special files in filesystem
- Still unidirectional

```bash
# Create a named pipe
mkfifo mypipe

# Terminal 1 (writer)
echo "Hello World" > mypipe

# Terminal 2 (reader)
cat < mypipe
```

## When to Use Pipes

### ✅ Good Use Cases:
- **Simple data streaming** between processes
- **Command chaining** in shell scripts
- **Parent-child communication** in C programs
- **Filter/transformation** pipelines
- **Log processing** workflows

### ❌ Not Ideal For:
- **Bidirectional communication** (need two pipes)
- **Multiple readers/writers** simultaneously
- **Large data transfers** (limited buffer size)
- **Random access** to data
- **Persistent data** storage

## Comparison with Other IPC Mechanisms

| Feature | Pipes | Shared Memory | Message Queues | Sockets |
|---------|-------|---------------|----------------|---------|
| **Direction** | Unidirectional | Bidirectional | Bidirectional | Bidirectional |
| **Process Relation** | Related (anonymous) | Any | Any | Any |
| **Performance** | Medium | Very Fast | Medium | Medium-Slow |
| **Data Size** | Limited by buffer | Very Large | Limited by system | Large |
| **Synchronization** | Automatic | Manual (semaphores) | Automatic | Automatic |
| **Persistence** | No | No | Yes (system) | Depends |
| **Network Support** | No | No | No | Yes |
| **Complexity** | Simple | Complex | Medium | Medium-Complex |

### Detailed Comparison

#### **Pipes vs Shared Memory**
```c
// Pipe: Simple but slower
pipe(fd);
write(fd[1], data, size);  // Copy data to kernel buffer
read(fd[0], buffer, size); // Copy data from kernel buffer

// Shared Memory: Complex but faster
shmget(), shmat();  // Setup
*shared_ptr = data;  // Direct memory access (no copying)
```

#### **Pipes vs Message Queues**
```c
// Pipe: Stream of bytes
write(fd, "Hello World", 11);  // Just bytes

// Message Queue: Structured messages
struct msg { long type; char data[100]; };
msgsnd(qid, &message, sizeof(message), 0);  // Typed messages
```

#### **Pipes vs Sockets**
```bash
# Pipe: Local only
command1 | command2

# Socket: Local or network
nc -l 8080 | command2  # Network capable
```

## Real-World Examples

### 1. Log Processing Pipeline
```bash
tail -f /var/log/apache/access.log | \
grep "ERROR" | \
awk '{print $1, $4, $7}' | \
sort | \
uniq -c | \
sort -nr
```

### 2. Data Processing
```bash
# Process CSV file
cat data.csv | \
cut -d',' -f2,3 | \
sort -t',' -k2 -n | \
head -10
```

### 3. System Monitoring
```bash
# Monitor system resources
ps aux | \
awk '$3 > 10 {print $2, $11, $3}' | \
sort -k3 -nr
```

## Advantages and Limitations

### ✅ Advantages:
- **Simple to use** - minimal setup required
- **Automatic synchronization** - blocking I/O handles timing
- **Shell integration** - works seamlessly with command line
- **Memory efficient** - kernel manages buffering
- **No cleanup needed** - automatically cleaned up when processes exit

### ❌ Limitations:
- **Unidirectional** - need two pipes for bidirectional communication
- **Limited buffer size** - can cause deadlocks if full
- **No random access** - strictly sequential data flow
- **Process relationship** - anonymous pipes only work between related processes
- **No message boundaries** - just a stream of bytes
- **Local only** - cannot cross network boundaries

## Best Practices

1. **Always close unused ends** of the pipe to avoid hanging
2. **Handle SIGPIPE** signal when reader terminates early
3. **Use error checking** for all pipe operations
4. **Consider buffering** for performance in large data transfers
5. **Use named pipes** for unrelated process communication
6. **Combine with select/poll** for non-blocking operations

## Interview Questions

1. Fundamental Concepts

    What is a pipe in IPC? 
    
        A pipe is a unidirectional communication channel that allows data to flow from one process to another in a First-In-First-Out (FIFO) manner.
    
    What is the difference between Unnamed Pipes and Named Pipes (FIFOs)?
    
        Unnamed Pipes: Can only be used between related processes (e.g., parent and child) because they do not have a name in the filesystem; they exist only while the processes are running.
        Named Pipes (FIFOs): Exist as special files in the filesystem, allowing unrelated processes to communicate. They persist even after processes terminate.

    Is a pipe half-duplex or full-duplex? 
    
        Standard pipes are half-duplex, meaning data flows in only one direction. For bidirectional communication, two pipes must be created.

2. Implementation & System Calls

    How do you create an unnamed pipe in C? 
        You use the pipe() system call, which takes an array of two integers to store file descriptors: fd[0] for reading and fd[1] for writing.

    What happens if a process reads from an empty pipe? 
        The read() call will block (wait) until data is written to the pipe or all write descriptors are closed.
    
    What happens if a process writes to a full pipe? 
        The write() call will block until enough data has been read from the pipe to make room.

    What is the mkfifo() system call? 
        It is used to create a named pipe (FIFO) at a specific path in the filesystem

3. Comparison & Trade-offs

    How do pipes differ from Shared Memory? 
        Shared memory is the fastest IPC mechanism because it avoids data copying between kernel and user space, but it requires manual synchronization (e.g., semaphores). Pipes are slower due to copying but provide built-in synchronization.

    When would you use a Message Queue instead of a Pipe?
         Message queues allow for structured, typed messages and can be accessed by unrelated processes, whereas pipes are simple byte streams typically used for streaming data between related processes.

    What are the advantages of pipes?
         They are simple to implement, provide automatic synchronization, and have low overhead for basic data transfer.

4. Advanced Scenarios

    Explain the "Broken Pipe" (SIGPIPE) error. 
        If a process tries to write to a pipe that has no readers (all read file descriptors are closed), the kernel sends a SIGPIPE signal to the writer, which usually terminates the process unless handled.

    How does a shell pipe (|) work?
         The shell uses pipe() to create a channel, fork() to create processes for each command, and dup2() to redirect the standard output of the first command to the write end of the pipe and the standard input of the second command to the read end.


## Conclusion

Pipes are the Swiss Army knife of IPC - simple, reliable, and perfect for many common use cases. While they have limitations, their simplicity and shell integration make them indispensable for system administration, data processing, and basic process communication.

For complex applications requiring bidirectional communication, shared memory performance, or network capabilities, consider other IPC mechanisms. But for straightforward data streaming and command chaining, pipes are often the perfect solution.
