# Red-Black Tree - Complete Guide

## Overview
A **Red-Black Tree** is a self-balancing binary search tree where each node has an additional color attribute (red or black). Through specific color rules and rotations, it guarantees **O(log n)** time complexity for all major operations, making it one of the most important data structures in computer science.

## Why Red-Black Trees?
Regular BSTs can degrade to **O(n)** performance when data is inserted in sorted order, essentially becoming a linked list. Red-Black trees solve this by automatically maintaining balance through:
- **Color properties** that constrain tree structure
- **Rotations** that restructure the tree when needed
- **Height guarantee**: Tree height ≤ 2×log₂(n+1)

## The Five Red-Black Properties

### 1. **Node Color Rule**
Every node is either **RED** or **BLACK**

### 2. **Root Color Rule**  
The root is always **BLACK**

### 3. **Leaf Color Rule**
All leaves (NIL nodes) are **BLACK**

### 4. **Red Node Rule**
**RED** nodes cannot have **RED** children
(No two consecutive RED nodes on any path)

### 5. **Black Height Rule**
Every path from root to leaf contains the **same number of BLACK nodes**

Legend: (B) = Black, (R) = Red

## Mathematical Foundation

### Height Guarantee Proof
1. **Shortest path**: Contains only BLACK nodes
2. **Longest path**: Alternates RED and BLACK nodes
3. **By Property 5**: All paths have same number of BLACK nodes
4. **By Property 4**: Longest path ≤ 2 × shortest path
5. **Therefore**: Height ≤ 2×log₂(n+1)

### Why This Matters
- **Guaranteed performance**: No worst-case O(n) degradation
- **Predictable behavior**: Critical for real-time systems
- **Optimal balance**: Not perfectly balanced, but "good enough"

## Core Operations

### 1. Search Operation
**Identical to regular BST** - colors don't affect search logic.

```cpp
bool search(node, target):
    if node == NIL:
        return false
    
    if target == node.data:
        return true
    elif target < node.data:
        return search(node.left, target)
    else:
        return search(node.right, target)
```

**Time Complexity**: O(log n) guaranteed

### 2. Insertion Operation

#### Step 1: Standard BST Insertion
1. Insert new node as **RED** (minimizes violations)
2. Set children to NIL nodes
3. Find correct position using BST property

#### Step 2: Fix Red-Black Violations
New RED node may violate Property 4 (RED parent). Fix using:

##### Case 1: Uncle is RED
```
    G(B)           G(R)
   /   \          /   \
  P(R) U(R) → P(B)   U(B)
 /           /
N(R)        N(R)
```
**Action**: Recolor parent, uncle, grandparent. Move up to grandparent.

##### Case 2: Uncle is BLACK (Triangle)
```
  G(B)         G(B)
 /   \        /   \
P(R) U(B) → X(R) U(B)
  \         /
  N(R)    P(R)
             \
             N(R)
```
**Action**: Rotate to convert to line case.

##### Case 3: Uncle is BLACK (Line)
```
    G(B)         P(B)
   /   \        /   \
  P(R) U(B) → N(R) G(R)
 /                   \
N(R)                 U(B)
```
**Action**: Recolor and rotate. Done!

### 3. Deletion Operation (Most Complex)

#### Step 1: Standard BST Deletion
Handle three cases:
1. **No children**: Remove directly
2. **One child**: Replace with child
3. **Two children**: Replace with inorder successor

#### Step 2: Fix Red-Black Violations
If deleted node was BLACK, may violate Property 5. Use complex fixup procedure with multiple cases involving sibling colors and rotations.

## Rotations - The Balancing Mechanism

### Left Rotation
```
     x               y
    / \             / \
   a   y    =>     x   c
      / \         / \
     b   c       a   b
```

### Right Rotation  
```
       y           x
      / \         / \
     x   c  =>   a   y
    / \             / \
   a   b           b   c
```

**Purpose**: Restructure tree while maintaining BST property and improving balance.

## Implementation Key Points

### NIL Sentinel Node
```cpp
// All leaf nodes point to a single NIL sentinel
NIL->color = BLACK;
NIL->left = NIL->right = NIL->parent = NIL;
```
**Benefits**:
- Simplifies code (no null checks)
- Ensures Property 3 automatically
- Consistent handling of leaf nodes

### Color Enum
```cpp
enum Color { RED, BLACK };
```
**Implementation**: Simple boolean would work, but enum improves readability.

### Node Structure
```cpp
struct Node {
    T data;
    Color color;
    Node* left, *right, *parent;
};
```
**Note**: Parent pointer essential for efficient rotations and fixups.

## Complexity Analysis

### Time Complexities
| Operation | Red-Black Tree | Regular BST (Avg) | Regular BST (Worst) |
|-----------|----------------|-------------------|-------------------|
| Search    | O(log n)       | O(log n)          | O(n)              |
| Insert    | O(log n)       | O(log n)          | O(n)              |
| Delete    | O(log n)       | O(log n)          | O(n)              |
| Min/Max   | O(log n)       | O(log n)          | O(n)              |

### Space Complexity
- **Storage**: O(n) for n nodes
- **Extra space per node**: 1 bit for color + parent pointer
- **Recursion stack**: O(log n) maximum depth

## Advantages and Disadvantages

### ✅ Advantages
1. **Guaranteed O(log n)** - No worst-case degradation
2. **Efficient insertions** - At most 2 rotations
3. **Widely implemented** - STL map/set, Java TreeMap
4. **Good general performance** - Balanced between search and update
5. **Memory efficient** - Only 1 extra bit per node for color

### ❌ Disadvantages
1. **Complex implementation** - Many cases in insertion/deletion
2. **Not perfectly balanced** - AVL trees are more balanced
3. **More rotations than needed** - For read-heavy workloads
4. **Debugging difficulty** - Complex invariants to maintain

## Common Interview Questions

### 1. "Why Red-Black instead of AVL?"
**Answer**: Red-Black trees require fewer rotations during insertion/deletion, making them better for write-heavy workloads, while AVL trees are more strictly balanced and better for read-heavy workloads.

### 2. "What's the maximum height?"
**Answer**: 2×log₂(n+1). This comes from the fact that the longest path (alternating red-black) is at most twice the shortest path (all black).

### 3. "Why color new nodes RED?"
**Answer**: Adding a BLACK node would violate Property 5 (black height) on all paths through that node. Adding RED might only violate Property 4 (red-red), which is easier to fix.

### 4. "Can you have all BLACK nodes?"
**Answer**: Yes! A tree with all BLACK nodes is a valid Red-Black tree, though not optimal for height.

## Quick Revision Checklist

### 🎯 Essential Properties
1. **5 Red-Black properties** - Know them by heart
2. **Height bound**: 2×log₂(n+1) - guaranteed O(log n)
3. **New nodes are RED** - minimizes violations
4. **NIL sentinel** - simplifies implementation
5. **3 rotation cases** - uncle red, triangle, line

### 🧠 Memory Aids
- **"No Red-Red"**: Property 4 - red nodes can't have red children
- **"Same Black Path"**: Property 5 - all root-to-leaf paths have equal black nodes
- **"Root is Black"**: Property 2 - always enforce this
- **"Color violations up"**: Fix violations by moving up the tree

### 🚨 Common Mistakes
1. **Forgetting NIL nodes** - they're always BLACK
2. **Wrong rotation direction** - draw it out first
3. **Infinite loops** - ensure fixup terminates
4. **Memory leaks** - delete nodes properly
5. **Parent pointer bugs** - update all pointers during rotations
