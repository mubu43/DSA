# Hash Table - Complete Guide

## Overview
A **Hash Table** (also called Hash Map) is a data structure that implements an associative array, mapping keys to values using a hash function. It provides average **O(1)** time complexity for search, insertion, and deletion operations, making it one of the most important and widely-used data structures in computer science.

## Core Concept
```
Key → Hash Function → Index → Value

Example:
"Alice" → hash("Alice") → 3 → 12345
"Bob"   → hash("Bob")   → 7 → 23456
```

The hash function converts keys into array indices, allowing direct access to stored values.

## Key Properties
- **Average Time Complexity**: O(1) for search, insert, delete
- **Worst Case Time Complexity**: O(n) when many collisions occur
- **Space Complexity**: O(n) for n key-value pairs
- **Load Factor**: α = n/m (elements/table size) - affects performance
- **No Ordering**: Elements are not stored in any particular order

## Hash Functions

### 1. Division Method
```cpp
h(k) = k mod m
```
- **Simple and fast**
- **Best with prime table sizes**
- **Can have poor distribution** for certain key patterns

**Example**:
```
Table size m = 11
h(123) = 123 % 11 = 2
h(456) = 456 % 11 = 5
```

### 2. Multiplication Method
```cpp
h(k) = floor(m * (k * A mod 1))
where A ≈ 0.6180339887 (golden ratio conjugate)
```
- **Good distribution** for most table sizes
- **Less sensitive** to table size choice
- **Slightly more computation** than division

**Example**:
```
A = 0.618, m = 10, k = 123
123 * 0.618 = 75.994
0.994 * 10 = 9.94
h(123) = floor(9.94) = 9
```

### 3. Universal Hashing
```cpp
h(k) = ((a * k + b) mod p) mod m
where a, b are random, p is prime > max key
```
- **Theoretical guarantees** on collision probability
- **Randomized approach** prevents worst-case attacks
- **More computation** but excellent distribution

## Collision Resolution Strategies

### 1. Separate Chaining (Our Implementation)
**Method**: Each table slot contains a linked list of all elements that hash to that index.

```
Table:
[0] → empty
[1] → (key1, val1) → (key2, val2)
[2] → (key3, val3)
[3] → empty
[4] → (key4, val4) → (key5, val5) → (key6, val6)
```

**Advantages**:
- Simple implementation
- No limit on number of elements
- Deletion is straightforward
- Performance degrades gracefully

**Disadvantages**:
- Extra memory for pointers
- Cache performance can be poor
- Need dynamic memory allocation

### 2. Open Addressing (Alternative Approach)
**Method**: All elements stored in table itself. When collision occurs, probe for next empty slot.

#### Linear Probing
```cpp
h(k, i) = (h'(k) + i) mod m
```
- Check h'(k), h'(k)+1, h'(k)+2, ...
- **Primary clustering** problem

#### Quadratic Probing  
```cpp
h(k, i) = (h'(k) + c1*i + c2*i²) mod m
```
- Reduces primary clustering
- **Secondary clustering** can occur

#### Double Hashing
```cpp
h(k, i) = (h1(k) + i*h2(k)) mod m
```
- Best open addressing method
- Two independent hash functions

## Load Factor and Performance

### Load Factor Definition
```
α = n/m
where n = number of elements, m = table size
```

### Performance Impact
| Load Factor | Avg Search (Chaining) | Avg Search (Linear Probing) |
|-------------|----------------------|----------------------------|
| 0.5         | 1.25                 | 1.5                        |
| 0.75        | 1.375                | 2.5                        |
| 1.0         | 1.5                  | ∞ (table full)             |
| 2.0         | 2.0                  | N/A                        |

### Why Load Factor Matters
- **Low load factor (α < 0.5)**: Fast operations, wasted space
- **Medium load factor (α ≈ 0.75)**: Good balance of speed and space
- **High load factor (α > 1.0)**: Space efficient, slower operations

## Dynamic Resizing

### When to Resize
```cpp
if (loadFactor > maxLoadFactor) {
    resize();
}
```
**Common thresholds**: 0.5, 0.75, or 1.0

### Resizing Process
1. **Create new table** (usually 2x size)
2. **Rehash all elements** into new table
3. **Update table reference**
4. **Deallocate old table**

**Cost**: O(n) for rehashing, but **amortized O(1)** per operation

### Example Resize Sequence
```
Initial: size=7, elements=5, α=0.71
Insert: size=7, elements=6, α=0.86 > 0.75 → RESIZE
After: size=17, elements=6, α=0.35
```

## Hash Table Operations

### Insert Operation
```cpp
void insert(key, value):
    if loadFactor > threshold:
        resize()
    
    index = hash(key)
    
    // Check if key exists (update case)
    for each pair in table[index]:
        if pair.key == key:
            pair.value = value
            return
    
    // Add new key-value pair
    table[index].add(key, value)
    numElements++
```

### Search Operation
```cpp
bool search(key, &value):
    index = hash(key)
    
    for each pair in table[index]:
        if pair.key == key:
            value = pair.value
            return true
    
    return false
```

### Delete Operation
```cpp
bool delete(key):
    index = hash(key)
    
    for each pair in table[index]:
        if pair.key == key:
            remove pair from table[index]
            numElements--
            return true
    
    return false
```

## Complexity Analysis

### Time Complexities
| Operation | Average Case | Worst Case | Best Case |
|-----------|--------------|------------|-----------|
| Search    | O(1)         | O(n)       | O(1)      |
| Insert    | O(1)         | O(n)       | O(1)      |
| Delete    | O(1)         | O(n)       | O(1)      |
| Resize    | O(n)         | O(n)       | O(n)      |

### Space Complexity
- **Table storage**: O(m) where m is table size
- **Element storage**: O(n) where n is number of elements
- **Total**: O(n + m) = O(n) when m is proportional to n

### Amortized Analysis
- **Individual operations**: May be O(n) during resize
- **Sequence of operations**: Amortized O(1) per operation
- **Resize frequency**: Approximately every n/2 insertions

## Choosing Good Hash Functions

### Properties of Good Hash Functions
1. **Fast computation** - O(1) time
2. **Uniform distribution** - spreads keys evenly
3. **Deterministic** - same key always gives same hash
4. **Avalanche effect** - small key changes cause large hash changes

### Common Pitfalls
```cpp
// BAD: Only uses first character
hash(string s) { return s[0] % tableSize; }

// BAD: Predictable pattern
hash(int k) { return k; }  // When keys are 1,2,3,4...

// GOOD: Uses all characters
hash(string s) {
    int result = 0;
    for (char c : s) {
        result = result * 31 + c;
    }
    return result % tableSize;
}
```

```cpp

// Consider expected data size

```

### 2. Monitor Load Factor
```cpp
void insert(key, value) {
    if (loadFactor() > MAX_LOAD_FACTOR) {
        resize();
    }
    // ... insertion logic
}
```

### 3. Handle Resize Gracefully
```cpp
void resize() {
    vector<list<pair>> oldTable = table;
    table.clear();
    table.resize(nextPrime(oldTable.size() * 2));
    
    // Rehash all elements
    for (auto& chain : oldTable) {
        for (auto& pair : chain) {
            insertWithoutResize(pair.key, pair.value);
        }
    }
}
```

### 4. Provide Clear API
```cpp
class HashTable {
public:
    void insert(K key, V value);           // Insert or update
    bool search(K key, V& value);          // Search with output parameter  
    V get(K key);                          // Search with exception on miss

    bool remove(K key);                    // Delete operation
    void clear();                          // Remove all elements
};
```

## Common Interview Questions

### 1. "How do you handle collisions?"
**Answer**: Mainly two approaches:
- **Separate chaining**: Each slot has a linked list
- **Open addressing**: Find next empty slot with probing

### 2. "What's a good load factor?"
**Answer**: Around 0.75 for separate chaining. Higher wastes space, lower degrades performance. For open addressing, keep below 0.7.

### 3. "How do you resize a hash table?"
**Answer**: Create larger table (usually 2x), rehash all existing elements into new table. O(n) operation but amortized O(1) per insertion.

### 4. "Why is average case O(1) but worst case O(n)?"
**Answer**: With good hash function, elements distribute evenly (short chains). With bad hash function or adversarial input, all elements might hash to same slot (long chain).
