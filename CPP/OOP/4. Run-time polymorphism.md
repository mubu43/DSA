# 1. What Is Run-Time Polymorphism?

> **Run-time polymorphism** means the function to be executed is decided **at runtime**, based on the *dynamic type* of the object, not the pointer/reference type.

In C++, this is achieved using:

* **Inheritance**
* **Virtual functions**
* **Base-class pointers or references**

---

## Simple example

```cpp
#include <iostream>

class Base {
public:
    virtual void process() {
        std::cout << "Base process\n";
    }

    virtual ~Base() = default;
};

class Derived : public Base {
public:
    void process() override {
        std::cout << "Derived process\n";
    }
};

int main() {
    Base* obj = new Derived();
    obj->process();   // calls Derived::process()
    delete obj;
}
```

Even though `obj` is a `Base*`, **Derived’s implementation runs**.

---

# 2. Why Run-Time Polymorphism Exists

Compile-time polymorphism (templates):

* Requires knowing types at compile time

Run-time polymorphism:

* Allows behavior to change **dynamically**
* Enables plugins, extensibility, frameworks, and ABI stability

---

# 3. How C++ Implements It Internally (Key Insight)

C++ uses:

* **vtable** (virtual table)
* **vptr** (virtual pointer)

> **This is not mandated by the C++ standard**, but is how *all mainstream compilers* implement it.

---

# 4. Memory Layout (Conceptual)

For a class with virtual functions:

```cpp
class Base {
    virtual void process();
};
```

### Object layout in memory (simplified)

```
Base object:
+------------------+
| vptr             | ---> vtable for Base
+------------------+
| Base data        |
+------------------+
```

For `Derived`:

```
Derived object:
+------------------+
| vptr             | ---> vtable for Derived
+------------------+
| Base data        |
+------------------+
| Derived data     |
+------------------+
```

Each object contains **one hidden pointer** → `vptr`.

---

# 5. What Is a vtable?

A **vtable** is a table of function pointers.

### Base vtable

```
Base vtable:
+-------------------+
| &Base::process   |
| &Base::~Base     |
+-------------------+
```

### Derived vtable

```
Derived vtable:
+----------------------+
| &Derived::process   |
| &Derived::~Derived  |
+----------------------+
```

Derived **overrides** entries.

---

# 6. Step-by-Step: Virtual Call Execution

```cpp
Base* obj = new Derived();
obj->process();
```

### What happens internally

1. `obj` points to a `Derived` object
2. Compiler emits code to:

   * Read `vptr` from `obj`
   * Index into vtable
   * Fetch function pointer for `process`
   * Call it

### Pseudocode

```cpp
obj->vptr->process(obj);
```

✔️ The **dynamic type** determines behavior.

---

# 7. Why Destructor Must Be Virtual

```cpp
Base* obj = new Derived();
delete obj;
```

If destructor is not virtual:

* Only `Base` destructor runs
* `Derived` resources leak

### Correct

```cpp
virtual ~Base() = default;
```

---

# 8. Cost of Run-Time Polymorphism

### Runtime costs

* One extra pointer dereference
* One indirect function call
* Prevents inlining

### Memory costs

* One `vptr` per object (usually 8 bytes)

### Compared to templates

| Aspect      | Runtime | Compile-time |
| ----------- | ------- | ------------ |
| Dispatch    | vtable  | Direct       |
| Inlining    | No      | Yes          |
| Overhead    | Small   | Zero         |
| Flexibility | High    | Low          |

---

# 9. Example Showing Why It’s Needed

### Plugin-like behavior

```cpp
void process(Base& obj) {
    obj.process();  // behavior depends on runtime type
}
```

You **cannot do this with templates** unless all types are known at compile time.

---

# 10. Common Pitfalls (Interview Gold)

### ❌ Calling virtuals in constructor

```cpp
Base() {
    process();  // calls Base::process, not Derived
}
```

Because:

* Derived part not constructed yet
* vptr points to Base vtable

---

### ❌ Object slicing

```cpp
Derived d;
Base b = d;   // slicing
b.process();  // Base::process
```

Always use **pointers or references**.

---

# 11. When to Use Run-Time Polymorphism

Use it when:

* Behavior must change dynamically
* You need a stable interface
* Plugins or extensions are involved
* ABI compatibility matters

Avoid it when:

* Performance is critical
* Types are known at compile time
* Tight loops / hot paths

---

# 12. Real-World Usage (Systems / Telecom)

Run-time polymorphism often combined with:

* RAII
* Smart pointers
* Factory patterns
