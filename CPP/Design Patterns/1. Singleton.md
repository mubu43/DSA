# 1. What Is the Singleton Pattern?

> A **Singleton** ensures that a class has **exactly one instance** and provides a **global access point** to it.

In short:

* Only **one object**
* **Controlled creation**
* Accessible from anywhere

---

# 2. The Problem It Solves

Without Singleton:

* Multiple parts of the program may accidentally create **multiple instances**
* This can cause:

  * Inconsistent state
  * Resource contention
  * Incorrect behavior

### Typical resources that must be unique

* Logger
* Configuration manager
* Statistics collector
* Hardware interface
* Global registry

---

# 3. The Simplest and Correct Singleton (Modern C++)

### ✅ Meyers’ Singleton (Recommended)

```cpp
#include <iostream>

class Logger {
public:
    static Logger& instance() {
        static Logger instance;  // created once, thread-safe (C++11+)
        return instance;
    }

    void log(const std::string& msg) {
        std::cout << msg << "\n";
    }

private:
    Logger() = default;                 // private constructor
    Logger(const Logger&) = delete;     // no copying
    Logger& operator=(const Logger&) = delete;
};
```

### Usage

```cpp
int main() {
    Logger::instance().log("Hello");
    Logger::instance().log("World");
}
```

---

## Why this works internally

* `static` local variable:

  * Initialized **once**
  * Guaranteed **thread-safe since C++11**
* Constructor is private → no external creation
* Copy/move disabled → only one instance

---

# 4. What Problem This Solves (Concrete Example)

### Without Singleton (bug-prone)

```cpp
Logger l1;
Logger l2;   // two loggers → two files / two buffers
```

### With Singleton

```cpp
Logger& l1 = Logger::instance();
Logger& l2 = Logger::instance();

// l1 and l2 refer to the same object
```

---

# 5. Lazy Initialization vs Eager Initialization

### Lazy (created only when needed)

✔️ Meyers’ singleton does this

### Eager (created at startup)

```cpp
class Config {
public:
    static Config instance;
};
Config Config::instance;
```

❌ Avoid this due to:

* Static initialization order issues
* Unnecessary startup cost

---

# 6. Thread-Safety Concern (Old C++ vs Modern)

### ❌ Broken (pre-C++11 style)

```cpp
static Logger* instance = nullptr;

if (!instance)
    instance = new Logger();  // race condition
```

### ✅ Correct (C++11+)

```cpp
static Logger instance;
```

Compiler generates proper synchronization.

# 7. Realistic Systems Example (Telecom-Style)

### Global statistics collector

```cpp
class Stats {
public:
    static Stats& instance() {
        static Stats s;
        return s;
    }

    void incrementCalls() {
        ++callCount_;
    }

    int calls() const {
        return callCount_;
    }

private:
    Stats() = default;
    std::atomic<int> callCount_{0};
};
```

Used across modules without passing references everywhere.

---

# 8. What Problems Singleton Solves Well

✔️ Guarantees **single instance**
✔️ Centralizes access to shared resource
✔️ Avoids passing references everywhere
✔️ Lazy and efficient initialization

---

# 9. Common Problems with Singleton (Very Important)

### ❌ Hidden global state

* Hard to reason about
* Makes testing difficult

### ❌ Tight coupling

* Code depends on a global object

### ❌ Hard to mock

* Unit tests become painful

---

# 10. When You SHOULD Use Singleton

Use it when:

* Resource must be unique
* Lifetime = entire program
* State is global by nature

Examples:

* Logger
* Metrics
* Configuration
* Hardware abstraction layer

---

# 11. When You SHOULD NOT Use Singleton

Avoid when:

* You want testability
* Object should be replaceable
* Dependency injection is possible

Prefer:

```cpp
void process(Logger& logger);
```

---

# 12. Interview-Level Summary

### One-line definition

> “A singleton ensures a class has exactly one instance and provides a global access point to it.”

### One-line best practice

> “Use Meyers’ Singleton in modern C++, and use it sparingly.”
