# 1. What Problem Does the PImpl Pattern Solve?

### Core problems it addresses

1. **Long compile times**

   * Header changes force massive recompilation
2. **ABI stability**

   * Binary compatibility across releases
3. **Encapsulation**

   * Hide private data and dependencies
4. **Header pollution**

   * Avoid including heavy headers everywhere

---

# 2. Without PImpl (Problematic Design)

### `player.h`

```cpp
#pragma once
#include <vector>
#include <string>
#include <mutex>   // heavy dependency

class AudioPlayer {
public:
    void play();

private:
    std::vector<int> buffer_;
    std::string device_;
    std::mutex mtx_;
};
```

### Problems

* Any change in private members → **recompile everything**
* Header leaks `<vector>`, `<mutex>`
* ABI breaks if layout changes

---

# 3. PImpl Pattern (Basic Example)

## Step 1: Header File (Public Interface Only)

### `player.h`

```cpp
#pragma once
#include <memory>

class AudioPlayer {
public:
    AudioPlayer();
    ~AudioPlayer();          // important!

    void play();

private:
    class Impl;              // forward declaration
    std::unique_ptr<Impl> impl_;
};
```

✔️ No STL headers
✔️ No private data exposed
✔️ Stable interface

---

## Step 2: Implementation File

### `player.cpp`

```cpp
#include "player.h"

#include <iostream>
#include <vector>
#include <string>
#include <mutex>

class AudioPlayer::Impl {
public:
    void play() {
        std::lock_guard<std::mutex> lock(mtx);
        std::cout << "Playing audio on " << device << "\n";
    }

private:
    std::vector<int> buffer;
    std::string device = "default";
    std::mutex mtx;
};

AudioPlayer::AudioPlayer()
    : impl_(std::make_unique<Impl>()) {}

AudioPlayer::~AudioPlayer() = default;

void AudioPlayer::play() {
    impl_->play();
}
```

---

# 4. How This Solves the Problems

| Problem        | Solution                           |
| -------------- | ---------------------------------- |
| Header changes | Private changes don’t touch header |
| Compile time   | Massive reduction                  |
| ABI stability  | Size/layout hidden                 |
| Encapsulation  | Strong separation                  |

---

# 5. Why Destructor Must Be Defined in `.cpp`

This is **very important**.

```cpp
~AudioPlayer();
```

* `std::unique_ptr<Impl>` needs the **complete type** to delete
* Impl is only defined in `.cpp`
* So destructor must be **out-of-line**

✅ This avoids undefined behavior

# 6. When PImpl Is Useful

### Use PImpl when:

* Library or SDK development
* Large projects with long build times
* ABI compatibility matters
* You want to hide implementation details

### Real-world examples

* `std::fstream`
* `std::regex`
* Qt classes
* LLVM APIs

---

# 7. Performance Cost?

### Overhead

* One extra pointer indirection
* One heap allocation

### In practice

* Negligible for:

  * IO
  * Networking
  * Media
* Avoid for:

  * Tiny hot-path objects

---

# 8. Variations of PImpl

### 1️⃣ `unique_ptr` (most common)

```cpp
std::unique_ptr<Impl>
```

### 2️⃣ `shared_ptr`

* Useful when copying objects cheaply

### 3️⃣ Value-PImpl (C++20-ish)

* No heap allocation
* More complex

# 9. Copy / Move with PImpl

### Disable copy, allow move

```cpp
AudioPlayer(const AudioPlayer&) = delete;
AudioPlayer& operator=(const AudioPlayer&) = delete;

AudioPlayer(AudioPlayer&&) = default;
AudioPlayer& operator=(AudioPlayer&&) = default;
```
