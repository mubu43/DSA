# 1. What Problem Does the Factory Pattern Solve?

### The core problem

> **Object creation logic gets mixed with business logic**, and the code becomes:

* Hard to extend
* Hard to test
* Full of `if/else` or `switch` statements

---

## Without Factory (Problematic)

```cpp
#include <iostream>
#include <memory>

class AudioDecoder {
public:
    virtual void decode() = 0;
    virtual ~AudioDecoder() = default;
};

class Mp3Decoder : public AudioDecoder {
public:
    void decode() override {
        std::cout << "Decoding MP3\n";
    }
};

class AacDecoder : public AudioDecoder {
public:
    void decode() override {
        std::cout << "Decoding AAC\n";
    }
};

void play(const std::string& type) {
    std::unique_ptr<AudioDecoder> decoder;

    if (type == "mp3") {
        decoder = std::make_unique<Mp3Decoder>();
    } else if (type == "aac") {
        decoder = std::make_unique<AacDecoder>();
    }

    decoder->decode();
}
```

### Problems

* Creation logic scattered
* Adding a new decoder means editing `play()`
* Violates **Open/Closed Principle**

---

# 2. Simple Factory (Static Factory Function)

### Solution

Move creation logic into **one place**.

```cpp
class DecoderFactory {
public:
    static std::unique_ptr<AudioDecoder> create(const std::string& type) {
        if (type == "mp3")
            return std::make_unique<Mp3Decoder>();
        if (type == "aac")
            return std::make_unique<AacDecoder>();
        return nullptr;
    }
};
```

### Usage

```cpp
void play(const std::string& type) {
    auto decoder = DecoderFactory::create(type);
    decoder->decode();
}
```

### What improved

✔️ Object creation is centralized
✔️ Business logic is cleaner

# 3. Factory Method Pattern (Classic GoF)

This is the **real design pattern**.

### Step 1: Base Factory Interface

```cpp
class DecoderFactory {
public:
    virtual std::unique_ptr<AudioDecoder> createDecoder() = 0;
    virtual ~DecoderFactory() = default;
};
```

---

### Step 2: Concrete Factories

```cpp
class Mp3Factory : public DecoderFactory {
public:
    std::unique_ptr<AudioDecoder> createDecoder() override {
        return std::make_unique<Mp3Decoder>();
    }
};

class AacFactory : public DecoderFactory {
public:
    std::unique_ptr<AudioDecoder> createDecoder() override {
        return std::make_unique<AacDecoder>();
    }
};
```

---

### Step 3: Client Code

```cpp
void play(DecoderFactory& factory) {
    auto decoder = factory.createDecoder();
    decoder->decode();
}

int main() {
    Mp3Factory mp3Factory;
    play(mp3Factory);

    AacFactory aacFactory;
    play(aacFactory);
}
```

---

### Why this is powerful

* No `if/else`
* New decoder → new factory
* Existing code unchanged

# 4. Where Factory Pattern Is Useful

### 1️⃣ When object creation is complex

* Multiple steps
* Dependencies
* Configuration-based creation

### 2️⃣ When you need run-time selection

```cpp
Factory chosen based on config / SIP message / SDP
```

### 3️⃣ When working with interfaces

Factories return **base class pointers**, not concrete types.

---

# 5. Real-World Systems Example (Telecom Style)

```cpp
class Transport {
public:
    virtual void send() = 0;
};

class UdpTransport : public Transport {};
class TcpTransport : public Transport {};

class TransportFactory {
public:
    static std::unique_ptr<Transport> create(bool reliable) {
        if (reliable)
            return std::make_unique<TcpTransport>();
        return std::make_unique<UdpTransport>();
    }
};
```

Used in:

* RTP (UDP)
* Control plane (TCP)

---

# 6. Factory vs Constructor (Key Difference)

| Constructor      | Factory                   |
| ---------------- | ------------------------- |
| Creates one type | Can create multiple types |
| Fixed            | Extensible                |
| Public           | Can hide concrete classes |

---

# 7. Common Pitfalls

### ❌ Overusing factories

* Simple objects don’t need factories

### ❌ Factories returning raw pointers

* Always return `unique_ptr` or `shared_ptr`

### ❌ Massive `switch` in factory

* Refactor using registration maps

---

# 8. When NOT to Use Factory

Avoid when:

* Object creation is trivial
* Only one concrete type
* No runtime selection

---

# 9. One-Line Interview Answer

> “The Factory pattern encapsulates object creation logic, allowing clients to work with interfaces instead of concrete classes and enabling easy extension without modifying existing code.”
