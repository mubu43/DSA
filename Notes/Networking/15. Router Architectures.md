## IP Implementation Overview

In this lecture, we will understand how IP networking is implemented in a typical end host/router.

Most hosts implement IP in the **kernel**, so we will study IP networking in the Linux kernel (other OSes should be similar conceptually).

**Assumption:** First, assume that the routing and forwarding tables are populated in the kernel (we will discuss how this is done later). What happens when a packet is transmitted and received?

---

## Packet Transmission Path

When an application sends data:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      Packet Transmission Path                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   APPLICATION                                                           │
│       │                                                                 │
│       │ write() to socket                                               │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    SEND BUFFER                                   │  │
│   │   Data placed here until TCP transmits it                       │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       │ TCP: takes data, forms segment, adds header                    │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    TCP LAYER                                     │  │
│   │   Creates segment, calls IP transmit function                   │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       │ IP: adds header, looks up route, finds interface                │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    IP LAYER                                      │  │
│   │   Looks up destination address for route                        │  │
│   │   Finds interface/link to send on                               │  │
│   │   Places packet in OUTPUT QUEUE of the device                   │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       │ ← All above done during write() to socket                       │
│       │                                                                 │
│       ▼ Device driver scheduled later                                  │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    DEVICE DRIVER                                 │  │
│   │   Adds link layer headers                                       │  │
│   │   Hands over to network hardware                                │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       ▼                                                                 │
│   ════════════════════ NETWORK HARDWARE ════════════════════            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Summary:**
1. Application writes packet to kernel
2. Data written into the **send buffer**
3. TCP takes the data, forms a segment, adds header, calls IP transmit function (UDP does something similar)
4. IP adds header, looks up destination address for a route, finds out the interface/link to send it on, and places packet in the **output queue** of the device

> **Note:** All this is done when you do a "write" into a socket. From here on, the device driver takes over. The kernel schedules the device driver to run at a different time. The driver adds link layer headers and hands over to the network hardware.

## Packet Reception Path

When a packet arrives:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Packet Reception Path                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ════════════════════ NETWORK HARDWARE ════════════════════            │
│       │                                                                 │
│       │ Packet arrives on physical medium                               │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    DEVICE DRIVER                                 │  │
│   │   Stores packet in BACKLOG QUEUE in kernel                      │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       │ Kernel schedules handler later                                  │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    IP LAYER                                      │  │
│   │   Checks for errors                                             │  │
│   │   Checks destination: local host or another host?               │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       ├──────────────────────────────┐                                  │
│       │                              │                                  │
│       ▼ Destination = Local Host    ▼ Destination = Another Host       │
│   ┌───────────────────────┐    ┌───────────────────────────────────┐   │
│   │      TCP LAYER        │    │         IP FORWARDING             │   │
│   │                       │    │                                   │   │
│   │ Process TCP data      │    │ Look up destination address       │   │
│   │ Place in recv buffer  │    │ Update IP headers (e.g., TTL)     │   │
│   │ Update TCP state      │    │ Place in output queue of          │   │
│   │ (if ACK)              │    │ corresponding interface           │   │
│   └───────────────────────┘    └───────────────────────────────────┘   │
│       │                                                                 │
│       ▼                                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                    RECEIVE BUFFER                                │  │
│   │   Data ready for application to read()                          │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│       │                                                                 │
│       ▼                                                                 │
│   APPLICATION                                                           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Summary:**
1. Device driver stores the packet in a **backlog queue** in the kernel
2. Kernel scheduler schedules the kernel code to handle the packet at a later point
3. IP layer checks for errors
4. IP checks if the destination is the local host or another host:
   - **If local host:** Hand off to TCP for processing (process TCP data, place into receive buffer, update TCP state if it is a TCP ACK, etc.)
   - **If another host (forwarding):** Look up destination address, update IP headers (like TTL), and place packet in the output queue of the corresponding interface

## Routing in User Space

**The kernel only does forwarding.** The routing protocols themselves can be implemented as **userspace programs** (listening on well-known port numbers) that can modify the forwarding tables in the kernel based on the messages they send and receive.

| Software | Description |
|----------|-------------|
| **routed** | Simple program in Linux kernel that implements a simple intradomain routing protocol |
| **Quagga** | Popular software suite that implements several intra and interdomain routing protocols |

## Why Specialized Routers?

So we have seen that a Linux box can serve as a simple router. **Why do we need specialized routers?**

Because a Linux machine **cannot process packets at several Gbps**.

### Main Components

| Component | Function |
|-----------|----------|
| **Input Ports** | Perform L1/L2 (physical and link layer) functions. Destination IP lookup (coordinate with forwarding engine), update headers, send packet to output ports via switching fabric. Each input port may have a separate forwarding engine to achieve high-speed lookups. Several input ports are placed in a single **linecard** hardware. |
| **Forwarding Engine** | Performs longest prefix match using destination IP and forwarding table, returns the output port/link/interface the packet has to leave. In a simple Linux router, this is handled by CPU. |
| **Switching Fabric** | Responsible for transferring packets from input ports to output ports |
| **Output Ports** | Handle L1/L2 processing during transmission. Also responsible for any **scheduling policy** to be followed |
| **Routing Processor** | Runs routing protocols and computes forwarding tables. It is like a general-purpose CPU |

## Performance Budget

Let's calculate the time budget to process each packet:

**Example:** Consider a 10 Gbps link with 64-byte packets.

$$\text{Packet Rate} = \frac{10 \text{ Gb/s}}{64 \times 8 \text{ bits}} = \frac{10 \times 10^9}{512} \approx 20 \text{ million pps}$$

$$\text{Time per packet} = \frac{1}{20 \times 10^6} = 50 \text{ nanoseconds}$$

> In this time, we must **lookup the destination** and **transfer the packet to the output port**. These two tasks form the **bottleneck** of any router design.

## IP Forwarding Algorithms

### The Challenge of Longest Prefix Match (LPM)

The algorithms responsible for performing a **longest prefix match (LPM)** of the destination address are performed by the forwarding engine.

**Why is this a hard problem?**

With classful addressing, you had only 3 possible prefix lengths, so lookup was easy. Now, with **CIDR**, you can have any possible prefix length. So, we may have to lookup multiple routing table entries.

With a **50 ns budget** per packet, and typical memory access times being a few nanoseconds, we must lookup **very few entries** to meet this goal.

### Why Multiple Prefixes Cover One Address?

Several reasons (we will study in detail later). One of them is called **prefix hole punching**:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Prefix Hole Punching                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ISP has: 10.0.0.0/8 (large prefix)                                   │
│                                                                         │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                         10.0.0.0/8                               │  │
│   │   ┌─────────────────────────────────────────────────────────┐   │  │
│   │   │                    10.1.0.0/16                           │   │  │
│   │   │         (Customer's "hole" - different next hop)         │   │  │
│   │   └─────────────────────────────────────────────────────────┘   │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│   • ISP announces 10.0.0.0/8 (shorter prefix)                          │
│   • Customer gets 10.1.0.0/16 and announces via another ISP            │
│   • Routing table has BOTH entries                                      │
│   • Must match on LONGER prefix for correctness                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

The ISP has a larger (shorter) prefix and it gives a smaller (longer) prefix to the customer. Then the customer might announce this smaller prefix through other ISPs. So we see the shorter prefix from the ISP and longer prefix from the customer in the routing tables. **We must match on the longer one for correctness.**

### Data Structure: Trie

What is the simplest data structure to implement a forwarding table and do LPM? A **trie** (pronounced as "try").

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          Trie for IP Lookup                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Prefixes: 0*, 00*, 01*, 10*, 101*                                    │
│                                                                         │
│                              ROOT                                        │
│                             /    \                                       │
│                           0/      \1                                     │
│                           /        \                                     │
│                         [0*]      [10*]                                 │
│                        /    \         \                                  │
│                      0/      \1        \1                                │
│                      /        \         \                                │
│                   [00*]      [01*]    [101*]                            │
│                                                                         │
│   To lookup 1011:                                                       │
│   • Start at root                                                       │
│   • Go right (1) → match [10*]                                         │
│   • Go left (0) → no entry                                              │
│   • Go right (1) → match [101*]   ← LONGEST MATCH                      │
│   • Go right (1) → no more entries                                      │
│                                                                         │
│   Return: [101*] as the longest matching prefix                         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**How it works:**
- A trie is a tree-like structure
- Every node has 2 branches for 0 and 1
- The nodes at any level hold information about the prefix formed by walking down the tree up to that level
- Branches that do not have any prefixes are pruned
- To perform LPM, walk down the tree as far as possible

**Problem:** This method can take **O(N) lookups**, where N is the length of the IP address. And each level of the tree may be in a separate memory location. So **too many memory lookups**.

### Improvements to Trie

| Approach | Description |
|----------|-------------|
| **Path Compressed Tries** | Compress portions of the tree that do not have many branches |
| **Binary Search on Prefix Length** | Organize prefixes into different sets based on length. Do a binary search on prefixes at various lengths. Takes O(log N) steps |
| **Interval-Based Methods** | Represent prefixes as intervals, find the shortest interval that holds a certain prefix |

A lot of work has been done on efficient algorithms using all these approaches.

## Switching Fabric Designs

### Crossbar Switch

The most common design is a **crossbar**.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         Crossbar Switch                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│              Output 1    Output 2    Output 3    Output 4               │
│                 │           │           │           │                   │
│   Input 1  ─────●───────────┼───────────●───────────┼─────              │
│                 │           │           │           │                   │
│   Input 2  ─────┼───────────●───────────┼───────────┼─────              │
│                 │           │           │           │                   │
│   Input 3  ─────┼───────────┼───────────┼───────────●─────              │
│                 │           │           │           │                   │
│   Input 4  ─────┼───────────┼───────────┼───────────┼─────              │
│                 │           │           │           │                   │
│                                                                         │
│   ● = Active connection (crosspoint)                                    │
│                                                                         │
│   In this example:                                                      │
│   • Input 1 → Output 1 and Output 3                                    │
│   • Input 2 → Output 2                                                 │
│   • Input 3 → Output 4                                                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**How it works:**
- A crossbar consists of N data transfer "buses" running from each of N inputs, and N buses from each of N outputs
- The crossbar can be configured to allow any input port to send to any output port
- Every input will have packets to some outputs, and a **bipartite matching** will be done from inputs to outputs to configure the crossbar for each round
- In the matching, every input can be paired with only one output, and every output with only one input

**Performance:**
- A crossbar can potentially transfer N packets from N input ports to N output ports
- In the best case, it can keep the inputs and outputs fully utilized
- A crossbar is the most common fabric design used in high-speed routers today

### Speedup

The **speedup** of the crossbar is defined as the speed of the crossbar I/O bus relative to the input port line speed.

**Example:** If the inputs are 1 Gbps links, and the crossbar can potentially transfer 10 Gbps between each pair of matched input and output in each round of the crossbar schedule, then speedup is 10.

In practice, you need a **speedup > 1** to achieve good performance.

> **Note:** The actual performance depends on which inputs and outputs are popular, how efficiently you can match, etc. For example, if all inputs always send to the same output, then the crossbar cannot schedule many packets in parallel, and you will get degraded performance even if the speedup is high.

## Router Queueing

Recall we discussed buffers at routers, buffer drops, scheduling, etc. Where do all of these happen in the router? At input ports or output ports?

### Input Queueing (IQ)

**Input ports need to have queues**, since the switching fabric may not always be available to transport the packet.

**Scenario:** Suppose there are N inputs and N outputs. Suppose the switching fabric speed is the same as input line speed (speedup = 1). If all inputs have packets for only one output, then the fabric can send packets of only one input to the output. And all but one input that is matched will have to queue the packets. This is called **Input Queueing (IQ)**.

If the switching fabric speed is N times that of the input speed (speedup = N), then the fabric can transfer all N packets from all N ports in the time that each port receives one packet. So, in such cases, IQ won't be needed.

In general, the switching fabric speed is not N times but greater than input line speed, so a small amount of queueing may occur. A reasonable speedup (say 2X), a reasonable distribution of traffic from inputs to outputs (not all inputs going to same output always), and a good matching algorithm can avoid too much input queueing.

### Head-of-Line (HoL) Blocking

**Problem:** What if the first packet in the input queue is to a busy output port, but the rest of the packets are to free output ports?

If we have only one queue for all packets destined to all outputs, we may have **head-of-line (HoL) blocking**. That is, we cannot send the first packet (to the busy output port), so we don't even get to the packets destined to less busy ports.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Head-of-Line (HoL) Blocking                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Input Queue (single queue):                                           │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │  [Pkt→Out1] [Pkt→Out2] [Pkt→Out3] [Pkt→Out2] [Pkt→Out4]        │  │
│   │      ▲                                                          │  │
│   │      │                                                          │  │
│   │   HEAD (blocked - Output 1 is busy!)                            │  │
│   └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│   ⚠ Even though Outputs 2, 3, 4 are FREE, we can't send to them!      │
│                                                                         │
│   Solution: Virtual Output Queueing (VOQ)                              │
│   ┌─────────────┬─────────────┬─────────────┬─────────────┐           │
│   │ Queue→Out1  │ Queue→Out2  │ Queue→Out3  │ Queue→Out4  │           │
│   │   [Pkt]     │ [Pkt][Pkt]  │   [Pkt]     │   [Pkt]     │           │
│   │   (blocked) │   (ready!)  │  (ready!)   │  (ready!)   │           │
│   └─────────────┴─────────────┴─────────────┴─────────────┘           │
│                                                                         │
│   ✓ Now we can send to Outputs 2, 3, 4 even if Out1 is busy!          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Virtual Output Queueing (VOQ)

To avoid HoL blocking, inputs have **different queues for packets destined for different output ports**.

That is, after a packet arrives:
1. Forwarding table is looked up
2. Packet is placed in a queue at the input port
3. Packets destined to different outputs reside in different sub-queues

This is called **Virtual Output Queueing (VOQ)**.

### Output Queueing

After crossing the fabric, **outputs also have queues** to implement QoS-related scheduling policies. It makes sense to implement these at the output queue because we want to distribute the outgoing link bandwidth between flows.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Complete Router Queueing Picture                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   INPUT PORTS                                      OUTPUT PORTS         │
│   (VOQ at each input)                             (Scheduling queues)   │
│                                                                         │
│   ┌─────────────┐                                 ┌─────────────┐      │
│   │ Input 1     │                                 │ Output 1    │      │
│   │ ┌─┬─┬─┬─┐   │                                 │ ┌─────────┐ │      │
│   │ │1│2│3│4│   │         ┌───────────┐          │ │Priority │ │      │
│   │ └─┴─┴─┴─┘   │────────►│           │─────────►│ │Scheduler│ │      │
│   │  VOQs       │         │ SWITCHING │          │ └─────────┘ │      │
│   └─────────────┘         │  FABRIC   │          └─────────────┘      │
│                           │           │                                 │
│   ┌─────────────┐         │           │          ┌─────────────┐      │
│   │ Input 2     │         │           │          │ Output 2    │      │
│   │ ┌─┬─┬─┬─┐   │────────►│           │─────────►│ ┌─────────┐ │      │
│   │ │1│2│3│4│   │         │           │          │ │Priority │ │      │
│   │ └─┴─┴─┴─┘   │         └───────────┘          │ │Scheduler│ │      │
│   │  VOQs       │                                 │ └─────────┘ │      │
│   └─────────────┘                                 └─────────────┘      │
│                                                                         │
│   VOQ: Avoids HoL blocking                                              │
│   Output Scheduler: Implements QoS policies                            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## Summary

| Component | Function |
|-----------|----------|
| **Input Ports** | L1/L2 processing, IP lookup, header update |
| **Forwarding Engine** | Longest Prefix Match (LPM) |
| **Switching Fabric** | Transfer packets between ports (crossbar) |
| **Output Ports** | L1/L2 processing, scheduling |
| **Routing Processor** | Runs routing protocols, computes tables |

| Concept | Description |
|---------|-------------|
| **Trie** | Tree structure for LPM, O(N) worst case |
| **Path Compression** | Optimization to reduce trie depth |
| **Crossbar** | Common switching fabric, supports parallel transfers |
| **Speedup** | Fabric speed / Line speed ratio |
| **Input Queueing** | Queues at input when fabric is busy |
| **HoL Blocking** | First packet blocks others in single queue |
| **VOQ** | Separate queues per destination, avoids HoL |
| **Output Queueing** | QoS and scheduling at output ports |
