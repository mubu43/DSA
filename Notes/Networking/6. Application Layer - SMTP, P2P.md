## SMTP (Simple Mail Transfer Protocol)

### Overview

SMTP is the protocol used to **transfer email** from mail servers of senders to mail servers of recipients.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Email Architecture                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ┌──────────┐        ┌──────────────┐        ┌──────────────┐        │
│   │  User    │        │   Sender's   │        │  Recipient's │        │
│   │  Agent   │───────►│  Mail Server │═══════►│  Mail Server │        │
│   │ (Outlook)│  SMTP  │              │  SMTP  │              │        │
│   └──────────┘        └──────────────┘        └──────┬───────┘        │
│                                                      │                 │
│                                                      │ POP3/IMAP      │
│                                                      ▼                 │
│                                               ┌──────────┐            │
│                                               │  User    │            │
│                                               │  Agent   │            │
│                                               └──────────┘            │
│                                                                         │
│   SMTP: Push protocol (sender initiates)                               │
│   POP3/IMAP: Pull protocol (recipient fetches)                         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### SMTP Protocol Details

| Aspect | Details |
|--------|---------|
| **Port** | 25 |
| **Transport** | TCP (reliable delivery) |
| **Type** | Push protocol |
| **Connection** | Persistent (multiple messages per connection) |
| **Encoding** | 7-bit ASCII for all content |

### SMTP Commands

| Command | Description | Example |
|---------|-------------|---------|
| `HELO` | Handshake, identify client | `HELO crepes.fr` |
| `MAIL FROM` | Specify sender | `MAIL FROM: <alice@crepes.fr>` |
| `RCPT TO` | Specify recipient | `RCPT TO: <bob@hamburger.edu>` |
| `DATA` | Begin message body | `DATA` |
| `QUIT` | Close connection | `QUIT` |

### SMTP Response Codes

| Code | Meaning |
|------|---------|
| 220 | Service ready |
| 250 | OK (action completed) |
| 354 | Start mail input |
| 421 | Service unavailable |
| 450 | Mailbox unavailable |
| 500 | Syntax error |

### Sample SMTP Session

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        SMTP Session Example                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   S: 220 hamburger.edu SMTP Ready                                       │
│   C: HELO crepes.fr                                                     │
│   S: 250 Hello crepes.fr                                                │
│   C: MAIL FROM: <alice@crepes.fr>                                       │
│   S: 250 OK                                                             │
│   C: RCPT TO: <bob@hamburger.edu>                                       │
│   S: 250 OK                                                             │
│   C: DATA                                                               │
│   S: 354 Start mail input; end with <CRLF>.<CRLF>                       │
│   C: From: alice@crepes.fr                                              │
│   C: To: bob@hamburger.edu                                              │
│   C: Subject: Hello!                                                    │
│   C:                                                                    │
│   C: This is the message body.                                          │
│   C: .                                                                  │
│   S: 250 Message accepted                                               │
│   C: QUIT                                                               │
│   S: 221 Bye                                                            │
│                                                                         │
│   Note: Message ends with a line containing ONLY a period (.)           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### SMTP vs HTTP Comparison

| Aspect | HTTP | SMTP |
|--------|------|------|
| **Direction** | Pull (client requests) | Push (sender initiates) |
| **Object handling** | Each object in separate response | All objects in one message |
| **Encoding** | Binary data allowed | 7-bit ASCII only (use MIME for binary) |
| **Persistent** | Optional | Default |

## Mail Access Protocols

### The Problem

SMTP is a **push protocol** — it pushes mail from sender to recipient's server. But how does the **recipient read the mail**?

The recipient needs to **pull** messages from their mailbox on the mail server.

### Protocol Options

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      Mail Access Protocols                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ┌──────────┐     ┌──────────────┐                                    │
│   │   Mail   │◄────│    User      │                                    │
│   │  Server  │     │    Agent     │                                    │
│   └──────────┘     └──────────────┘                                    │
│        │                                                                │
│        │   Options:                                                     │
│        │                                                                │
│        ├── POP3 (Port 110)    Simple download-and-delete               │
│        │                                                                │
│        ├── IMAP (Port 143)    Server-side folders, sync across devices │
│        │                                                                │
│        └── HTTP (Webmail)     Gmail, Outlook.com, etc.                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### POP3 (Post Office Protocol v3)

**Simple protocol** for downloading mail:

| Phase | Commands |
|-------|----------|
| **Authorization** | `USER`, `PASS` |
| **Transaction** | `LIST`, `RETR`, `DELE` |
| **Update** | Apply deletions after `QUIT` |

**Modes:**
- **Download-and-delete**: Messages removed from server after download
- **Download-and-keep**: Messages remain on server

**Limitations:**
- Stateless across sessions
- No server-side folders
- Hard to access from multiple devices

### IMAP (Internet Mail Access Protocol)

**More sophisticated protocol:**

| Feature | Description |
|---------|-------------|
| **Server-side folders** | Organize mail in folders on server |
| **State across sessions** | Server tracks which messages read |
| **Partial fetch** | Can fetch parts of messages (e.g., just headers) |
| **Multi-device access** | Sync state across all devices |

### Webmail

Modern approach using **HTTP**:
- User accesses mailbox via web browser
- Server provides web interface
- Examples: Gmail, Outlook.com, Yahoo Mail
- Often IMAP is used between webmail server and mail server

## Web Services (REST and RPC)

### Communication Between Applications

Beyond human users accessing web servers, **applications communicate with each other** over HTTP.

### REST (Representational State Transfer)

REST is an **architectural style** for web services:

| Principle | Description |
|-----------|-------------|
| **Stateless** | Each request contains all info needed |
| **Resource-based** | Everything is a resource with a URI |
| **Standard methods** | Use HTTP methods (GET, POST, PUT, DELETE) |
| **Representations** | Resources represented as JSON/XML |

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       REST API Example                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Resource: /users/123                                                  │
│                                                                         │
│   ┌────────────┬────────────────────────────────────────────────────┐ │
│   │  Method    │  Action                                            │ │
│   ├────────────┼────────────────────────────────────────────────────┤ │
│   │  GET       │  Retrieve user 123's information                   │ │
│   │  POST      │  Create new user (on /users)                       │ │
│   │  PUT       │  Update user 123's information                     │ │
│   │  DELETE    │  Delete user 123                                   │ │
│   └────────────┴────────────────────────────────────────────────────┘ │
│                                                                         │
│   Example Request:                                                      │
│   GET /users/123 HTTP/1.1                                              │
│   Host: api.example.com                                                 │
│   Accept: application/json                                              │
│                                                                         │
│   Example Response:                                                     │
│   {                                                                     │
│     "id": 123,                                                          │
│     "name": "Alice",                                                    │
│     "email": "alice@example.com"                                        │
│   }                                                                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### RPC (Remote Procedure Call)

**RPC Style** treats network calls like local function calls:

| Aspect | RPC Style |
|--------|-----------|
| **Focus** | Actions/procedures |
| **Request** | Function name + parameters |
| **Examples** | SOAP, XML-RPC, gRPC |

### REST vs RPC

| Aspect | REST | RPC |
|--------|------|-----|
| **Orientation** | Resource-oriented | Action-oriented |
| **URL design** | `/users/123` | `/getUser?id=123` |
| **HTTP methods** | Uses GET/POST/PUT/DELETE semantically | Often all POST |
| **Caching** | Easy (GET is cacheable) | Harder |
| **Discovery** | URLs are self-describing | Need documentation |

## Peer-to-Peer (P2P) Systems

### Client-Server vs P2P

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Client-Server vs Peer-to-Peer                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   CLIENT-SERVER                         PEER-TO-PEER                    │
│                                                                         │
│        ┌───────┐                            ┌───┐                       │
│        │Server │                         ┌──│ P │──┐                    │
│        └───┬───┘                         │  └───┘  │                    │
│            │                            ┌───┐   ┌───┐                   │
│     ┌──────┼──────┐                     │ P │───│ P │                   │
│     │      │      │                     └───┘   └───┘                   │
│   ┌───┐  ┌───┐  ┌───┐                      \   /                        │
│   │ C │  │ C │  │ C │                       ┌───┐                       │
│   └───┘  └───┘  └───┘                       │ P │                       │
│                                             └───┘                       │
│                                                                         │
│   • Single point of failure        • No single point of failure        │
│   • Server is bottleneck           • Resources scale with users        │
│   • Easy to manage                 • Complex coordination              │
│   • Bandwidth at server            • Aggregate peer bandwidth          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### P2P Advantages

| Advantage | Description |
|-----------|-------------|
| **Scalability** | Adding peers adds capacity |
| **Fault tolerance** | No single point of failure |
| **Resource sharing** | Utilize idle resources across peers |

### P2P Challenges

| Challenge | Description |
|-----------|-------------|
| **Discovery** | How to find peers with desired content? |
| **Churn** | Peers join and leave frequently |
| **Free-riding** | Some peers consume without contributing |
| **Security** | No central authority for trust |

## BitTorrent

### Overview

BitTorrent is the most successful P2P file distribution protocol:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      BitTorrent Architecture                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ┌──────────────────────────────────────────────────────────────────┐ │
│   │                         TRACKER                                  │ │
│   │  (Keeps track of peers participating in torrent)                 │ │
│   └────────────────────────────┬─────────────────────────────────────┘ │
│                                │                                        │
│              "Who has pieces?" │ "Here's a list of peers"              │
│                                ▼                                        │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │                          SWARM                                  │   │
│   │                                                                  │   │
│   │    ┌─────┐      ┌─────┐      ┌─────┐      ┌─────┐             │   │
│   │    │Peer │◄────►│Peer │◄────►│Peer │◄────►│Peer │             │   │
│   │    │[###]│      │[## ]│      │[#  ]│      │[###]│             │   │
│   │    └─────┘      └─────┘      └─────┘      └─────┘             │   │
│   │       ▲            │            │            ▲                  │   │
│   │       └────────────┴────────────┴────────────┘                  │   │
│   │                                                                  │   │
│   │    Each peer has different pieces, exchanges with others        │   │
│   │                                                                  │   │
│   └────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│   SEEDER: Has complete file     LEECHER: Still downloading             │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Torrent file** | Metadata file containing tracker URL and file hash |
| **Tracker** | Server that coordinates peers in a swarm |
| **Swarm** | Group of peers sharing a particular file |
| **Piece** | Fixed-size chunk of the file (typically 256KB) |
| **Seeder** | Peer with complete file |
| **Leecher** | Peer still downloading |

### BitTorrent Mechanisms

#### 1. Piece Selection: Rarest First

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Rarest First Strategy                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Piece availability in swarm:                                          │
│                                                                         │
│   Piece 1: [■■■■■■■■■■] 10 peers have it                              │
│   Piece 2: [■■■■■■■■  ]  8 peers have it                              │
│   Piece 3: [■■        ]  2 peers have it  ◄── Download this first!    │
│   Piece 4: [■■■■■■    ]  6 peers have it                              │
│   Piece 5: [■■■■■■■■■ ]  9 peers have it                              │
│                                                                         │
│   Why rarest first?                                                     │
│   • Prevents rare pieces from disappearing if seeder leaves            │
│   • Increases piece diversity in swarm                                  │
│   • Each peer becomes valuable by having rare pieces                   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 2. Peer Selection: Tit-for-Tat

**Problem:** Prevent free-riding (leechers who download but don't upload).

**Solution:** Prioritize peers who give you the best upload rates:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Tit-for-Tat Mechanism                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Every 10 seconds, evaluate peers:                                     │
│                                                                         │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │  Peer     │  Upload rate to me  │  Status                      │   │
│   ├───────────┼─────────────────────┼──────────────────────────────┤   │
│   │  Peer A   │  500 KB/s           │  UNCHOKED (I upload to them) │   │
│   │  Peer B   │  300 KB/s           │  UNCHOKED                    │   │
│   │  Peer C   │  200 KB/s           │  UNCHOKED                    │   │
│   │  Peer D   │  100 KB/s           │  UNCHOKED                    │   │
│   │  Peer E   │   50 KB/s           │  CHOKED (no upload)          │   │
│   │  Peer F   │   10 KB/s           │  CHOKED                      │   │
│   └───────────┴─────────────────────┴──────────────────────────────┘   │
│                                                                         │
│   Top 4 peers are "unchoked" — I upload to them                        │
│   Others are "choked" — I refuse to upload                             │
│                                                                         │
│   OPTIMISTIC UNCHOKING:                                                 │
│   Every 30 seconds, unchoke one random peer                            │
│   • Allows new peers to bootstrap                                       │
│   • Discover potentially better peers                                   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### BitTorrent Workflow

1. **Get .torrent file** (from website)
2. **Contact tracker** to get list of peers
3. **Connect to peers** and exchange piece availability
4. **Download rarest pieces first**
5. **Upload to peers** who upload to you (tit-for-tat)
6. **Become seeder** when download complete (optional but encouraged)

## Distributed Hash Tables (DHT)

### The Discovery Problem

**Problem:** In BitTorrent, trackers are single points of failure. How can we find peers **without a central server**?

**Solution:** Distributed Hash Table (DHT)

### What is a DHT?

A DHT provides a **distributed key-value store**:
- **Put(key, value)**: Store value at key
- **Get(key)**: Retrieve value for key

Keys and values are distributed across all participating nodes.

### Consistent Hashing

DHTs use **consistent hashing** to assign keys to nodes:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Consistent Hashing Ring                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                           0/2^m                                         │
│                             │                                           │
│                        ┌────┴────┐                                      │
│                   ┌────┤  Node A ├────┐                                 │
│                   │    └─────────┘    │                                 │
│                   │                   │                                 │
│               ┌───┴───┐           ┌───┴───┐                            │
│               │       │           │       │                            │
│      ┌────────┴──┐    │           │    ┌──┴────────┐                   │
│      │  Node D   │    │           │    │  Node B   │                   │
│      └───────────┘    │           │    └───────────┘                   │
│                       │           │                                     │
│                   ┌───┴───────────┴───┐                                │
│                   │      Node C       │                                │
│                   └───────────────────┘                                │
│                           │                                             │
│                         2^(m-1)                                         │
│                                                                         │
│   • Nodes positioned at hash(NodeID) on ring                           │
│   • Key stored at first node clockwise from hash(key)                  │
│   • Successor(key) = node responsible for key                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Key Assignment

- Each node is assigned an **ID** (hash of IP:port)
- Each key is assigned to the **successor node** (first node with ID ≥ key hash)
- When nodes join/leave, only keys of adjacent nodes are affected

### Routing in DHT (Chord Example)

**Simple approach:** Each node knows only its successor
- Route query around the ring
- **O(N)** hops for N nodes — too slow!

**Better approach:** Finger tables
- Each node maintains **O(log N)** fingers
- Finger i points to successor of $(n + 2^i) \mod 2^m$
- **O(log N)** hops for any lookup

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          Finger Table                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Node n's Finger Table (m-bit identifiers):                           │
│                                                                         │
│   ┌───────┬──────────────────┬─────────────────────┐                   │
│   │ Entry │  Start           │  Successor          │                   │
│   ├───────┼──────────────────┼─────────────────────┤                   │
│   │   0   │  n + 2^0 = n+1   │  first node ≥ n+1   │                   │
│   │   1   │  n + 2^1 = n+2   │  first node ≥ n+2   │                   │
│   │   2   │  n + 2^2 = n+4   │  first node ≥ n+4   │                   │
│   │   3   │  n + 2^3 = n+8   │  first node ≥ n+8   │                   │
│   │  ...  │  ...             │  ...                │                   │
│   │  m-1  │  n + 2^(m-1)     │  first node ≥ ...   │                   │
│   └───────┴──────────────────┴─────────────────────┘                   │
│                                                                         │
│   Fingers point exponentially further around ring                       │
│   → Can reach any node in O(log N) hops                                │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### DHT in BitTorrent

BitTorrent uses **Mainline DHT**:
- Key = info_hash (hash of torrent)
- Value = list of peers in swarm
- Eliminates need for central tracker

## Summary

| Topic | Key Points |
|-------|------------|
| **SMTP** | Push protocol for email transfer, port 25, 7-bit ASCII, persistent TCP |
| **Mail Access** | POP3 (simple download), IMAP (server folders, sync), Webmail (HTTP) |
| **REST** | Resource-oriented, stateless, uses HTTP methods semantically |
| **P2P** | Distributed resources, no central server, scales with users |
| **BitTorrent** | Rarest-first piece selection, tit-for-tat peer selection |
| **DHT** | Distributed key-value store, consistent hashing, O(log N) lookup |
