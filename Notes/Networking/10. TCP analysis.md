## Bandwidth-Delay Product Revisited

### Recall: BDP Definition

The **Bandwidth-Delay Product (BDP)** represents the amount of data "in flight" to keep the network pipe full:

$$BDP = Bandwidth \times RTT$$

| Example | Bandwidth | RTT | BDP |
|---------|-----------|-----|-----|
| LAN connection | 1 Gbps | 1 ms | 125 KB |
| Transcontinental | 1 Gbps | 50 ms | 6.25 MB |
| Intercontinental | 1 Gbps | 200 ms | 25 MB |

### Why BDP Matters for TCP

TCP uses a **sliding window** to control how much data is in flight. To fully utilize a link:

$$Window \geq BDP$$

If the window is smaller than BDP, the sender will be waiting for ACKs before it can send more data, **underutilizing** the link.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Window Size vs Link Utilization                       │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   WINDOW < BDP (Underutilization)                                       │
│                                                                         │
│   Sender                                                    Receiver    │
│   ┌───┐                                                     ┌───┐      │
│   │   │──[pkt1]──[pkt2]──[pkt3]────────────────────────────►│   │      │
│   │   │                                                     │   │      │
│   │   │◄──────────────────────────────────────────[ACK1]────│   │      │
│   │   │   ▲                                                 │   │      │
│   │   │   │ Idle! Waiting for ACK                          │   │      │
│   └───┘   ▼                                                 └───┘      │
│                                                                         │
│   WINDOW ≥ BDP (Full Utilization)                                       │
│                                                                         │
│   Sender                                                    Receiver    │
│   ┌───┐                                                     ┌───┐      │
│   │   │──[p1][p2][p3][p4][p5][p6]──────────────────────────►│   │      │
│   │   │──[p7][p8]...◄─────────────────────────────[ACK1]────│   │      │
│   │   │   ▲                                                 │   │      │
│   │   │   │ ACKs arrive continuously, can keep sending     │   │      │
│   └───┘   ▼                                                 └───┘      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## Buffer Sizing at Routers

### The Problem

**Question:** How much buffer should a router have on its output interfaces?

If buffers are too small:
- Packets get dropped during bursts
- TCP throughput suffers

If buffers are too large:
- Increased queuing delay
- Memory is expensive
- "Bufferbloat" — excessively high latency

### Classical Rule: Buffer = BDP

Traditional recommendation:

$$Buffer = Bandwidth \times RTT$$

**Reasoning:** TCP reduces its window by half on packet loss. To maintain high link utilization, the buffer should absorb the "slack" when TCP backs off.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TCP Sawtooth and Buffer Role                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   cwnd                                                                  │
│     ▲                                                                   │
│     │     /\        /\        /\                                       │
│     │    /  \      /  \      /  \                                      │
│     │   /    \    /    \    /    \     ← cwnd oscillates               │
│     │  /      \  /      \  /      \                                    │
│     │ /        \/        \/        \                                   │
│     └──────────────────────────────────► time                          │
│                                                                         │
│   Link utilization depends on cwnd + queue:                            │
│                                                                         │
│     cwnd_max = BDP + Buffer                                             │
│     cwnd_min = cwnd_max / 2 = (BDP + Buffer) / 2                       │
│                                                                         │
│   For full utilization:  cwnd_min ≥ BDP                                │
│   Therefore:  (BDP + Buffer) / 2 ≥ BDP                                 │
│   Solving:    Buffer ≥ BDP                                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### The Math

When TCP is in congestion avoidance:
- **cwnd_max** = BDP + Buffer (queue is full, about to drop)
- **cwnd_min** = cwnd_max / 2 (after multiplicative decrease)

For 100% link utilization, we need cwnd_min ≥ BDP:

$$\frac{BDP + Buffer}{2} \geq BDP$$

$$Buffer \geq BDP$$

### Modern Revision: Smaller Buffers

With many TCP flows (N), the sawteeth are **desynchronized**:

```
┌─────────────────────────────────────────────────────────────────────────┐
│              Desynchronized TCP Flows (Statistical Multiplexing)         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Flow 1:  /\    /\    /\                                              │
│   Flow 2:    /\    /\    /\                                            │
│   Flow 3:  /\  /\  /\  /\                                              │
│   Flow 4:   /\ /\ /\ /\                                                │
│   ─────────────────────────────────────────────                        │
│   Aggregate: ≈≈≈≈≈≈≈≈≈≈≈≈≈≈≈≈  (relatively smooth)                     │
│                                                                         │
│   With N flows, aggregate variance is reduced by √N                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Stanford rule (2004):**

$$Buffer = \frac{BDP}{\sqrt{N}}$$

where N is the number of flows.

| Scenario | Classical Buffer | Stanford Buffer (100 flows) |
|----------|------------------|----------------------------|
| 10 Gbps × 100 ms | 125 MB | 12.5 MB |
| 40 Gbps × 100 ms | 500 MB | 50 MB |

**Result:** Modern high-speed routers can use significantly smaller buffers.

## TCP Throughput Analysis

### Modeling TCP Behavior

**Question:** What is the average throughput of a TCP connection with packet loss rate $p$?

### Assumptions
- TCP in congestion avoidance (AIMD phase)
- Loss detected via triple duplicate ACKs (fast retransmit)
- Window oscillates in sawtooth pattern

### Analysis Setup

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TCP Sawtooth Analysis                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Window (packets)                                                      │
│        ▲                                                                │
│        │                                                                │
│   W    │            ╱│                                                 │
│        │           ╱ │                                                 │
│        │          ╱  │                                                 │
│        │         ╱   │                                                 │
│   W/2  │────────╱    │                                                 │
│        │       ╱     │                                                 │
│        │      ╱      │                                                 │
│        │     ╱       │                                                 │
│        └─────────────┴──────────────► Time (RTTs)                      │
│             W/2 RTTs                                                    │
│                                                                         │
│   During one cycle:                                                     │
│   • Window grows from W/2 to W                                          │
│   • Takes W/2 RTTs (increase by 1 per RTT)                             │
│   • Then loss occurs, window drops to W/2                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Packets Per Cycle

During one sawtooth cycle:
- Window increases from W/2 to W over W/2 RTTs
- Packets sent = sum of window sizes each RTT

$$Packets = \frac{W}{2} + \left(\frac{W}{2}+1\right) + \left(\frac{W}{2}+2\right) + \cdots + W$$

$$Packets = \sum_{i=0}^{W/2} \left(\frac{W}{2} + i\right) = \frac{3W^2}{8}$$

### Relating to Loss Rate

If one packet is lost per cycle, and we send $\frac{3W^2}{8}$ packets per cycle:

$$p = \frac{1}{3W^2/8} = \frac{8}{3W^2}$$

Solving for W:

$$W = \sqrt{\frac{8}{3p}}$$

### Throughput Formula

Average window size is $\frac{3W}{4}$ (average of W/2 and W):

$$Throughput = \frac{Average\_Window \times MSS}{RTT} = \frac{3W}{4} \times \frac{MSS}{RTT}$$

Substituting W:

$$\boxed{Throughput = \sqrt{\frac{3}{2}} \times \frac{MSS}{RTT \times \sqrt{p}}}$$

Or approximately:

$$Throughput \approx \frac{1.22 \times MSS}{RTT \times \sqrt{p}}$$

### Key Insights

| Observation | Implication |
|-------------|-------------|
| Throughput ∝ $\frac{1}{RTT}$ | High RTT connections get less throughput |
| Throughput ∝ $\frac{1}{\sqrt{p}}$ | Throughput degrades slowly with loss |
| Throughput ∝ $MSS$ | Larger segments → higher throughput |

**RTT Unfairness:** This formula shows TCP is **inherently unfair** to long-distance connections.

### Required Loss Rates for High-Speed Networks

**Problem:** To achieve high throughput, TCP requires extremely low loss rates.

| Target Throughput | RTT | Required Loss Rate |
|-------------------|-----|-------------------|
| 1 Gbps | 100 ms | 2 × 10⁻¹⁰ |
| 10 Gbps | 100 ms | 2 × 10⁻¹² |

This is **nearly impossible** to achieve in practice!

**Conclusion:** Standard TCP AIMD is not suitable for very high-speed networks. This motivates:
- **High-speed TCP variants** (CUBIC, BBR, etc.)
- Faster window increase algorithms

## AIMD Fairness Analysis

### The Question

When multiple TCP connections share a bottleneck link, does AIMD lead to fair sharing?

**Answer:** Yes! AIMD converges to fairness.

### Setup

- Two flows sharing a link of capacity R
- Flow 1 has rate x₁, Flow 2 has rate x₂
- Goal: Both flows should get R/2

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    AIMD Convergence to Fairness                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   x₂ (Flow 2 rate)                                                      │
│       ▲                                                                 │
│       │    Fairness line                                                │
│       │    (x₁ = x₂)                                                    │
│   R   │      ╱                                                          │
│       │     ╱                                                           │
│       │    ╱                                                            │
│       │   ╱  ↗ ↗ ↗                                                     │
│       │  ╱  ╱    ╲                                                      │
│  R/2  │─╱─★───────                 ← Fair share point (R/2, R/2)       │
│       │╱  ↖     ╱                                                       │
│       │    ↖  ╱                                                         │
│       │     ╱                                                           │
│       │   ╱   Efficiency line                                           │
│       │ ╱     (x₁ + x₂ = R)                                             │
│       └────────────────────────────► x₁ (Flow 1 rate)                  │
│           R/2           R                                               │
│                                                                         │
│   Arrows show trajectory:                                               │
│   • Additive Increase: move diagonally ↗ (45°)                         │
│   • Multiplicative Decrease: move toward origin (halve both)           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### AIMD Dynamics

**Additive Increase (AI):**
- Both flows increase by same amount α
- Movement direction: $(+α, +α)$ → **45° diagonal**
- Moves toward efficiency line (x₁ + x₂ = R)

**Multiplicative Decrease (MD):**
- Both flows multiply by same factor β (typically 0.5)
- Movement direction: toward origin
- **Preserves fairness ratio**: if x₁/x₂ = k, after MD: (βx₁)/(βx₂) = k

### Why AIMD Converges to Fairness

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    AIMD Convergence Trajectory                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Starting Point: A (unfair, x₁ > x₂)                                  │
│                                                                         │
│   x₂ ▲                                                                  │
│      │    Fairness                                                      │
│      │    ╱                                                             │
│   R  │   ╱                                                              │
│      │  ╱                                                               │
│      │ ╱   ┌──B         1. AI: A → B (move 45° up-right)               │
│      │╱   ╱│                                                            │
│      │   ╱ │            2. MD: B → C (halve toward origin)              │
│      │  C──┘                                                            │
│      │ ╱↗   ┌──D        3. AI: C → D                                   │
│      │╱    ╱│                                                           │
│      │    E─┘           4. MD: D → E                                    │
│      │   ╱                                                              │
│      │──A                ... converges to fairness line!               │
│      │                                                                  │
│      └──────────────────────────────────► x₁                           │
│                                                                         │
│   Each MD-AI cycle moves closer to fairness line                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Key insight:** 
- AI moves at 45°, which **approaches the fairness line** when starting below it
- MD moves toward origin, which **preserves the ratio** but brings point **closer to fairness line** in absolute terms

### Mathematical Proof Sketch

Let unfairness = |x₁ - x₂|

After AI: unfairness unchanged (both increase by α)

After MD: unfairness = |βx₁ - βx₂| = β|x₁ - x₂|

Since β < 1, unfairness **decreases by factor β** each cycle!

$$Unfairness_{after} = \beta \times Unfairness_{before}$$

**Convergence is exponential.**

### What About AIAD and MIMD?

| Algorithm | Convergence to Fairness? | Why? |
|-----------|-------------------------|------|
| **AIMD** | ✓ Yes | MD reduces unfairness |
| **AIAD** | ✗ No | AD preserves absolute difference |
| **MIMD** | ✗ No | MI and MD both preserve ratio |
| **MIAD** | ✗ No | Oscillates, may diverge |

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Why Only AIMD Works                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   AIAD: Additive Increase, Additive Decrease                           │
│   • AI: move 45° ↗                                                     │
│   • AD: move 45° ↙                                                     │
│   • Just oscillates parallel to efficiency line!                       │
│                                                                         │
│   MIMD: Multiplicative Increase, Multiplicative Decrease               │
│   • MI: scale up (move away from origin)                               │
│   • MD: scale down (move toward origin)                                │
│   • Ratio x₁/x₂ NEVER changes!                                         │
│                                                                         │
│   AIMD: The only combination that:                                      │
│   1. Reaches efficiency (AI drives toward full utilization)            │
│   2. Converges to fairness (MD reduces absolute differences)           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## Congestion Control Summary

### TCP Congestion Control Properties

| Property | Mechanism | Effect |
|----------|-----------|--------|
| **Efficiency** | Additive Increase | Grow to fill available capacity |
| **Safety** | Multiplicative Decrease | Back off quickly on congestion |
| **Fairness** | AIMD combination | Converges to equal shares |
| **Stability** | Conservative growth | Prevents oscillations |

### Key Formulas

| Formula | Description |
|---------|-------------|
| $BDP = Bandwidth \times RTT$ | Data in flight for full utilization |
| $Buffer = BDP / \sqrt{N}$ | Router buffer sizing (N flows) |
| $Throughput = \frac{1.22 \cdot MSS}{RTT \cdot \sqrt{p}}$ | TCP throughput with loss rate p |
| $Unfairness_{new} = \beta \cdot Unfairness_{old}$ | AIMD fairness convergence |

### Limitations of Standard TCP

1. **RTT unfairness** — Long RTT connections get less bandwidth
2. **High-speed inadequacy** — Requires impossibly low loss rates
3. **Slow convergence** — Takes many RTTs to discover capacity
4. **Bufferbloat** — Large buffers cause high latency

**Modern solutions:** CUBIC, BBR, DCTCP, etc. (different increase/decrease functions)
