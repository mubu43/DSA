## Introduction to Network Performance

Two main attributes measure the performance of a network:

| Metric | Description | Analogy |
|--------|-------------|---------|
| **Throughput** | How many bits per second are going through the network | Width of a pipe |
| **Delay** | How long does it take a bit from one end to the other | Length of a pipe |

> **Important:** These are two orthogonal concepts — think of it as the width of a pipe (throughput) and the length of a pipe (delay) through which data flows.

```
┌─────────────────────────────────────────────────────────────────┐
│                    The Pipe Analogy                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Throughput (Width)                                            │
│   ◄──────────────────►                                          │
│   ┌═══════════════════════════════════════════════════════════┐ │
│   ║                                                           ║ │
│   ║    ────────────────────────────────────────────────►      ║ │
│   ║                     Data Flow                             ║ │
│   ║                                                           ║ │
│   └═══════════════════════════════════════════════════════════┘ │
│   ◄─────────────────────────────────────────────────────────────►
│                        Delay (Length)                           │
│                                                                 │
│   • Wider pipe = Higher throughput                              │
│   • Shorter pipe = Lower delay                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## Throughput

### Throughput vs. Bandwidth

Throughput is related to other quantities like **bandwidth** and **datarate** of a link. However, they are not the same:

- A link can have a certain **"nominal" bandwidth** or datarate to send data at
- However, all of it may not be used all the time to send useful bits
- You may also have packet losses and retransmissions
- **Throughput measures the number of useful bits delivered at the receiver**, and is different from but related to the individual link data rates

### The Bottleneck Link

The throughput of a transfer is limited by the link with the **slowest throughput** along the path — this is called the **bottleneck link**. You cannot pump data faster than the rate of the slowest link.

> **Caveat:** The bottleneck link need not always be the link with the slowest nominal datarate. Sometimes a high-speed link may be shared by several flows, causing each flow to receive a small share, thus becoming the bottleneck.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Bottleneck Link Example                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Sender ═══════════════► Router ═══════► Router ═══════► Receiver │
│            10 Mbps           │      1 Mbps       10 Mbps            │
│                              │                                      │
│                              ▼                                      │
│                     ┌─────────────────┐                             │
│                     │  BOTTLENECK!    │                             │
│                     │  Max throughput │                             │
│                     │  limited to     │                             │
│                     │  1 Mbps         │                             │
│                     └─────────────────┘                             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Instantaneous vs. Average Throughput

Sometimes, you may not always be able to send at the bottleneck rate, because your protocol may have other delays, like waiting for ACKs. So:
- **Instantaneous throughput** can be the bottleneck link rate
- **Average throughput** may be lower

**The way to compute average throughput:**

$$\text{Average Throughput} = \frac{\text{Total Data Sent (F)}}{\text{Total Time Taken (T)}}$$

## Delay Components

The delay of an end-to-end path is the sum of delays on all links and intermediate nodes. There are **four components** of delay:

### 1. Transmission Delay

When a packet leaves a node, it first experiences **transmission delay**. That is, all the bits of a packet have to be put out on the link.

$$d_{trans} = \frac{B}{R}$$

Where:
- $B$ = Packet size in bits
- $R$ = Link transmission rate in bits/second

### 2. Propagation Delay

Next is **propagation delay**. The bits have to propagate at the speed of waves in the transmission medium to reach the other end. This delay depends on the length of the wire, and is usually only significant for long-distance links.

$$d_{prop} = \frac{d}{s}$$

Where:
- $d$ = Distance the wave has to travel
- $s$ = Speed of the wave in the medium

**Reference speeds:**

| Medium | Speed | Example Calculation |
|--------|-------|---------------------|
| Free space (radio) | $3 \times 10^8$ m/s | 1 μs for 300 meters |
| Copper wire | $2 \times 10^8$ m/s | 10 ns to travel a 2-meter wire |

> **Insight:** If propagation delay < transmission delay, the first bit of the packet would have reached the other endpoint before the sender finishes putting all bits on the wire. So the limiting factor is really how fast the link is. On the other hand, if propagation delay > transmission delay, as is the case for long-distance links, then the first bit reaches the other endpoint much after the last bit has been sent.

### 3. Processing Delay

Once a packet arrives at the other endpoint, it must be **processed** by the switch or router. This processing delay could involve:
- Looking up routing tables
- Computing header checksums
- Other computations

This is usually not a significant component with today's high-speed hardware.

### 4. Queueing Delay

Once the other endpoint processes the packet and decides which link to send it on, the packet may potentially be **queued** until the next link becomes free. This is called **queueing delay**.

> This is the **most unpredictable** part of the delay, as it depends on traffic sent by other nodes.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    The Four Components of Delay                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌─────────┐                                       ┌─────────┐    │
│   │ Sender  │                                       │Receiver │    │
│   └────┬────┘                                       └────▲────┘    │
│        │                                                 │         │
│        │ (1) Transmission Delay: d_trans = B/R           │         │
│        ▼                                                 │         │
│   ══════════════════════════════════════════════════════          │
│        │                                                 ▲         │
│        │ (2) Propagation Delay: d_prop = distance/speed  │         │
│        ▼                                                 │         │
│   ┌──────────┐                                          │         │
│   │  Router  │ (3) Processing Delay (table lookup, etc.)│         │
│   └────┬─────┘                                          │         │
│        │                                                 │         │
│        │ (4) Queueing Delay (waiting for busy link)      │         │
│        ▼                                                 │         │
│   [Queue: ▓▓▓▓░░░░]                                      │         │
│        │                                                 │         │
│        └─────────────────────────────────────────────────┘         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Understanding Queueing Delay

A large branch of study (**"Queueing Theory"**) is devoted to modeling and understanding this delay under various conditions.

Internet traffic is often **bursty**, and hence queueing delays occur even if the aggregate traffic is less than the capacity of the links on average.

**Key Insight:** Suppose incoming packets arrive at an aggregate rate of $L$ bits/s and link rate is $R$ bits/s. Then, as long as $L < R$, it appears that there should be no queueing. However, packets don't arrive in an equally spaced fashion, and the arrival pattern is often random. In such cases:

$$\text{Queueing Delay} \approx \frac{1}{R - L}$$

The queueing delay increases quite steeply as $L/R$ approaches 1:

```
Queueing
Delay
    │
    │                                    ╱
    │                                  ╱
    │                                ╱
    │                              ╱
    │                           ╱
    │                        ╱
    │                    ╱
    │              ╱─────
    │      ╱──────
    └─────────────────────────────────────► L/R
    0                                    1.0
    
    ⚠ Delay increases steeply as L/R → 1
```

> **Best Practice:** Network designers try to keep the $L/R$ ratio well below 1.

### Store-and-Forward Behavior

Most switches today are **store-and-forward**. That is, they wait for the entire packet to arrive, then start forwarding. Once the packet gets out of the queue and gets ready for transmission, the cycle begins again with the transmission delay on the next link.

### Packet Loss

Once a queue is full, it may **drop packets**, leading to losses. Losses can also occur due to:
- **Transmission errors** on the wire (more common in wireless links; wired links are pretty reliable)

## Worked Examples

### Example 1: Average Throughput vs. Bottleneck Bandwidth

**Problem:** Consider a 125 KB file that needs to be sent through a network path. The bottleneck bandwidth of the path is 1 Mbps. The one-way delay between sender and receiver is 20 ms.

**Case 1: Continuous Sending (No ACK waiting)**

Suppose the sender continuously sends data at the bottleneck rate, and no packets are lost, no retransmissions. How long does it take to send the file?

$$\text{Time} = \frac{125 \times 8 \times 1000 \text{ bits}}{1000 \times 1000 \text{ bps}} = 1 \text{ second}$$

**Average throughput = 1 Mbps** (equals the bottleneck bandwidth)

**Case 2: Stop-and-Wait (ACK after each packet)**

Suppose the sender needs to wait for an ACK after sending every 1 KB packet. Assume ACK also takes 20 ms to come back.

Now, the sender can send 1 KB in:
$$\text{Time per packet} = 20\text{ ms (send)} + 20\text{ ms (ACK)} = 40\text{ ms}$$

So the average throughput is:
$$\frac{1 \times 8 \times 1000 \text{ bits}}{40 \text{ ms}} = 200 \text{ kbps}$$

The average throughput is **one-fifth** of what it was before, with the new ACK requirement. The time to send the file:

$$\text{Total time} = 125 \times 40\text{ ms} = 5 \text{ seconds}$$

| Scenario | Average Throughput | Time to Send 125 KB |
|----------|-------------------|---------------------|
| Continuous sending | 1 Mbps | 1 second |
| Stop-and-wait (1 KB packets) | 200 kbps | 5 seconds |

---

### Example 2: End-to-End Delay Calculation

**Problem:** Consider a link A—S—B. A and B are end hosts and S is a switch/router in between. Each link has length 200 m (speed of light in medium is $2 \times 10^8$ m/s). Each link has bandwidth of 1 Mbps. A has sent a 125-byte packet. Each node takes 9 μs to process each received bit. Let's compute various end-to-end delays.

```
┌───────────────────────────────────────────────────────────┐
│    A ════════════════ S ════════════════ B                │
│        200m, 1 Mbps      200m, 1 Mbps                     │
└───────────────────────────────────────────────────────────┘
```

**Step 1: Calculate Propagation Delay per Link**

$$d_{prop} = \frac{200\text{ m}}{2 \times 10^8 \text{ m/s}} = 1 \text{ μs}$$

**Step 2: Calculate Transmission Delay**

Packet size: 125 bytes = 1000 bits

$$d_{trans} = \frac{1000 \text{ bits}}{1 \times 10^6 \text{ bps}} = 1000 \text{ μs} = 1 \text{ ms}$$

**Step 3: Total Delay A → S**

- Transmission delay: 1000 μs
- Propagation delay: 1 μs  
- Processing delay: 9 μs

Total A → S: **1010 μs**

**Step 4: Total End-to-End Delay**

$$d_{total} = 2 \times 1010 = 2020 \text{ μs}$$

---

### Example 3: Benefits of Packetization in Store-and-Forward Networks

**Problem:** Consider the above A—S—B problem. Suppose A wants to send a 1 MB file to B. Compare two approaches:
1. Send the entire file as one big packet
2. Break up into 100-byte chunks, with a 25-byte header per chunk

For simplicity, let's ignore propagation and processing delays, as they are small.

**Option 1: Single Large Packet**

```
Time: ─────[A sends to S]─────[S sends to B]─────
            8 seconds          8 seconds
                                              Total: 16 sec
```

- Transmission time on A-S: $\frac{1\text{ MB} \times 8}{1\text{ Mbps}} = 8$ seconds
- Transmission time on S-B: 8 seconds
- **Total: 16 seconds**

**Option 2: Packetized (10,000 chunks)**

```
Time: ─[Pkt1]─[Pkt2]─[Pkt3]──────────────[Pkt10000]─[Pkt10000→B]─
       │      │                                      │
       └──────┴── S forwards while A sends next ─────┘
```

Each packet: 100 + 25 = 125 bytes

Transmission time per packet: $\frac{125 \times 8}{1 \times 10^6} = 1$ ms

**Key Insight:** While S forwards a packet to B, A can send the next packet to S (pipelining)!

- Time for A to send all packets to S: $10,000 \times 1\text{ ms} = 10$ seconds
- Time for last packet to travel from S to B: 1 ms
- **Total: 10.001 seconds**

| Approach | Total Time | Observation |
|----------|------------|-------------|
| Single 1 MB packet | 16 seconds | Sequential transmission |
| Packetized (125-byte chunks) | 10.001 seconds | Pipelining enables parallelism |

> **Conclusion:** Packetization significantly improves performance despite the overhead of additional headers, because it enables pipelining in store-and-forward networks.

## Bandwidth-Delay Product (BDP)

### Understanding BDP

If bandwidth is the "width of a bit" on the link, and delay is the "length of the bit", then **BDP is the volume of the pipe** in terms of how many bits it can hold.

$$\text{BDP} = \text{Bandwidth} \times \text{Delay}$$

**BDP signifies how many bits the sender can send before the first bit reaches the receiver.**

```
┌─────────────────────────────────────────────────────────────────────┐
│                   Bandwidth-Delay Product (BDP)                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Sender                                              Receiver      │
│   ┌────┐                                              ┌────┐       │
│   │    │──────────────────────────────────────────────│    │       │
│   │    │  ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │    │       │
│   │    │──────────────────────────────────────────────│    │       │
│   └────┘                                              └────┘       │
│                                                                     │
│         ◄──────────── Bits "in flight" = BDP ───────────►          │
│                                                                     │
│   BDP = Bandwidth × Propagation Delay                               │
│       = "Volume" of the network pipe                                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### BDP with Round-Trip Time (RTT)

Suppose an extra signal/packet has to be sent by the receiver indicating that it has started to receive the bits. Let us consider this sum of forward delay and reverse delay together as the **round-trip-time (RTT)**. Then the product of bandwidth and RTT is the number of bits **"in-flight"** before the sender can expect to hear back from the receiver.

> **Note:** BDP can refer to the product of bandwidth and one-way delay or RTT, depending on context.

---

### Example 4: BDP Calculation

**Problem:** A sender and receiver are communicating over a 1 Mbps link. Sender sends 1 KB packets. Receiver sends 250-byte ACKs. Round-trip propagation delay is 10 ms (assume long-distance link).

**Step 1: Calculate Individual Delays**

| Component | Calculation | Result |
|-----------|-------------|--------|
| Data packet transmission | $\frac{1 \times 8 \times 1000}{1 \times 10^6}$ | 8 ms |
| ACK transmission | $\frac{250 \times 8}{1 \times 10^6}$ | 2 ms |
| Round-trip propagation | Given | 10 ms |
| **Total RTT** | $8 + 2 + 10$ | **20 ms** |

**Step 2: If Sender Uses Stop-and-Wait**

If the sender transmits only one packet and waits for ACK:

$$\text{Average Throughput} = \frac{1 \text{ KB}}{20 \text{ ms}} = \frac{8000 \text{ bits}}{0.02 \text{ s}} = 400 \text{ kbps}$$

This is only **40%** of the link capacity!

**Step 3: Calculate BDP**

$$\text{BDP} = 1 \text{ Mbps} \times 20 \text{ ms} = 20,000 \text{ bits} = 2500 \text{ bytes}$$

In terms of packets:
$$\text{BDP in packets} = \frac{2500 \text{ bytes}}{1024 \text{ bytes/packet}} \approx 2.5 \text{ packets}$$

**Interpretation:** If the sender were to be continuously sending without waiting for an ACK, he would have sent 2.5 packets before receiving the ACK for the first packet from the receiver.

```
┌─────────────────────────────────────────────────────────────────────┐
│                   BDP Visualization: 2.5 Packets                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Time ──────────────────────────────────────────────────────────►   │
│                                                                     │
│  Sender:  [Pkt 1][Pkt 2][Pkt 3]────────────────────────────         │
│           ▼                                                         │
│  Link:    ═════[Pkt1]══════[Pkt2]══════[Pkt2.5]══════►              │
│                                            │                        │
│  Receiver:                          Receives Pkt 1                  │
│                                            │                        │
│           ◄────────────[ACK for Pkt 1]─────┘                        │
│                                                                     │
│  When ACK for Pkt 1 arrives, 2.5 packets are "in flight"           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Why BDP Matters

The concept of BDP is essential to understanding:

1. **How much data to keep in flight** to fully utilize a link
2. **How much data is in flight** before you hear about packet losses etc. from the receiver

> **Key Takeaway:** TCP tries to keep BDP worth of data in flight to fully utilize the bottleneck link. We will revisit this concept of BDP when studying TCP.

## Summary

| Concept | Formula/Description |
|---------|---------------------|
| **Throughput** | Useful bits delivered per second; limited by bottleneck link |
| **Transmission Delay** | $d_{trans} = B/R$ |
| **Propagation Delay** | $d_{prop} = d/s$ |
| **Queueing Delay** | Unpredictable; increases steeply as utilization → 1 |
| **BDP** | $\text{Bandwidth} \times \text{Delay}$ = bits "in flight" |
| **Average Throughput** | $F/T$ = File size / Total time |

Understanding these concepts is fundamental to designing efficient network protocols and troubleshooting performance issues.
