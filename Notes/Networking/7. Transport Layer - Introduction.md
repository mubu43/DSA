## Role of the Transport Layer

We have seen that the application layer operates as processes that communicate between hosts. The transport layer provides **process-to-process delivery** of messages.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     Transport Layer Role                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Host A                                              Host B            │
│   ┌─────────────────┐                    ┌─────────────────┐           │
│   │  Process P1     │                    │  Process P3     │           │
│   │   (Port 80)     │                    │   (Port 80)     │           │
│   └────────┬────────┘                    └────────▲────────┘           │
│            │                                      │                     │
│   ┌────────┴────────┐                    ┌────────┴────────┐           │
│   │  Process P2     │                    │  Process P4     │           │
│   │   (Port 443)    │                    │   (Port 443)    │           │
│   └────────┬────────┘                    └────────▲────────┘           │
│            │                                      │                     │
│   ═════════╪══════════════════════════════════════╪═════════           │
│   │      TRANSPORT LAYER                          │        │           │
│   │  (Process-to-Process Delivery)                │        │           │
│   ═════════╪══════════════════════════════════════╪═════════           │
│            │                                      │                     │
│   ═════════╪══════════════════════════════════════╪═════════           │
│   │       NETWORK LAYER                           │        │           │
│   │   (Host-to-Host Delivery)                     │        │           │
│   ═════════════════════════════════════════════════════════            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Key Insight:** The underlying network layer provides host-to-host delivery of messages, **without any reliability guarantees**. So, the job of the transport layer is to take this host-to-host delivery service from the network layer, and provide process-to-process delivery abstraction to the application layer.

### Socket-Based View

Processes send messages via **sockets**. So, we can also think of the transport layer as providing a data delivery service from **socket to socket**.

### Terminology

| Layer | Unit Name |
|-------|-----------|
| Application layer | **Message** |
| Transport layer | **Segment** |
| IP/Network layer | **Datagram** |

## Main Functions of the Transport Layer

### 1. Multiplexing and Demultiplexing (Mux/Demux)

Several processes on a host may be sending messages. Each application process is assigned a **port number**.

**Sending (Multiplexing):**
- Transport layer takes the application layer message
- Appends port number
- Passes to network layer

**Receiving (Demultiplexing):**
- At the receiver end, hands over message to correct application process based on port number

> **Note:** Both TCP and UDP provide this basic mux/demux functionality. In fact, UDP is a barebones transport layer that provides **ONLY** this functionality.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Multiplexing / Demultiplexing                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │

│                                                                         │
│   ┌──────┐  ┌──────┐  ┌──────┐         ┌──────┐  ┌──────┐  ┌──────┐   │
│   │ P1   │  │ P2   │  │ P3   │         │ P1   │  │ P2   │  │ P3   │   │
│   │:80   │  │:443  │  │:8080 │         │:80   │  │:443  │  │:8080 │   │
│   └──┬───┘  └──┬───┘  └──┬───┘         └──▲───┘  └──▲───┘  └──▲───┘   │
```

### 2. Reliable Data Delivery

**TCP provides reliable data delivery.** That is, the application can be assured that the message will reach the other side (or it will know if lost). TCP provides reliability using several mechanisms, on top of an unreliable network layer.

### 3. Congestion Control

**TCP ensures that data from one application does not swamp all the links and routers on the path.**

> **Important:** Congestion control is not so much a service to the application as it is a service to the Internet.

---

## Limitations of the Transport Layer

What are functions that the transport layer **cannot** provide?

| Cannot Provide | Reason |
|----------------|--------|
| **Bandwidth guarantees** | Underlying network layer does not provide guarantees |
| **Delay guarantees** | Underlying network layer does not provide guarantees |

> **Note:** The IP layer does not provide security either, but TCP has special mechanisms (**SSL/TLS**) to provide security over unsecure transport. However, bandwidth/delay guarantees are harder to provide.

## TCP: Connection-Oriented Protocol

### Overview

TCP is a **connection-oriented** protocol. This means there are a few connection establishment messages before data can be sent from sender to receiver.

**Important distinction:** This connection state resides **only at end hosts**; unlike connections in circuit switching where state is established at all routers on the path.

| Term | Definition |
|------|------------|
| **TCP Client** | The side that initiates the connection |
| **TCP Server** | The side that responds |
| **Full Duplex** | Data flow can happen both ways |

### The TCP Three-Way Handshake

Recall from socket programming: both client and server first create sockets. Client sends a connect request to server IP and port. Then, the **"TCP handshake"** takes place:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      TCP Three-Way Handshake                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│      CLIENT                                           SERVER            │
│        │                                                │               │
│        │                                                │               │
│        │  1. SYN ─────────────────────────────────────► │               │
│        │     "I want to connect"                        │               │
│        │                                                │               │
│        │                                                │               │
│        │  2. SYN-ACK ◄───────────────────────────────── │               │
│        │     "OK, I acknowledge your request"           │               │
│        │                                                │               │
│        │                                                │               │
│        │  3. ACK (+ optional data) ───────────────────► │               │
│        │     "Great, connection established!"           │               │
│        │                                                │               │
│        │                                                │               │
│   ═════╪════════ CONNECTION ESTABLISHED ════════════════╪═════          │
│        │                                                │               │
│        │        ◄─────── DATA EXCHANGE ───────►         │               │
│        │                                                │               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Step-by-step:**

1. **TCP client sends a SYN packet** to the server to initiate connection
2. **Server responds with SYN-ACK**
3. **Client then sends SYN ACK ACK** (or simply ACK), along with any data possibly

At this point:
- The accept call at the server returns
- The server accepts the request
- A new client socket is created for this connection
- Connection is said to be **established**

Once the connection is established, both client and server may send data through the TCP connection via the sockets. This data exchange translates to read/write on sockets.

### TCP Demultiplexing: The 4-Tuple

When a packet arrives at a host, how does TCP know which client socket to deliver the message to?

**TCP uses a 4-tuple as the demux key:**

| Component | Description |
|-----------|-------------|
| Source IP | IP address of the sender |
| Source Port | Port number of the sender |
| Destination IP | IP address of the receiver |
| Destination Port | Port number of the receiver |

> **Why can't it just use destination IP and port?** Because a server can have several sockets open for different clients.

## UDP: Connectionless Protocol

### Overview

Note that there is **no handshake** in UDP. Sender and receiver applications:
1. Create sockets
2. Fill in the destination port and IP in the socket structures
3. Simply send and receive messages using the socket handle

The source and destination port numbers are embedded in the UDP header.

### UDP Server Model

A UDP-based server only has **one listening socket**, not one per client.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         UDP Server Model                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Client 1                                                              │
│   ┌───────┐                                                             │
│   │Port:  │──────┐                                                      │
│   │5001   │      │                                                      │
│   └───────┘      │                                                      │
│                  │                                                      │
│   Client 2       │         ┌─────────────────────┐                      │
│   ┌───────┐      ├────────►│    UDP Server       │                      │
│   │Port:  │──────┤         │                     │                      │
│   │5002   │      │         │   Single Socket     │                      │
│   └───────┘      │         │   (Port 53)         │                      │
│                  │         │                     │                      │
│   Client 3       │         │   Handles ALL       │                      │
│   ┌───────┐      │         │   clients via       │                      │
│   │Port:  │──────┘         │   same socket       │                      │
│   │5003   │                │                     │                      │
│   └───────┘                └─────────────────────┘                      │
│                                                                         │
│   Demux key: (Destination IP, Destination Port) - 2-tuple              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### UDP Demultiplexing: The 2-Tuple

When a packet reaches the destination IP address (via network layer), the destination port is looked up to identify the correct socket to deliver the message to.

**UDP uses a 2-tuple as the demux key:**
- Destination IP
- Destination Port

## TCP vs UDP: Demultiplexing

### Why is the demux key different?

| Protocol | Demux Key | Reason |
|----------|-----------|--------|
| **TCP** | 4-tuple (src IP, src port, dst IP, dst port) | Maintains a separate socket for every client-server connection |
| **UDP** | 2-tuple (dst IP, dst port) | Server processes all clients via the same socket |

### Why is TCP connection-oriented?

**Next question:** Why is TCP connection-oriented and why does it have to maintain a separate socket for every connection?

**Answer:** Because TCP implements reliability, it is easier with separate sockets. For example:
- When a message arrives at a socket, it is easy to simply see the source IP/port associated with that socket and send an ACK
- If you want to send a reply to a UDP message, you need to extract the source IP and port from the UDP header for every message

## UDP in Detail

There is not much else to UDP other than mux/demux. UDP is just **barebones transport**:

### UDP Features

| Feature | Description |
|---------|-------------|
| **Mux/demux** | Basic multiplexing and demultiplexing |
| **Light error detection** | Checksum over header (includes port numbers and checksum; IP addresses are from IP header) |
| **Lower overhead** | UDP: 8 bytes header, TCP: 20 bytes header |

### UDP Header Structure

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         UDP Header (8 bytes)                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   0               8               16              24              31    │
│   ┌───────────────┬───────────────┬───────────────┬───────────────┐    │
│   │         Source Port           │       Destination Port        │    │
│   │           (16 bits)           │          (16 bits)            │    │
│   ├───────────────────────────────┼───────────────────────────────┤    │
│   │            Length             │           Checksum            │    │
│   │           (16 bits)           │          (16 bits)            │    │
│   ├───────────────────────────────┴───────────────────────────────┤    │
│   │                                                               │    │
│   │                         Data (Payload)                        │    │
│   │                                                               │    │
│   └───────────────────────────────────────────────────────────────┘    │
│                                                                         │
│   Total Header Size: 8 bytes (vs TCP's 20 bytes)                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Which Applications Use UDP?

| Application | Reason |
|-------------|--------|
| **DNS** | Simple request-reply does not justify the overhead of TCP's connection setup |
| **Multimedia applications** | They have more control over what data is sent when. For example, if the voice sample is stale, no point in TCP retransmitting it |
| **Real-time streaming** | Low latency is more important than reliability |
| **Gaming** | Fast, lightweight communication needed |

---

## Summary

| Aspect | TCP | UDP |
|--------|-----|-----|
| **Connection** | Connection-oriented (3-way handshake) | Connectionless |
| **Reliability** | Reliable (ACKs, retransmissions) | Unreliable |
| **Congestion Control** | Yes | No |
| **Demux Key** | 4-tuple | 2-tuple |
| **Header Size** | 20 bytes | 8 bytes |
| **Sockets per client** | One per connection | One for all clients |
| **Use Case** | Web, email, file transfer | DNS, multimedia, gaming |
