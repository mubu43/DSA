## Domain Name System (DNS)

### What is DNS?

DNS (Domain Name System) maps **hostnames** (e.g., `www.cse.iitb.ac.in`) to **IP addresses**. 

### The Scalability Problem

How to design such a system? Initially, one file used to hold all mappings when the Internet was only a few hundred hosts. Now, such a centralized system won't scale. Instead, we use a **hierarchical setup** for DNS.

### DNS Resolution: A Step-by-Step Example

Let's look at a simplified resolution of the hostname `www.cse.iitb.ac.in`:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         DNS Hierarchical Resolution                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. Client                        2. Root Server                           │
│   ┌───────┐    "www.cse.iitb.ac.in?"   ┌───────────┐                       │
│   │       │ ──────────────────────────►│   ROOT    │                       │
│   │       │◄────────────────────────── │  SERVER   │                       │
│   │       │   "Ask the .in TLD server" └───────────┘                       │
│   │       │                                                                 │
│   │       │    3. "www.cse.iitb.ac.in?"                                    │
│   │       │ ──────────────────────────►┌───────────┐                       │
│   │       │◄────────────────────────── │ .in TLD   │                       │
│   │       │   "Ask the ac.in server"   │  SERVER   │                       │
│   │       │                            └───────────┘                       │
│   │       │    4. Continue down the hierarchy...                           │
│   │       │ ──────────────────────────►┌───────────┐                       │
│   │       │                            │ ac.in     │                       │
│   │       │ ──────────────────────────►┌───────────┐                       │
│   │       │                            │iitb.ac.in │                       │
│   │       │ ──────────────────────────►┌───────────┐                       │
│   │ Client│◄─ Final IP Address ─────── │cse.iitb   │                       │
│   └───────┘                            │ .ac.in    │                       │
│                                        └───────────┘                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Step-by-step process:**

1. **All DNS requests go to one of the 13 root servers.** The root server then redirects to one of the TLD (top-level domains). Here, the server handles the "in" domain. That is, the root server says: *"I can't provide you the IP address of `www.cse.iitb.ac.in`, but here is the IP address of the server that knows about hosts ending with `.in`"*

2. **Next, you contact the TLD server for "in" domain**, which gives you the IP address of the server for `ac.in`.

3. **You walk down the hierarchy** to the `iitb.ac.in` name server, to the `cse.iitb.ac.in` server, which gives you the IP address of the web server (www host) in its domain.

### Authoritative Name Servers

The name server that is responsible for a certain domain (e.g., `ac.in`, `iitb.ac.in`, `cse.iitb.ac.in`) is called the **authoritative name server** for that domain.

| Property | Description |
|----------|-------------|
| **Redundancy** | There are usually more than one for redundancy |
| **Outsourcing** | You can also outsource your auth server to a third party |

### Local DNS Servers

Every group of hosts also has a **"local DNS server"** that does all this resolution of contacting multiple hosts for you on your behalf.

- Each department typically has a local DNS server (which is configured along with your default gateway)
- All DNS queries from individual machines are sent to this local server
- The local server does the job of contacting various authoritative DNS servers

### DNS Caching

DNS responses can be **cached**. When you get a name→IP mapping, it comes with a **TTL (time to live)**. You can reuse that mapping within that time without traversing the entire chain again.

```
┌─────────────────────────────────────────────────────────────────┐
│                         DNS Caching                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   First Query:                                                  │
│   Client ──► Local DNS ──► Root ──► TLD ──► Auth ──► Response  │
│                  │                                              │
│                  ▼                                              │
│              ┌────────────────┐                                 │
│              │ Cache Entry    │                                 │
│              │ www.example.com│                                 │
│              │ = 93.184.216.34│                                 │
│              │ TTL: 3600 sec  │                                 │
│              └────────────────┘                                 │
│                                                                 │
│   Subsequent Queries (within TTL):                              │
│   Client ──► Local DNS ──► Cache Hit! ──► Response             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Other DNS Uses

| Use Case | Description |
|----------|-------------|
| **Mail servers** | DNS resolves not just names of web servers but also names of mail servers. For example, if you send mail to someone @iitb.ac.in, your SMTP mail server contacts the domain iitb.ac.in asking for the IP address of that SMTP mail server |
| **Load balancing** | If you resolve a web server's name, you can get different IP addresses depending on which replica you are assigned to |
| **Multiple addresses** | DNS can also return multiple IP addresses in a response, in which case you can try contacting any of the hosts |

## DNS Record Types

DNS servers store different types of records:

| Record Type | Name | Description | Example |
|-------------|------|-------------|---------|
| **A** | Address | Maps name to IP address (most important) | `www.example.com → 93.184.216.34` |
| **NS** | Name Server | Maps a name to another name server | `{ac.in, iitb.ac.in, NS}` |
| **MX** | Mail Exchange | For mail servers | `example.com → mail.example.com` |
| **CNAME** | Canonical Name | Gives an alias to a hostname | `www.example.com → webserver.example.com` |

### How NS and A Records Work Together

When you contact the authoritative server for the `ac.in` domain, it gives you:
1. An **NS record** that points to the authoritative server for `iitb.ac.in`:
   - `{ac.in, iitb.ac.in, NS}`
2. An **A record** with the IP address of the auth server:
   - `{iitb.ac.in, XXX.XXX.XXX.XXX, A}`

With these two, you can contact the next authoritative server in the hierarchy.

## Designing Large-Scale Servers

### The Basic Problem

The simple server socket program we saw could only handle one client at a time. It could not multiplex several clients. For example:
- If it decides to just "accept" new connections all the time, it will not have time to "read" from other sockets
- Similarly, if it is reading from one socket, the other sockets could lay idle

So, at the very least, servers need a mechanism for **multiplexing several client connections** in an efficient manner. Several techniques exist for this (e.g., the server could create separate threads or processes for each client, etc.).

### Real-World Server Complexity

In general, designing servers to handle a large number of clients is a challenging problem. Handling several sockets simultaneously is only one part of the puzzle.

Typical web servers today do extensive processing on each request:
- Read/write files or database tables
- Perform computation

**Example: Online Travel Portal**

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Web Server Request Processing                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   User Request                                                          │
│       │                                                                 │
│       ▼                                                                 │
│   ┌──────────────────────────────────────────────────────────────┐     │
│   │                      WEB SERVER                               │     │
│   │  ┌─────────┐   ┌──────────────┐   ┌─────────────────────┐   │     │
│   │  │ Receive │──►│ Query Backend│──►│ Compute Cheapest    │   │     │
│   │  │ Request │   │   Database   │   │  Travel Options     │   │     │
│   │  └─────────┘   └──────────────┘   └──────────┬──────────┘   │     │
│   │                                              │               │     │
│   │                                              ▼               │     │
│   │                                   ┌─────────────────────┐   │     │
│   │                                   │ Return Response to  │   │     │
│   │                                   │       User          │   │     │
│   │                                   └─────────────────────┘   │     │
│   └──────────────────────────────────────────────────────────────┘     │
│                                                                         │
│   Each client request involves multiple steps!                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

A good web server needs to:
- Multiplex multiple requests in an efficient manner
- Serve as many clients as it can for a given hardware configuration

### Server Overload

However, no matter how much multiplexing you do, at some point, some system resources of the server are bound to run out. That is, after the number of clients exceed a certain capacity, a single server cannot handle the load anymore because:
- The CPU is too busy
- Disk is the bottleneck
- No more free sockets are available

This is called **server overload**. When the server is overloaded, its performance suffers:
- Requests fail
- Response times are high
- This is called a **"server crash"**

### Scaling Web Servers: Load Balancing

The most common idea is to have several **"replicas"** of the server in a **server farm**, and have a **"load balancer"** to distribute load between the replicas.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         Load Balancer Architecture                       │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                              Internet                                    │
│                                 │                                       │
│                                 ▼                                       │
│                        ┌───────────────┐                                │
│                        │ LOAD BALANCER │                                │
│                        └───────┬───────┘                                │
│                                │                                        │
│              ┌─────────────────┼─────────────────┐                      │
│              │                 │                 │                      │
│              ▼                 ▼                 ▼                      │
│       ┌──────────┐      ┌──────────┐      ┌──────────┐                 │
│       │ Server 1 │      │ Server 2 │      │ Server 3 │                 │
│       │ (Replica)│      │ (Replica)│      │ (Replica)│                 │
│       └──────────┘      └──────────┘      └──────────┘                 │
│                                                                         │
│                         Server Farm                                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### Load Balancing Approaches

| Method | Description |
|--------|-------------|
| **DNS-level redirection** | A DNS request can return several IP addresses, and the client can try to contact the servers in a round-robin fashion |
| **Transparent load balancing** | When you contact a web server on a particular IP address, the load balancer located at the entry of the server farm rewrites the IP header to point to one of several server replica IP addresses. This way, even though the client believes it is talking to one IP address, it is in fact talking to several machines that are juggled by the load balancer |

> **Stickiness:** Load balancers also need to ensure the same user goes to the same server replica in some cases ("stickiness").

## Content Distribution Networks (CDNs)

CDNs are **third-party applications** that outsource content distribution from content providers.

### How CDNs Work

A CDN manages several **geographically distributed replica servers** that hold content from several websites/content providers. Each user is directed to the **closest replica via DNS**.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         CDN Architecture                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Content Provider                                                      │
│   ┌────────────┐                                                        │
│   │ Origin     │                                                        │
│   │ Server     │                                                        │
│   └─────┬──────┘                                                        │
│         │ Distribute content                                            │
│         ▼                                                               │
│   ┌─────────────────────────────────────────────────────────────────┐  │
│   │                      CDN Network                                 │  │
│   │                                                                  │  │
│   │  ┌────────┐        ┌────────┐        ┌────────┐                 │  │
│   │  │ Edge   │        │ Edge   │        │ Edge   │                 │  │
│   │  │ Server │        │ Server │        │ Server │                 │  │
│   │  │ (USA)  │        │(Europe)│        │ (Asia) │                 │  │
│   │  └────┬───┘        └────┬───┘        └────┬───┘                 │  │
│   └───────┼─────────────────┼─────────────────┼─────────────────────┘  │
│           │                 │                 │                         │
│           ▼                 ▼                 ▼                         │
│        Users in          Users in          Users in                     │
│        Americas          Europe            Asia Pacific                 │
│                                                                         │
│   DNS directs each user to the closest edge server!                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Benefits of CDNs

| Benefit | Description |
|---------|-------------|
| **Reduced latency** | Users connect to nearby servers |
| **Reduced origin load** | Edge servers handle most traffic |
| **Improved reliability** | Multiple replicas provide redundancy |
| **Scalability** | Can handle traffic spikes by distributing load |
