## Circuit Switching vs Packet Switching

The Internet today is what is called a **packet switched network**:
- Information is broken into small packets
- Each packet has a destination address
- Each router/packet switch along the path looks up the destination address and sends the packet in the right direction

**Is this the only way to build networks?** No. There is also **circuit switching**.

These are two fundamental ways of transporting data through a network.

```
┌─────────────────────────────────────────────────────────────────────────┐
│               Circuit Switching vs Packet Switching                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   CIRCUIT SWITCHING                    PACKET SWITCHING                 │
│                                                                         │
│   ┌───────────────────────┐           ┌───────────────────────┐        │
│   │  Setup Phase          │           │  No Setup Phase       │        │
│   │  (reserve resources)  │           │  (just send packets)  │        │
│   └───────────┬───────────┘           └───────────────────────┘        │
│               │                                                         │
│               ▼                                                         │
│   ┌───────────────────────┐           ┌───────────────────────┐        │
│   │  Dedicated Circuit    │           │  Store-and-Forward    │        │
│   │  ════════════════════ │           │  [Buffer]→[Buffer]→   │        │
│   │  (guaranteed path)    │           │  (best effort)        │        │
│   └───────────────────────┘           └───────────────────────┘        │
│                                                                         │
│   TDM/FDM Multiplexing                Statistical Multiplexing          │
│   Low delay, low jitter               Variable delay, possible loss     │
│   May waste resources                 Better utilization                │
│                                                                         │
│   Example: Telephone                  Example: Internet                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## Circuit Switching (CS)

In circuit switching, before starting a flow:

1. **Setup phase happens** - A setup message goes through the network
2. **Resources are reserved** at all links for the flow
3. **Dedicated circuit established** from one endpoint to the other, through which you can push data

### Multiplexing in Circuit Switching

The links along the path are shared by **time/frequency division multiplexing** (TDM/FDM) between various circuits:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    TDM and FDM Multiplexing                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   TIME DIVISION MULTIPLEXING (TDM)                                      │
│                                                                         │
│   Time ───────────────────────────────────────────────────────────────► │
│   ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐       │
│   │ U1  │ U2  │ U3  │ U4  │ U1  │ U2  │ U3  │ U4  │ U1  │ ... │       │
│   └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘       │
│     Each user gets a dedicated time slot                               │
│                                                                         │
│   FREQUENCY DIVISION MULTIPLEXING (FDM)                                 │
│                                                                         │
│   Frequency                                                             │
│       ▲                                                                 │
│       │  ┌──────────────────────────────────┐  User 4                  │
│       │  ├──────────────────────────────────┤  User 3                  │
│       │  ├──────────────────────────────────┤  User 2                  │
│       │  ├──────────────────────────────────┤  User 1                  │
│       └──────────────────────────────────────────────────────────► Time │
│     Each user gets a dedicated frequency band                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

With TDM for example, you have a **timeslot reserved** for every established flow on all links.

### Why Use Circuit Switching?

**Telephone networks work this way.** Why?
- **Lower delay** 
- **Lower jitter** (variance of delay)

**Drawback:** CS may potentially **waste resources** (e.g., when voice call is idle, the reserved slot goes unused).

## Packet Switching (PS)

Packet switching is different from CS:

1. **No explicit setup phase** for a flow
2. Whenever a source has a packet for a destination, the packet is **sent along the first link**
3. The node at the end of that link **receives the packet and forwards it** along as soon as it can
4. And so on...

**No explicit resources are reserved** at any intermediate node for any flow. So if a link is busy, incoming packets may have to be **temporarily stored**. Thus the intermediate nodes are called **"store-and-forward"** switches.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Store-and-Forward Switching                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Source                                                   Destination  │
│   ┌───┐      ┌─────────────┐      ┌─────────────┐      ┌───┐          │
│   │   │─────►│   Switch 1  │─────►│   Switch 2  │─────►│   │          │
│   │   │      │  ┌───────┐  │      │  ┌───────┐  │      │   │          │
│   └───┘      │  │Buffer │  │      │  │Buffer │  │      └───┘          │
│              │  │ [pkt] │  │      │  │ [pkt] │  │                      │
│              │  │ [pkt] │  │      │  │       │  │                      │
│              │  └───────┘  │      │  └───────┘  │                      │
│              └─────────────┘      └─────────────┘                      │
│                                                                         │
│   Packets are stored at each switch until they can be forwarded        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## Statistical Multiplexing

The links in PS are shared not by explicitly reserving resources, but by **"statistical multiplexing"**:

- All packets that arrive at a node are sent out on the outgoing link in a **first-come-first-serve** (or some other) order
- Intermediate nodes have **buffers** to store packets till they are forwarded
- Packets may incur a **"queueing delay"** if there are many packets arriving at a node and waiting to be forwarded
- Some packets may also be **dropped** if the buffer at an intermediate node overflows

**Quality of Service:** Thus you cannot provide any guaranteed Quality of Service (QoS), it is only **"best effort"**.

| Aspect | Packet Switching |
|--------|------------------|
| Delays | Longer delays and jitter |
| Utilization | Better utilization of resources |
| Guarantees | Best effort only |

### Example: Statistical Multiplexing vs TDMA

**Problem:** Consider a link of rate 1 Mbps. Users generate data at 100 kbps when busy, but are busy with probability 0.1.

**With TDMA:**
- Can support only **10 users**
- **90% of slots are wasted** (users are only busy 10% of time)

**With Statistical Multiplexing:**
- If M users in total, probability that N users are active = $\binom{M}{N} \times p^N \times (1-p)^{M-N}$
- For **35 users**, probability that 11 or more are active is **0.0004**
- Most of the time it is okay as 10 or fewer users are active
- When more than 10 users are active, queueing takes place, and queue drains when fewer than 10 users are active

**Result:** Statistical multiplexing can support **3 times as many users** with better utilization of the link.

## Packet Size Considerations

### What is a Packet?

The unit at which you transmit information. If you have a big application message, you:
1. Split it into smaller packets
2. Put a header on each one
3. Send each one independently through the packet switched network

> **Note:** Headers are not so important for circuit switching because a circuit and timeslot schedule is established. Headers are a **must** for packet switching.

### How Big Should a Packet Be?

| Factor | Small Packets | Large Packets |
|--------|---------------|---------------|
| Header Overhead | Higher (repeated in every packet) | Lower |
| Traversal Delay | Lower (pipelining possible) | Higher (wait for full packet) |
| Retransmission Cost | Lower (less data to resend) | Higher (entire packet resent for 1 bit error) |

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Pipelining with Small Packets                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   LARGE PACKET (no pipelining):                                         │
│                                                                         │
│   Time ────────────────────────────────────────────────────────────►    │
│   Link 1: ════════════════════════                                      │
│   Link 2:                         ════════════════════════              │
│           Wait for entire packet before forwarding                      │
│                                                                         │
│   SMALL PACKETS (with pipelining):                                      │
│                                                                         │
│   Time ────────────────────────────────────────────────────────────►    │
│   Link 1: ════╗════╗════╗════                                          │
│   Link 2:     ╚════╗════╗════╗════                                     │
│                    ╚════╗════╗════                                      │
│           First packet proceeds while later ones still arriving        │
│                                                                         │
│   ✓ Small packets finish faster overall!                               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Conclusion:** Choosing optimum packet size is a **fine balancing act**.

## History of Networking

### Timeline

| Era | Development |
|-----|-------------|
| **Pre-1960s** | Only telephone networks existed (circuit switched) |
| **1960s** | Packet switching concepts and theory developed (mainly for data) |
| **1970s** | Several proprietary packet switched networks started with ARPANET |
| **1980s** | Refining of TCP congestion control algorithms; Internet grows |
| **1990s** | US government commercializes the backbone; ISPs emerge |
| **Late 1990s–2000s** | Dotcom bubble, explosion of usage and applications |
| **Late 2000s+** | Stabilization, growth of cellular/mobile data, convergence with Internet |

### The Origin of TCP/IP Split

Several proprietary packet switched networks started in the 1970s beginning with ARPANET. The need came up to **integrate these networks** using a few top-level store-and-forward gateways.

The primitive TCP/IP protocols came into place, but TCP and IP were **tightly coupled**. What led to the split into layers we see now?

## The End-to-End Argument

### Key Design Decisions

**1. Survivability and Fault Tolerance**

One of the main goals of the Internet — survivability, fault tolerance. The intermediate gateways have a lot of state. How should this state be preserved across failures?

**Decision:** The core would store **soft state** (periodically refreshed, nothing permanent, okay to lose state once in a while), and would only forward datagrams in a **connection-less manner**. The **end hosts would maintain** any connection state needed.

**2. Different Transport Needs**

People realized that TCP provides only one type of transport, and people may want to use different transport protocols for different types of applications. For example, not all applications will want the reliability provided by TCP.

**Decision:** TCP and IP were split. **UDP** was provided as another alternative simpler transport.

**3. Minimal Network Assumptions**

We have IP that runs on any network that can deliver a datagram from one IP address to another. **No assumptions made** on the underlying network (in order, reliable, etc.). TCP and other transports run on top of IP and customize the transport protocol to the application needs.

### The End-to-End Principle

The split of TCP and IP is also referred to as the **end-to-end argument**:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       The End-to-End Argument                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   ┌─────────────────┐                           ┌─────────────────┐    │
│   │    END HOST     │                           │    END HOST     │    │
│   │   (Smart)       │                           │    (Smart)      │    │
│   │                 │                           │                 │    │
│   │  • Reliability  │                           │  • Reliability  │    │
│   │  • Security     │                           │  • Security     │    │
│   │  • Ordering     │                           │  • Ordering     │    │
│   │  • App Logic    │                           │  • App Logic    │    │
│   └────────┬────────┘                           └────────▲────────┘    │
│            │                                             │              │
│            │    ┌───────────────────────────────────┐   │              │
│            │    │        NETWORK CORE               │   │              │
│            └───►│          (Dumb)                   │───┘              │
│                 │                                   │                   │
│                 │     • Forward datagrams           │                   │
│                 │     • Best effort delivery        │                   │
│                 │     • No connection state         │                   │
│                 │                                   │                   │
│                 └───────────────────────────────────┘                   │
│                                                                         │
│   "All application and transport intelligence should reside at         │
│    the end hosts. The core of the network should be kept dumb."        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Key Insight:**

> It may be possible to spend a lot of energy in engineering the network core to do some of the jobs of the higher layers (e.g., provide reliability guarantees), but it was decided that the effort to realize it in the core was too high to be worth it, and the end points would be doing it anyways.

End-to-end checks, retries, recovery at end-to-end level, etc. makes more sense.

**The tradeoff** of where to place a certain functionality — end hosts or network — is a common debate in several aspects of networking.

## Summary

| Concept | Description |
|---------|-------------|
| **Circuit Switching** | Setup phase, reserved resources, TDM/FDM, low delay/jitter |
| **Packet Switching** | No setup, store-and-forward, statistical multiplexing |
| **Store-and-Forward** | Packets buffered at intermediate nodes |
| **Statistical Mux** | Better utilization, but variable delay and possible loss |
| **Packet Size** | Trade-off between header overhead and pipelining/retransmission |
| **End-to-End Argument** | Keep network core simple, put intelligence at endpoints |
| **Soft State** | Periodically refreshed, survives failures |
