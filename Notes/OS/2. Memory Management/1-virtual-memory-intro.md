# Introduction to Virtual Memory

---

## 1. Why Virtual Memory?

In the simplest model, a process would directly use **physical memory addresses** — "load the byte at address 0x1000" literally means reading physical RAM location 0x1000. This model has crippling problems:

1. **No isolation**: Process A can read/write process B's memory (intentionally or by bug). A segfault in one program can corrupt another.
2. **No flexibility**: Each process must be loaded at a specific physical address range. Two programs compiled to start at the same address can't coexist.
3. **No efficient use of memory**: A process must have all its memory physically allocated, even if it doesn't use most of it.
4. **No protection**: User programs can overwrite OS kernel memory.

**Virtual memory** solves all of these. Each process operates in its own **virtual address space** — a private, contiguous range of addresses that the hardware translates to physical addresses at runtime.

```
  Without Virtual Memory:               With Virtual Memory:

  Process A:  0x1000 ──► RAM 0x1000     Process A:  VA 0x1000 ──► PA 0x5000
  Process B:  0x1000 ──► RAM 0x1000     Process B:  VA 0x1000 ──► PA 0x9000
              COLLISION!                             No conflict!

  VA = Virtual Address
  PA = Physical Address
```

### Goals of Virtual Memory

| Goal | How Virtual Memory Achieves It |
|------|-------------------------------|
| **Transparency** | Process uses virtual addresses as if it owns all of memory. Doesn't know about physical layout. |
| **Isolation / Protection** | Each process has its own address space. Cannot access another process's physical pages unless explicitly shared. |
| **Efficiency** | Only allocate physical memory for pages actually used (demand paging). Share common pages (shared libraries, COW after fork). |
| **Flexibility** | Process address space layout is independent of physical memory layout. OS can place pages anywhere in physical RAM. |

## 2. Mechanism of Address Translation

Address translation is the process of converting a **virtual address (VA)** generated by the CPU to a **physical address (PA)** in RAM. This happens on **every** memory access (instruction fetch, load, store).

```
  ┌────────┐    Virtual     ┌────────────────┐    Physical     ┌────────────┐
  │  CPU   │───Address────►│  MMU            │───Address─────►│   RAM      │
  │        │    (VA)        │  (Memory        │    (PA)         │            │
  │ (runs  │               │   Management    │                │  (physical │
  │  code) │               │   Unit)         │                │   memory)  │
  └────────┘               └────────────────┘                └────────────┘
                                    │
                                    │ Consults
                                    ▼
                            ┌──────────────┐
                            │  Page Table   │
                            │ (in memory,   │
                            │  per-process) │
                            └──────────────┘
```

The **MMU (Memory Management Unit)** is hardware built into the CPU that performs this translation. It consults a **page table** (a data structure in memory, maintained by the OS) to find the mapping.

There have been two main approaches to virtual memory: **segmentation** and **paging**. Modern systems use paging (with remnants of segmentation on x86).

---

## 3. Segmentation

Segmentation was the earlier approach to virtual memory. The idea: divide the virtual address space into variable-sized **segments**, each with a base and a bound (limit).

### How It Works

Each segment has a pair of registers:
- **Base register**: The starting physical address of the segment.
- **Bound (limit) register**: The size of the segment.

Translation: `Physical Address = Base + Offset`, and the hardware checks that `Offset < Bound`.

```
  Virtual Address:
  ┌──────────────┬────────────────────┐
  │  Segment #   │     Offset         │
  │  (top bits)  │  (remaining bits)  │
  └──────┬───────┴────────┬───────────┘
         │                │
         ▼                │
  ┌──────────────────┐    │
  │  Segment Table    │    │
  ├──────┬───────────┤    │
  │  #0  │ Base=0x4000│    │     Check: Offset < Bound?
  │      │ Bound=0x2000│   │     If yes:  PA = Base + Offset
  ├──────┼───────────┤    │     If no:   SEGFAULT
  │  #1  │ Base=0xA000│    │
  │      │ Bound=0x3000│   │
  ├──────┼───────────┤    │
  │  #2  │ Base=0xF000│    │
  │      │ Bound=0x1000│   │
  └──────┴───────────┘    │
         │                │
         ▼                ▼
  Physical Address = Segment_Base + Offset
```

### Typical Segments

A process might have three segments:

```
  Virtual Address Space:            Physical Memory:

  ┌─────────────────┐               (non-contiguous in physical RAM)
  │  Code Segment    │  ──────►     PA 0x4000 - 0x5FFF
  │  (read-execute)  │
  ├─────────────────┤
  │  Data/Heap Seg   │  ──────►     PA 0xA000 - 0xCFFF
  │  (read-write)    │
  ├─────────────────┤
  │  Stack Segment   │  ──────►     PA 0xF000 - 0xFFFF
  │  (read-write)    │
  └─────────────────┘
```

### Problems with Segmentation

Segmentation suffers from a critical flaw: **external fragmentation**.

```
  Physical Memory After Several Processes Load/Exit:

  ┌──────────┐
  │ Process A │  20 KB
  │  Code     │
  ├──────────┤
  │  FREE     │  8 KB      ← too small for 15 KB request
  ├──────────┤
  │ Process B │  30 KB
  │  Data     │
  ├──────────┤
  │  FREE     │  5 KB      ← too small
  ├──────────┤
  │ Process C │  10 KB
  │  Stack    │
  ├──────────┤
  │  FREE     │  12 KB     ← too small
  └──────────┘
  
  Total free: 25 KB, but no single contiguous block ≥ 15 KB!
  This is EXTERNAL FRAGMENTATION.
```

Because segments are **variable-sized**, they leave irregular holes in physical memory when freed. Even if total free memory is sufficient, it may not be contiguous enough for a new segment.

Solutions (all expensive):
- **Compaction**: Move segments in memory to consolidate free space. Requires copying large amounts of data, stopping processes.
- **Best-fit / first-fit allocation**: Mitigates but doesn't solve the problem.

### x86 Segmentation (Legacy)

x86 historically used segmentation heavily (real mode, 16-bit protected mode). Modern x86-64 in long mode effectively **disables segmentation** for user space:
- Base addresses for `CS`, `DS`, `ES`, `SS` are forced to 0.
- The `FS` and `GS` segments are the exception — Linux uses `GS` for per-CPU data (kernel) and `FS` for thread-local storage (user space, set via `arch_prctl(ARCH_SET_FS, addr)`).
- Segmentation exists in x86-64 only for backward compatibility and the few uses above. **Paging is the real virtual memory mechanism.**

## 4. Paging — The Modern Approach

**Paging** solves the fragmentation problem by dividing both virtual and physical memory into fixed-size blocks:

- **Virtual page**: A fixed-size block of the virtual address space (typically 4 KB).
- **Physical frame (page frame)**: A fixed-size block of physical RAM (same size, 4 KB).

Any virtual page can map to any physical frame. There's no requirement for contiguity.

```
  Virtual Address Space              Physical Memory (RAM)
  (per process)                      (shared by all processes)
  
  ┌─────────────┐ Page 0            ┌─────────────┐ Frame 0
  │             │──────────────────►│             │
  ├─────────────┤ Page 1            ├─────────────┤ Frame 1
  │             │────┐              │  (used by   │
  ├─────────────┤    │              │  Process B) │
  │ (unmapped)  │    │              ├─────────────┤ Frame 2
  ├─────────────┤    │         ┌───►│             │
  │             │────┼────┐    │    ├─────────────┤ Frame 3
  ├─────────────┤    │    │    │    │  (free)     │
  │             │    │    │    │    ├─────────────┤ Frame 4
  └─────────────┘    │    │    │    │             │
                     │    │    │    ├─────────────┤ Frame 5
                     └────┼────┼───►│             │
                          │    │    ├─────────────┤ Frame 6
                          └────┼───►│             │
                               │    ├─────────────┤ Frame 7
                               │    │  (free)     │
                               │    └─────────────┘
                               │
                    Any page can map to any frame!
                    No contiguity required!
```

### Why Fixed-Size Blocks Eliminate External Fragmentation

Because every block is the same size, any free frame can satisfy any page allocation. There's no "hole too small" problem. Free frames don't need to be contiguous.

**Internal fragmentation** still exists — if a process needs 4097 bytes, it gets two 4 KB pages (8192 bytes), wasting 4095 bytes. But with small page sizes (4 KB), this waste is minimal.

### Page Size Trade-offs

| Smaller Pages (e.g., 4 KB) | Larger Pages (e.g., 2 MB, 1 GB) |
|----------------------------|----------------------------------|
| Less internal fragmentation | More internal fragmentation |
| More page table entries (larger tables) | Fewer entries (smaller tables) |
| More TLB misses (limited TLB capacity) | Fewer TLB misses (each entry covers more) |
| Finer-grained protection | Coarser protection |

Linux supports **huge pages**: 2 MB and 1 GB pages on x86-64, used for large memory allocations (databases, VMs, HPC) to reduce TLB pressure.

```bash
# Check huge page support and usage
$ cat /proc/meminfo | grep -i huge
$ cat /sys/kernel/mm/transparent_hugepage/enabled

# Allocate huge pages
$ echo 1024 > /proc/sys/vm/nr_hugepages    # reserve 1024 2MB huge pages
```

## 5. Segmentation vs. Paging: Summary

| Aspect | Segmentation | Paging |
|--------|-------------|--------|
| Block size | Variable | Fixed (4 KB typically) |
| External fragmentation | **Yes** (major problem) | **No** |
| Internal fragmentation | No | Small (up to page_size - 1) |
| Address translation | Base + Offset, check Bound | Page table lookup: VPN → PFN |
| Sharing | Segment-level (coarse) | Page-level (fine-grained) |
| Protection | Per-segment bits | Per-page bits |
| Modern use | Effectively dead (x86-64 base=0) | **Universal** |
| Physical contiguity | Required per segment | **Not required** |

Paging is the dominant virtual memory mechanism in all modern operating systems. The next note ([2-paging.md](2-paging.md)) dives deep into how page tables work.

## Summary

| Concept | Key Idea | Linux Detail |
|---------|----------|--------------|
| Virtual memory | Each process gets a private address space; hardware translates VA → PA | MMU + page tables, `CR3` holds page table base |
| Address translation | Happens on every memory access, by the MMU | MMU walks page tables, TLB caches translations |
| Segmentation | Variable-size regions, base+bound | Effectively disabled in x86-64 long mode (base=0); `FS`/`GS` still used |
| Paging | Fixed-size pages/frames eliminate external fragmentation | 4 KB default, 2 MB / 1 GB huge pages available |
| External fragmentation | Free memory exists but isn't contiguous | Paging eliminates this problem |
