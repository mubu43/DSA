## 1. Thread Models

Before diving into specific thread models, let's understand why thread models matter. When you design a concurrent system, you're essentially deciding how to map work (tasks, requests, computations) onto execution resources (CPU cores, threads). The way you make this mapping has profound implications for performance, latency, throughput, and resource utilization.

### 1.1 One Thread Per Core vs Thread Pools

#### The "One Thread Per Core" Model

The "one thread per core" model is a philosophy where you create exactly as many worker threads as you have CPU cores (or logical processors if hyperthreading is enabled). Each thread is typically pinned (affinity-bound) to a specific core.

**Why would you want this?**

The fundamental insight is that context switching is expensive. When the operating system switches from one thread to another on the same core, it must:

1. Save the entire CPU state (registers, program counter, stack pointer) of the outgoing thread
2. Flush or invalidate certain caches (depending on architecture)
3. Load the saved state of the incoming thread
4. The incoming thread often experiences cache misses because its data may have been evicted

This overhead can range from a few microseconds to tens of microseconds. If your application is doing this thousands of times per second, you're wasting significant CPU time on housekeeping rather than actual work.

By having exactly one thread per core, you eliminate involuntary context switches between your worker threads. Each thread runs until it voluntarily yields (e.g., waiting for I/O), and there's no competition for the core among your application's threads.

**How it works in practice:**

```cpp
#include <thread>
#include <vector>

int main() {
    unsigned int num_cores = std::thread::hardware_concurrency();
    std::vector<std::thread> workers;
    
    for (unsigned int i = 0; i < num_cores; ++i) {
        workers.emplace_back([i]() {
            // Pin this thread to core i (platform-specific)
            // On Linux: pthread_setaffinity_np()
            
            while (true) {
                // Grab work from a queue
                // Process work
                // Never block unless absolutely necessary
            }
        });
    }
    
    for (auto& w : workers) {
        w.join();
    }
}
```

**When one-thread-per-core shines:**

- **High-frequency trading systems**: Every microsecond matters. You want deterministic, predictable latency.
- **Game engines**: The main game loop, physics, and rendering often use dedicated threads to ensure consistent frame rates.
- **Real-time systems**: Medical devices, industrial controllers, and similar systems where timing guarantees are critical.

**The challenges:**

The one-thread-per-core model requires that your threads almost never block. If a thread blocks waiting for I/O, that core sits idle—a waste. This means you must use asynchronous I/O everywhere, which complicates your code. You also need sophisticated work-stealing or work-distribution mechanisms to keep all cores busy.

---

#### Thread Pools

A thread pool is a collection of pre-created threads that sit idle, waiting for work to arrive. When a task comes in, it's assigned to an available thread. When the thread finishes the task, it returns to the pool to await more work.

**Why use a thread pool?**

Creating and destroying threads is expensive. Each thread creation involves:
- Kernel calls to allocate thread control structures
- Stack allocation (typically 1-8 MB per thread)
- Initialization of thread-local storage
- Synchronization overhead

If you're handling 10,000 requests per second and creating a new thread for each one, you'll spend more time managing threads than doing actual work. A thread pool amortizes the creation cost across many tasks.

**How it works:**

```cpp
#include <thread>
#include <queue>
#include <mutex>
#include <condition_variable>
#include <functional>
#include <vector>

class ThreadPool {
public:
    ThreadPool(size_t num_threads) : stop(false) {
        for (size_t i = 0; i < num_threads; ++i) {
            workers.emplace_back([this]() {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lock(queue_mutex);
                        condition.wait(lock, [this]() {
                            return stop || !tasks.empty();
                        });
                        
                        if (stop && tasks.empty()) return;
                        
                        task = std::move(tasks.front());
                        tasks.pop();
                    }
                    task();  // Execute the task
                }
            });
        }
    }
    
    template<typename F>
    void enqueue(F&& f) {
        {
            std::unique_lock<std::mutex> lock(queue_mutex);
            tasks.emplace(std::forward<F>(f));
        }
        condition.notify_one();
    }
    
    ~ThreadPool() {
        {
            std::unique_lock<std::mutex> lock(queue_mutex);
            stop = true;
        }
        condition.notify_all();
        for (auto& worker : workers) {
            worker.join();
        }
    }
    
private:
    std::vector<std::thread> workers;
    std::queue<std::function<void()>> tasks;
    std::mutex queue_mutex;
    std::condition_variable condition;
    bool stop;
};
```

**Sizing the thread pool:**

This is where the art comes in. Too few threads, and you underutilize your CPU. Too many threads, and you waste memory and incur context-switching overhead.

**Rules of thumb:**

- **CPU-bound tasks**: Use approximately `num_cores` threads. More threads won't help because you're limited by CPU cycles, not waiting.
- **I/O-bound tasks**: Use more threads than cores. While one thread waits for disk or network, others can use the CPU. A common formula is `num_cores * (1 + wait_time/compute_time)`.
- **Mixed workloads**: Consider separate pools for CPU-intensive and I/O-intensive tasks.

**Advanced: Work Stealing**

In a naive thread pool, all threads contend on a single queue. This creates a bottleneck. Work-stealing thread pools give each thread its own local queue. Threads primarily consume from their own queue but "steal" from other threads' queues when idle.

```
Thread 1's queue: [Task A] [Task B] [Task C]
Thread 2's queue: [Task D] [Task E]
Thread 3's queue: []  <-- empty, so Thread 3 steals from Thread 1's tail

After stealing:
Thread 1's queue: [Task A] [Task B]
Thread 3's queue: [Task C]  <-- stolen!
```

This reduces contention because threads usually work on their own queues, and stealing happens from the opposite end (tail) to minimize conflicts.

### 1.2 Reactor / Proactor Patterns

Both the Reactor and Proactor patterns are architectural patterns for handling I/O in concurrent applications. They're particularly important for network servers that must handle thousands of simultaneous connections.

#### The Reactor Pattern

**The core idea:** Instead of dedicating a thread to each connection (which doesn't scale), use a single thread (or a small number of threads) to monitor many connections simultaneously. When any connection has data ready to be read (or is ready to accept writes), the reactor "reacts" by dispatching that event to the appropriate handler.

**How it works step by step:**

1. **Registration**: Each I/O source (socket, file descriptor) registers with the reactor, along with a callback (event handler) for events it cares about (readable, writable, error).

2. **Event loop**: The reactor enters an infinite loop where it calls a system multiplexing function (`select()`, `poll()`, `epoll()` on Linux, `kqueue()` on BSD/macOS, `IOCP` on Windows) that blocks until at least one registered source has an event.

3. **Demultiplexing**: When the multiplexing function returns, it tells us which sources have events.

4. **Dispatch**: For each ready source, the reactor calls the registered event handler.

5. **Handling**: The event handler performs the actual I/O operation (read/write). This is **synchronous**—the handler does the read/write itself.

```
                    ┌─────────────────┐
                    │   Application   │
                    └────────┬────────┘
                             │ registers handlers
                             ▼
                    ┌─────────────────┐
                    │     Reactor     │
                    │   (Event Loop)  │
                    └────────┬────────┘
                             │ waits on
                             ▼
                    ┌─────────────────┐
                    │   Demultiplexer │
                    │ (epoll/kqueue)  │
                    └────────┬────────┘
                             │ notifies when ready
                             ▼
          ┌──────────────────┼──────────────────┐
          ▼                  ▼                  ▼
    ┌──────────┐       ┌──────────┐       ┌──────────┐
    │ Handler  │       │ Handler  │       │ Handler  │
    │  (Read)  │       │ (Write)  │       │ (Accept) │
    └──────────┘       └──────────┘       └──────────┘
```

**Pseudocode example:**

```cpp
class Reactor {
    std::map<int, std::function<void(int)>> handlers;  // fd -> callback
    int epoll_fd;
    
public:
    void register_handler(int fd, std::function<void(int)> handler) {
        handlers[fd] = handler;
        // Also register fd with epoll
        epoll_event ev;
        ev.events = EPOLLIN;
        ev.data.fd = fd;
        epoll_ctl(epoll_fd, EPOLL_CTL_ADD, fd, &ev);
    }
    
    void event_loop() {
        epoll_event events[MAX_EVENTS];
        while (true) {
            int n = epoll_wait(epoll_fd, events, MAX_EVENTS, -1);
            for (int i = 0; i < n; ++i) {
                int fd = events[i].data.fd;
                handlers[fd](fd);  // Handler does the actual read/write
            }
        }
    }
};
```

**The key characteristic**: The reactor only tells you *when* I/O is ready. *You* (the handler) must then perform the I/O operation. This is why it's called "synchronous event demultiplexing"—the I/O itself is synchronous.

**Famous implementations:**
- **libevent**, **libev**: C libraries implementing the reactor pattern
- **Node.js**: Uses libuv, which is a reactor on Unix and a proactor on Windows
- **Redis**: Single-threaded reactor, famously efficient
- **Nginx**: Multi-reactor model (one reactor per worker process)

**Limitations:**

If an event handler takes a long time (e.g., CPU-intensive work, or accidental blocking I/O), it blocks the entire event loop. Other connections starve. You must ensure handlers are fast and non-blocking.

---

#### The Proactor Pattern

**The core idea:** Instead of waiting for I/O to be *ready* and then doing it yourself (reactor), you initiate I/O operations *asynchronously* and get notified when they're *complete*. The OS handles the actual data transfer in the background.

**How it works step by step:**

1. **Initiation**: Your application initiates an asynchronous I/O operation (e.g., "read 1024 bytes from this socket into this buffer").

2. **Background processing**: The OS (or an I/O subsystem) performs the actual read/write. Your application thread is free to do other work.

3. **Completion notification**: When the I/O operation finishes, the OS notifies your application (via a completion queue, callback, or event).

4. **Completion handler**: Your completion handler is called with the results (the data that was read, or confirmation that the write succeeded).

```
                    ┌─────────────────┐
                    │   Application   │
                    └────────┬────────┘
                             │ initiates async I/O
                             ▼
                    ┌─────────────────┐
                    │    Proactor     │
                    │ (Async I/O Mgr) │
                    └────────┬────────┘
                             │ delegates to OS
                             ▼
                    ┌─────────────────┐
                    │   OS Kernel /   │
                    │   I/O Subsystem │
                    └────────┬────────┘
                             │ completes I/O, notifies
                             ▼
                    ┌─────────────────┐
                    │  Completion     │
                    │   Dispatcher    │
                    └────────┬────────┘
                             │
          ┌──────────────────┼──────────────────┐
          ▼                  ▼                  ▼
    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
    │  Completion  │  │  Completion  │  │  Completion  │
    │  Handler A   │  │  Handler B   │  │  Handler C   │
    └──────────────┘  └──────────────┘  └──────────────┘
```

**Pseudocode example (conceptual):**

```cpp
class ProactorHandler {
public:
    void start_read(Socket& socket) {
        // Initiate async read - OS will do the actual reading
        socket.async_read(buffer, 1024, 
            [this](size_t bytes_read, Error err) {
                // This is called when read COMPLETES
                handle_read_complete(bytes_read, err);
            }
        );
    }
    
    void handle_read_complete(size_t bytes_read, Error err) {
        // Data is already in 'buffer' - just process it
        process_data(buffer, bytes_read);
        
        // Start another read
        start_read(socket);
    }
};
```

**Platform support:**

True asynchronous I/O requires kernel support:
- **Windows**: IOCP (I/O Completion Ports) is a native proactor implementation, widely considered the most efficient I/O model on Windows.
- **Linux**: `io_uring` (since kernel 5.1) provides true async I/O. Before that, `aio_*` functions existed but were limited and less efficient.

**Boost.Asio** abstracts these differences, providing a proactor-style API on all platforms (though it simulates proactor behavior using reactor semantics on platforms without native async I/O).

---

#### Reactor vs Proactor: The Key Difference

| Aspect | Reactor | Proactor |
|--------|---------|----------|
| When is handler called? | When I/O is *ready* | When I/O is *complete* |
| Who does the I/O? | Your handler (synchronously) | OS/kernel (asynchronously) |
| Data location | You read into your buffer | Data is already in buffer when handler runs |
| Threading model | Usually single-threaded event loop | Can be multi-threaded; handlers run when I/O finishes |
| Platform support | Universal | Requires OS support (IOCP, io_uring) |
| Complexity | Simpler to reason about | More complex, but potentially higher performance |

**When to choose which:**

- Use **Reactor** when you want simplicity, portability, and your I/O operations are fast.
- Use **Proactor** when you need maximum throughput, have OS support, or when your I/O operations might block for significant time.

## 2. Synchronization Choices

When multiple threads access shared data, you need synchronization. But not all synchronization is created equal. Choosing the right primitive can mean the difference between a system that scales linearly and one that becomes a bottleneck under load.

### 2.1 Mutex vs Spinlock vs RW Lock

#### Mutex (Mutual Exclusion Lock)

A mutex is the most common synchronization primitive. When a thread tries to acquire a mutex that's already held by another thread, it **blocks**—the OS puts the thread to sleep and schedules other work.

**How it works internally:**

1. Thread A calls `mutex.lock()`
2. If the mutex is free, Thread A acquires it and continues
3. If Thread B holds the mutex, Thread A makes a system call asking the OS to block it
4. The OS adds Thread A to a wait queue associated with the mutex
5. Thread A stops executing (doesn't consume CPU cycles)
6. When Thread B calls `mutex.unlock()`, the OS wakes one waiting thread
7. Thread A resumes and now holds the mutex

```cpp
#include <mutex>

std::mutex mtx;
int shared_counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(mtx);  // RAII-style locking
    ++shared_counter;
}  // Mutex automatically released here
```

**Cost analysis:**

The cost of a mutex has two components:

1. **Uncontended case**: If no other thread holds the mutex, acquiring it is cheap—often just an atomic compare-and-swap instruction. On modern CPUs, this might take 10-25 nanoseconds.

2. **Contended case**: If another thread holds the mutex, you pay:
   - System call overhead to block (~1000+ nanoseconds)
   - Context switch cost when sleeping
   - Another context switch cost when waking up
   - Potential cache misses when resuming

**When mutexes are best:**

- The critical section is long (more than a few microseconds)
- Contention is expected to be low
- You don't want to waste CPU cycles while waiting
- Fairness matters (most mutex implementations are fair or semi-fair)

---

#### Spinlock

A spinlock is a lock where the waiting thread doesn't sleep—it actively "spins" in a tight loop, repeatedly checking if the lock is available.

**How it works:**

```cpp
#include <atomic>

class Spinlock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT;
    
public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire)) {
            // Spin! We're burning CPU cycles here.
            // Optional: Add a pause instruction to reduce power and
            // avoid memory bus saturation
            #if defined(__x86_64__)
            __builtin_ia32_pause();
            #endif
        }
    }
    
    void unlock() {
        flag.clear(std::memory_order_release);
    }
};
```

**Why would you ever want to burn CPU cycles?**

The key insight is that blocking and unblocking (context switches) are expensive. If the lock is held for only a very short time (tens to hundreds of nanoseconds), the spinning thread might waste less time spinning than it would sleeping and waking up.

Consider:
- Time to block and wake up: ~1000-2000 nanoseconds
- Critical section duration: 50 nanoseconds

If you use a mutex, you might wait 2000ns to access something that will be free in 50ns. With a spinlock, you wait ~50ns (spinning) and get the lock much faster.

**The dangers:**

1. **Long critical sections**: If the lock is held for a long time, spinners waste enormous CPU resources.

2. **Priority inversion**: Imagine a low-priority thread holds the spinlock, but a high-priority thread is spinning for it. The high-priority thread burns CPU that could have been used to let the low-priority thread finish!

3. **Hyperthreading issues**: On hyperthreaded cores, two logical CPUs share physical resources. If one is spinning, it can steal resources from the other (which might be doing useful work or holding the lock you need!).

**Adaptive spinning:**

Modern implementations often combine both approaches:
1. First, spin for a short time (hoping the lock becomes free quickly)
2. If still locked, fall back to blocking

This is sometimes called an "adaptive mutex" or "hybrid lock."

**When spinlocks are best:**

- Critical section is extremely short (dozens of instructions)
- You have dedicated cores (no hyperthreading concerns)
- Low contention expected
- Real-time systems where context switch jitter is unacceptable

---

#### Read-Write Lock (RW Lock / Shared-Exclusive Lock)

Many data structures are read much more often than they're written. A read-write lock exploits this asymmetry:

- **Multiple readers** can hold the lock simultaneously (shared mode)
- **Writers** need exclusive access (no readers, no other writers)

**How it works:**

```cpp
#include <shared_mutex>

std::shared_mutex rw_mutex;
std::map<std::string, int> data;

int read_value(const std::string& key) {
    std::shared_lock<std::shared_mutex> lock(rw_mutex);  // Shared (read) lock
    auto it = data.find(key);
    return (it != data.end()) ? it->second : -1;
}  // Many threads can be here simultaneously

void write_value(const std::string& key, int value) {
    std::unique_lock<std::shared_mutex> lock(rw_mutex);  // Exclusive (write) lock
    data[key] = value;
}  // Only one thread can be here, and no readers
```

**The trade-offs:**

RW locks seem like a free lunch, but they have hidden costs:

1. **Complexity**: The lock implementation is more complex than a simple mutex, requiring more atomic operations and bookkeeping.

2. **Writer starvation**: If readers constantly arrive, a writer might wait forever. Some RW lock implementations prioritize writers to avoid this.

3. **Cache coherency traffic**: When a reader acquires the lock, it must atomically increment a reader count. This modifies the lock's cache line, potentially invalidating it on other cores (we'll explore this more in the false sharing section).

**When RW locks are worth it:**

- Reads vastly outnumber writes (>10:1 ratio or higher)
- Read critical sections are long enough to justify the overhead
- Writes are infrequent enough that readers don't often wait

**Counter-intuitive truth:**

For short critical sections with moderate write frequency, a simple mutex often outperforms an RW lock because the RW lock's overhead exceeds the benefit of concurrent reads.

---

#### Summary Table

| Characteristic | Mutex | Spinlock | RW Lock |
|----------------|-------|----------|---------|
| Waiting strategy | Sleep (block) | Busy-wait (spin) | Sleep (usually) |
| CPU usage while waiting | None | 100% of a core | None |
| Best for critical section length | Medium to long | Very short | Any |
| Read concurrency | No | No | Yes |
| Typical overhead | Medium | Low (if uncontended) | Higher |
| Fairness | Usually fair | Often unfair | Varies |

### 2.2 Lock-Free / Wait-Free Data Structures

Lock-based programming has inherent problems:
- **Priority inversion**: A low-priority thread holding a lock blocks high-priority threads
- **Convoying**: Threads queue up behind a slow lock holder
- **Deadlock**: Multiple locks acquired in different orders
- **Performance**: Locks serialize access, limiting parallelism

Lock-free and wait-free programming offer alternatives.

#### Definitions

**Lock-free**: At least one thread makes progress in a finite number of steps. Some threads might starve, but the system as a whole always moves forward. If a thread is suspended mid-operation, it doesn't prevent other threads from completing their operations.

**Wait-free**: Every thread makes progress in a bounded number of steps. No thread ever starves. This is strictly stronger than lock-free and much harder to achieve.

**Obstruction-free**: A thread will complete its operation in a bounded number of steps if all other threads are suspended. This is weaker than lock-free.

```
Wait-free ⊂ Lock-free ⊂ Obstruction-free
(strongest)            (weakest)
```

#### How Lock-Free Works: Atomic Operations

Lock-free programming is built on atomic operations, particularly **Compare-And-Swap (CAS)**:

```cpp
// Pseudocode for CAS
bool compare_and_swap(int* address, int expected, int desired) {
    if (*address == expected) {
        *address = desired;
        return true;  // Success
    }
    return false;  // Someone else modified it
}
```

In C++:
```cpp
std::atomic<int> value{0};

int expected = 0;
int desired = 1;
bool success = value.compare_exchange_strong(expected, desired);
// If value was 0, it's now 1, success is true
// If value wasn't 0, expected now contains the actual value, success is false
```

#### Example: Lock-Free Stack

```cpp
#include <atomic>

template<typename T>
class LockFreeStack {
    struct Node {
        T data;
        Node* next;
        Node(const T& d) : data(d), next(nullptr) {}
    };
    
    std::atomic<Node*> head{nullptr};
    
public:
    void push(const T& value) {
        Node* new_node = new Node(value);
        new_node->next = head.load(std::memory_order_relaxed);
        
        // Keep trying until we successfully link the new node
        while (!head.compare_exchange_weak(
            new_node->next,  // Expected: what we think head is
            new_node,        // Desired: make head point to new_node
            std::memory_order_release,
            std::memory_order_relaxed
        )) {
            // CAS failed because another thread modified head
            // new_node->next has been updated to the current head
            // Loop will try again
        }
    }
    
    bool pop(T& result) {
        Node* old_head = head.load(std::memory_order_relaxed);
        
        while (old_head != nullptr) {
            // Try to swing head to the next node
            if (head.compare_exchange_weak(
                old_head,           // Expected
                old_head->next,     // Desired
                std::memory_order_acquire,
                std::memory_order_relaxed
            )) {
                result = old_head->data;
                // NOTE: Deleting old_head is tricky! (See ABA problem)
                return true;
            }
            // CAS failed, old_head has been updated, try again
        }
        return false;  // Stack was empty
    }
};
```

**Why is this lock-free?**

Even if one thread is suspended mid-`push` or mid-`pop`, other threads can still successfully complete their operations. The suspended thread isn't holding any lock that would block others.

#### The ABA Problem

Consider this scenario with our lock-free stack:

1. Thread 1 sees head = A (with A->next = B), prepares to pop A
2. Thread 1 is suspended
3. Thread 2 pops A
4. Thread 2 pops B
5. Thread 2 pushes a new node that happens to be allocated at the same address as A (memory was recycled!)
6. Now head = A again (but it's a different A!)
7. Thread 1 resumes, sees head is still A, CAS succeeds
8. Thread 1 sets head = B, but B was already popped!

The stack is now corrupted because Thread 1 couldn't tell that A had changed identity.

**Solutions:**

1. **Hazard pointers**: Threads announce which nodes they're accessing. Memory can't be reclaimed until no thread has it as a hazard.

2. **Epoch-based reclamation**: Divide time into epochs. Memory is only freed when all threads have passed through the epoch when it was retired.

3. **Tagged pointers**: Include a counter with the pointer. Each modification increments the counter, so ABA becomes (A,1) → (A,2), which is detectable.

```cpp
// Tagged pointer approach
struct TaggedPtr {
    Node* ptr;
    uintptr_t tag;
};
std::atomic<TaggedPtr> head;

// When modifying, increment tag
TaggedPtr old_head = head.load();
TaggedPtr new_head = {new_node, old_head.tag + 1};
head.compare_exchange_strong(old_head, new_head);
```

#### Memory Ordering

Lock-free code requires careful attention to memory ordering. Without locks to provide synchronization, you must use atomic operations with appropriate memory orderings:

```cpp
std::atomic<bool> ready{false};
int data = 0;

// Thread 1 (Producer)
data = 42;                                  // Non-atomic write
ready.store(true, std::memory_order_release);  // "Release" the data

// Thread 2 (Consumer)
while (!ready.load(std::memory_order_acquire)) { }  // "Acquire" the data
std::cout << data;  // Guaranteed to see 42
```

The release-acquire pair ensures that all writes before the release are visible to code after the acquire.

#### Should You Use Lock-Free Structures?

**Pros:**
- No deadlocks (by definition)
- No priority inversion
- Often better scalability under high contention
- Progress guarantees (lock-free or wait-free)

**Cons:**
- Extremely difficult to get right
- Memory reclamation is hard
- Harder to reason about and debug
- May not be faster than well-designed locked structures for your specific use case

**Recommendation:**

Use battle-tested libraries (like Folly's ConcurrentHashMap, libcds, or Boost.Lockfree) rather than writing your own. Lock-free programming is a minefield, and even experts regularly discover bugs in published algorithms.

## 3. False Sharing and Cache Line Alignment

To understand false sharing, you must first understand how CPUs cache memory.

### The Memory Hierarchy

Modern CPUs access RAM, but RAM is slow—about 100 nanoseconds per access. To bridge this gap, CPUs have caches:

```
CPU Core
   ↓
L1 Cache (32-64 KB, ~1-4 cycles, ~1ns)
   ↓
L2 Cache (256 KB - 1 MB, ~10-20 cycles, ~3-10ns)
   ↓
L3 Cache (shared, several MB, ~30-50 cycles, ~10-20ns)
   ↓
Main RAM (~100-300 cycles, ~100ns)
```

### Cache Lines: The Unit of Transfer

CPUs don't fetch individual bytes from memory—they fetch **cache lines**, typically 64 bytes on modern x86 processors. When you access any byte within a 64-byte block, the entire block is loaded into the cache.

```
Memory address: 0x1000 contains byte X
Cache line contains addresses: 0x1000 - 0x103F (64 bytes)

When you read X, all 64 bytes come into cache together
```

### Cache Coherency

When multiple cores have caches, they might cache the same memory location. What happens when one core modifies it? The hardware maintains **cache coherency**—all cores see a consistent view of memory.

The most common protocol is **MESI** (Modified, Exclusive, Shared, Invalid):

- **Modified**: I have the only copy, and I've changed it. RAM is stale.
- **Exclusive**: I have the only cached copy, it matches RAM.
- **Shared**: Multiple cores might have copies, all match RAM.
- **Invalid**: My copy is outdated, must fetch from elsewhere.

When Core A writes to a Shared line, it must first **invalidate** copies on other cores. Those cores must then fetch the new value (from Core A's cache or RAM) before they can read it.

### False Sharing: The Problem

Now imagine two threads on different cores, working on different variables that happen to reside on the same cache line:

```cpp
struct SharedData {
    int counter_a;  // Used only by Thread A
    int counter_b;  // Used only by Thread B
};

SharedData data;  // Both counters are likely on the same cache line!

// Thread A
for (int i = 0; i < 1000000; ++i) {
    data.counter_a++;
}

// Thread B
for (int i = 0; i < 1000000; ++i) {
    data.counter_b++;
}
```

**What happens:**

1. Thread A increments `counter_a`, marking its cache line as Modified
2. This invalidates Thread B's copy of the cache line (even though Thread B doesn't care about `counter_a`!)
3. Thread B tries to increment `counter_b`, but its cache line is Invalid
4. Thread B must fetch the cache line from Thread A
5. Thread B increments `counter_b`, marking its cache line as Modified
6. This invalidates Thread A's copy
7. Repeat ad infinitum...

The cache lines are **ping-ponging** between cores, causing massive slowdowns—sometimes 10x to 100x slower than the unsynchronized case.

**This is false sharing**: threads are unintentionally "sharing" a cache line even though they're accessing completely independent data.

### Detecting False Sharing

Performance counters can reveal false sharing. On Linux:

```bash
perf stat -e cache-misses,cache-references ./your_program
```

High cache miss rates on data that should be thread-local are a red flag.

### Solving False Sharing: Cache Line Alignment

The solution is to ensure that data accessed by different threads resides on different cache lines.

**Method 1: Padding**

```cpp
struct PaddedCounter {
    alignas(64) int counter_a;  // Starts at a 64-byte boundary
    alignas(64) int counter_b;  // Starts at the NEXT 64-byte boundary
};
```

Or with explicit padding:

```cpp
struct PaddedCounter {
    int counter_a;
    char padding1[60];  // Pad to fill rest of 64-byte cache line
    int counter_b;
    char padding2[60];
};
```

**Method 2: C++17 `std::hardware_destructive_interference_size`**

```cpp
#include <new>  // For hardware_destructive_interference_size

struct alignas(std::hardware_destructive_interference_size) AlignedCounter {
    int value;
};

AlignedCounter counters[NUM_THREADS];  // Each counter on its own cache line
```

`hardware_destructive_interference_size` is the minimum offset between two objects to avoid false sharing (typically 64 bytes).

There's also `hardware_constructive_interference_size`, which is the maximum size of contiguous memory that benefits from being on the same cache line (also typically 64 bytes). Use this when you *want* related data to share a cache line for performance.

**Method 3: Thread-Local Storage**

If each thread only needs its own copy of the data:

```cpp
thread_local int local_counter = 0;

void thread_work() {
    for (int i = 0; i < 1000000; ++i) {
        local_counter++;  // No sharing at all!
    }
}
```

### Example: Fixing a Real Problem

**Before (false sharing):**
```cpp
std::atomic<long> counters[4];  // All may be on 1-2 cache lines

void worker(int id) {
    for (int i = 0; i < 10000000; ++i) {
        counters[id].fetch_add(1);
    }
}
```

**After (cache-aligned):**
```cpp
struct alignas(64) AlignedCounter {
    std::atomic<long> value;
};

AlignedCounter counters[4];  // Each on its own cache line

void worker(int id) {
    for (int i = 0; i < 10000000; ++i) {
        counters[id].value.fetch_add(1);
    }
}
```

The performance difference can be dramatic—often 5-20x faster.

## 4. NUMA-Aware Design

### What is NUMA?

NUMA stands for **Non-Uniform Memory Access**. In a NUMA system, not all memory is equal—access time depends on which processor is accessing which memory.

**Traditional symmetric multiprocessing (SMP):**
```
    CPU 0        CPU 1        CPU 2        CPU 3
       \            \            /            /
        \            \          /            /
         \            \        /            /
          ============ Memory Bus ===========
                        |
                     Memory
```

All CPUs connect to a single memory bus. As you add more CPUs, the bus becomes a bottleneck.

**NUMA architecture:**
```
┌─────────────────────┐           ┌─────────────────────┐
│      NUMA Node 0    │           │      NUMA Node 1    │
│ ┌───────┬───────┐   │           │ ┌───────┬───────┐   │
│ │ CPU 0 │ CPU 1 │   │           │ │ CPU 2 │ CPU 3 │   │
│ └───────┴───────┘   │           │ └───────┴───────┘   │
│          │          │           │          │          │
│    Local Memory     │◄─────────►│    Local Memory     │
│     (fast access)   │ Interconnect│   (fast access)   │
└─────────────────────┘           └─────────────────────┘
```

Each NUMA node has its own memory controller and local memory. Accessing local memory is fast; accessing memory on another node ("remote memory") requires traversing an interconnect and is slower.

**Typical latency difference:**
- Local memory access: ~80ns
- Remote memory access: ~150-200ns (1.5x to 2.5x slower)

On systems with many nodes (4, 8, or more), the difference grows because you might need to hop through multiple interconnects.

### Why NUMA Matters for Performance

If you don't consider NUMA topology, your threads might:

1. Be scheduled on a different node than where their data resides
2. Always access remote memory, cutting memory bandwidth in half or worse
3. Saturate interconnect bandwidth while local bandwidth goes unused

### NUMA-Aware Memory Allocation

**First-touch policy:**

By default on Linux, memory is allocated on the node that first "touches" (writes to) it. This is the first-touch policy.

```cpp
void* buffer = malloc(1GB);  // No physical pages allocated yet (just virtual)

// Thread on Node 0 initializes the data
for (size_t i = 0; i < 1GB; ++i) {
    buffer[i] = 0;  // First touch! Pages allocated on Node 0
}

// Later, if Thread on Node 1 uses this buffer heavily, it's accessing
// remote memory—slow!
```

**Solution: Parallel first-touch initialization**

```cpp
#pragma omp parallel for
for (size_t i = 0; i < 1GB; ++i) {
    buffer[i] = 0;
    // Each thread touches its portion
    // Pages allocated on the node where each thread runs
}
```

**Explicit NUMA allocation:**

On Linux, you can use `libnuma` or `numactl`:

```cpp
#include <numa.h>

void* allocate_on_node(size_t size, int node) {
    return numa_alloc_onnode(size, node);
}

// Or interleave across all nodes for balanced access
void* buffer = numa_alloc_interleaved(size);
```

Command-line control:
```bash
# Run process with memory on node 0 only
numactl --membind=0 ./my_program

# Interleave memory across all nodes
numactl --interleave=all ./my_program
```

### Thread Placement

Allocating memory correctly is half the battle; you also need to run threads on the right nodes.

**Thread affinity:**

```cpp
#include <pthread.h>
#include <sched.h>

void pin_thread_to_cpu(int cpu_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(cpu_id, &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpuset), &cpuset);
}
```

**Pin thread to a NUMA node (all CPUs on that node):**

```cpp
#include <numa.h>

void pin_thread_to_node(int node) {
    struct bitmask* cpus = numa_allocate_cpumask();
    numa_node_to_cpus(node, cpus);
    numa_sched_setaffinity(0, cpus);  // 0 = current thread
    numa_free_cpumask(cpus);
}
```

### NUMA-Aware Data Structure Design

**Principle: Keep data close to the threads that use it.**

**Example: NUMA-aware thread pool**

Instead of one central work queue, have one queue per NUMA node:

```cpp
class NUMAThreadPool {
    struct NodePool {
        std::queue<Task> tasks;
        std::mutex mutex;
        std::condition_variable cv;
        std::vector<std::thread> workers;
    };
    
    std::vector<NodePool> node_pools;  // One per NUMA node
    
public:
    void submit(int preferred_node, Task task) {
        auto& pool = node_pools[preferred_node];
        {
            std::lock_guard<std::mutex> lock(pool.mutex);
            pool.tasks.push(std::move(task));
        }
        pool.cv.notify_one();
    }
};
```

Threads on each node preferentially pull from their local queue. This keeps data access local.

### NUMA Pitfalls

**Kernel migration:**

Even if you pin threads and allocate carefully, the Linux kernel might migrate memory pages between nodes for "optimization" or because of memory pressure. You can use `mlock()` to prevent this:

```cpp
mlock(buffer, size);  // Lock pages in RAM, prevent migration
```

**Allocator behavior:**

Standard allocators like `malloc` may not be NUMA-aware. Consider:
- **jemalloc** or **tcmalloc**: Better for multi-threaded workloads, some NUMA awareness
- **Custom NUMA allocators**: For maximum control

**Measuring NUMA effects:**

```bash
# Show NUMA topology
numactl --hardware

# Memory access statistics
numastat -p <pid>

# Performance counters for remote access
perf stat -e node-loads,node-load-misses ./program
```

### NUMA Summary

1. **Understand your topology**: Use `numactl --hardware`, `lscpu`, or `hwloc` to understand your system.

2. **Allocate memory on the right node**: Use first-touch policy or explicit NUMA allocation.

3. **Pin threads appropriately**: Keep threads close to their data.

4. **Design data structures for locality**: Per-node queues, partitioned data, avoid shared-nothing when possible.

5. **Measure, don't assume**: NUMA effects vary widely by workload. Profile to find hotspots.

## Summary

Understanding concurrency and parallelism at this level is essential for building high-performance systems:

1. **Thread models** determine how you map work to cores. One-thread-per-core minimizes context switching for latency-sensitive work; thread pools manage thread lifecycle efficiently for general workloads. Reactor and Proactor patterns enable handling many I/O operations with few threads.

2. **Synchronization choices** involve trade-offs. Mutexes are the default; spinlocks are for microsecond-level critical sections; RW locks help when reads dominate. Lock-free structures offer progress guarantees but are fiendishly complex.

3. **False sharing** is a hidden performance killer. Understanding cache lines and ensuring thread-local data doesn't share cache lines with other threads' data can yield dramatic speedups.

4. **NUMA awareness** is critical on multi-socket systems. Keeping data close to the threads that use it—through careful memory allocation and thread placement—prevents remote memory access penalties from dominating your performance profile.

These concepts are interconnected. A NUMA-aware thread pool that avoids false sharing in its work queues, uses appropriate synchronization, and follows the reactor pattern for I/O—this is how high-performance systems are built.
