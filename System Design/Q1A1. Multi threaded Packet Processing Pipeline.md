## 1. Understanding the Requirements

Before diving into the design, we need to clarify what "packet processing" means and what constraints we're working under. In a real interview, you would ask these clarifying questions.

### What kind of packets?

- **Network packets** (Ethernet frames, IP packets, TCP/UDP segments)
- Typical sizes: 64 bytes (minimum Ethernet) to 1500 bytes (standard MTU) to 9000 bytes (jumbo frames)
- For this design, we'll assume a mix, with an average of ~500 bytes

### What does "processing" involve?

A typical packet processing pipeline might include:
1. **Receive**: Get packets from network interface
2. **Parse**: Extract headers (Ethernet, IP, TCP/UDP)
3. **Classify**: Determine packet type, priority, destination
4. **Filter**: Apply firewall rules, ACLs
5. **Transform**: NAT, encapsulation, encryption
6. **Route/Forward**: Determine output interface
7. **Transmit**: Send to destination

### What are the latency requirements?

- Soft real-time: 99th percentile latency < 1ms
- Or hard real-time: every packet processed within deadline
- We'll design for low and predictable latency

### What hardware are we targeting?

- Modern multi-core server (let's assume 16-32 cores)
- NUMA architecture (2-4 sockets)
- 10 Gbps or higher network interfaces
- Potentially with hardware offload capabilities (DPDK-compatible NICs)

## 2. Back-of-the-Envelope Calculations

Let's do the math to understand if 10M packets/sec is even feasible.

### Time budget per packet

```
10,000,000 packets/second
= 10 packets per microsecond
= 1 packet per 100 nanoseconds
```

100 nanoseconds is roughly **200-400 CPU cycles** on a 2-4 GHz processor. That's extremely tight for any non-trivial processing!

### Is this achievable on a single core?

On a single core, 100ns per packet means:
- No system calls (each syscall costs ~100-1000ns)
- No memory allocation (malloc can cost 50-500ns)
- No cache misses (L3 cache miss to RAM costs ~100ns)
- Minimal branching (branch mispredictions cost ~10-20ns)

**Conclusion**: A single core cannot handle 10M pps with any real processing. We need multiple cores.

### Multi-core requirement

If we can process 1M packets/sec per core (1µs per packet, a more realistic budget), we need at least **10 cores** dedicated to packet processing. With overhead and safety margin, we should plan for **12-16 cores**.

### Memory bandwidth check

```
10M packets/sec × 500 bytes average = 5 GB/sec
```

Modern DDR4 provides 25-50 GB/sec per channel, with multiple channels. Memory bandwidth is likely not the bottleneck.

### Network interface check

```
10M packets × 500 bytes × 8 bits = 40 Gbps
```

We need at least a 40 Gbps NIC, or multiple 10 Gbps NICs.

## 3. High-Level Architecture

Based on our analysis, here's the high-level architecture:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              PACKET FLOW                                     │
└─────────────────────────────────────────────────────────────────────────────┘

     ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
     │   NIC    │────►│ RX Ring  │────►│  Stage   │────►│  Stage   │────►
     │(Hardware)│     │ Buffers  │     │    1     │     │    2     │
     └──────────┘     └──────────┘     │ (Parse)  │     │(Classify)│
                                       └──────────┘     └──────────┘
                                             │                │
                                             │                │
                                      ┌──────┴──────┐  ┌──────┴──────┐
                                      │Worker│Worker│  │Worker│Worker│
                                      │  1   │  2   │  │  1   │  2   │
                                      └──────┴──────┘  └──────┴──────┘

     ┌──────────┐     ┌──────────┐     ┌──────────┐
────►│  Stage   │────►│ TX Ring  │────►│   NIC    │
     │    3     │     │ Buffers  │     │(Hardware)│
     │(Forward) │     └──────────┘     └──────────┘
     └──────────┘
          │
   ┌──────┴──────┐
   │Worker│Worker│
   │  1   │  2   │
   └──────┴──────┘
```

### Key Architectural Decisions

1. **Pipeline Architecture**: Break processing into stages, each stage handled by a pool of workers
2. **Lock-Free Queues**: Between stages, use lock-free MPMC (multi-producer, multi-consumer) queues
3. **Kernel Bypass**: Use DPDK or similar to avoid kernel overhead
4. **Zero-Copy**: Pass pointers between stages, never copy packet data
5. **NUMA-Aware**: Allocate memory and pin threads to respect NUMA topology

## 4. Detailed Component Design

### 4.1 Packet Ingress (Receive Path)

The first challenge is getting packets from the network into our application as fast as possible.

#### The Problem with Standard Linux Networking

Standard Linux socket APIs have significant overhead:
- Each `recv()` or `recvmsg()` is a **system call** (~100-500ns)
- Kernel copies packet data to user space
- Interrupt handling overhead
- Protocol stack processing we may not need

At 10M pps, we'd need 10 million syscalls/second—impossible.

#### Solution: Kernel Bypass with DPDK

**DPDK (Data Plane Development Kit)** bypasses the kernel entirely:

1. **Huge Pages**: Uses 2MB or 1GB huge pages to reduce TLB misses
2. **Poll Mode Driver (PMD)**: No interrupts; dedicated cores poll the NIC
3. **Ring Buffers**: Lock-free ring buffers between NIC and application
4. **Zero-Copy**: DMA directly into application memory

```cpp
// Pseudocode for DPDK packet receive
void rx_thread(int port_id, int queue_id) {
    rte_mbuf* packets[BURST_SIZE];
    
    while (running) {
        // Poll for received packets (no syscall, no interrupt)
        uint16_t nb_rx = rte_eth_rx_burst(port_id, queue_id, packets, BURST_SIZE);
        
        if (nb_rx > 0) {
            // Process or enqueue packets
            for (uint16_t i = 0; i < nb_rx; ++i) {
                process_packet(packets[i]);
            }
        }
        // No packets? Loop immediately - busy polling
    }
}
```

#### RSS (Receive Side Scaling)

Modern NICs can hash incoming packets and distribute them across multiple RX queues:

```
Incoming Packets ─────┬────► RX Queue 0 ────► Core 0
                      ├────► RX Queue 1 ────► Core 1
                      ├────► RX Queue 2 ────► Core 2
                      └────► RX Queue 3 ────► Core 3
```

The hash is typically computed over (src IP, dst IP, src port, dst port), ensuring packets from the same flow go to the same queue. This is critical for maintaining packet ordering within flows.

### 4.2 Packet Parsing Stage

Once we have raw packets, we need to parse headers to understand what they are.

#### The Challenge

Parsing involves:
- Accessing different offsets in the packet
- Handling variable-length headers (IP options, TCP options)
- Validating checksums
- Dealing with encapsulation (VLAN, MPLS, GRE, VXLAN)

#### Efficient Parsing Strategy

```cpp
struct ParsedPacket {
    // Original packet reference (zero-copy)
    uint8_t* raw_data;
    uint16_t raw_length;
    
    // Parsed header pointers (just offsets into raw_data)
    EthernetHeader* eth;
    IpHeader* ip;
    union {
        TcpHeader* tcp;
        UdpHeader* udp;
        IcmpHeader* icmp;
    } l4;
    
    // Computed metadata
    uint32_t flow_hash;
    uint16_t payload_offset;
    uint16_t payload_length;
    uint8_t protocol;
    uint8_t priority;
};

bool parse_packet(uint8_t* data, uint16_t length, ParsedPacket* out) {
    if (length < sizeof(EthernetHeader)) return false;
    
    out->raw_data = data;
    out->raw_length = length;
    out->eth = reinterpret_cast<EthernetHeader*>(data);
    
    uint16_t offset = sizeof(EthernetHeader);
    uint16_t ethertype = ntohs(out->eth->ethertype);
    
    // Handle VLAN tags
    while (ethertype == 0x8100 || ethertype == 0x88a8) {  // 802.1Q or QinQ
        if (offset + 4 > length) return false;
        ethertype = ntohs(*reinterpret_cast<uint16_t*>(data + offset + 2));
        offset += 4;
    }
    
    // Parse IP header
    if (ethertype == 0x0800) {  // IPv4
        if (offset + sizeof(IpHeader) > length) return false;
        out->ip = reinterpret_cast<IpHeader*>(data + offset);
        
        uint8_t ihl = (out->ip->version_ihl & 0x0F) * 4;
        offset += ihl;
        out->protocol = out->ip->protocol;
        
        // Parse L4 header
        switch (out->protocol) {
            case 6:  // TCP
                if (offset + sizeof(TcpHeader) > length) return false;
                out->l4.tcp = reinterpret_cast<TcpHeader*>(data + offset);
                out->payload_offset = offset + (out->l4.tcp->data_offset >> 4) * 4;
                break;
            case 17:  // UDP
                if (offset + sizeof(UdpHeader) > length) return false;
                out->l4.udp = reinterpret_cast<UdpHeader*>(data + offset);
                out->payload_offset = offset + sizeof(UdpHeader);
                break;
            // ... other protocols
        }
        
        // Compute flow hash for consistent routing
        out->flow_hash = compute_flow_hash(out->ip->src_addr, out->ip->dst_addr,
                                           out->l4.tcp->src_port, out->l4.tcp->dst_port);
    }
    
    out->payload_length = length - out->payload_offset;
    return true;
}
```

#### Key Optimizations

1. **No memory allocation**: ParsedPacket is on the stack or from a pool
2. **Zero-copy**: We store pointers into the original packet, not copies
3. **Branch reduction**: Common case (IPv4 TCP/UDP) should have minimal branches
4. **Prefetching**: If processing in batches, prefetch the next packet while parsing the current one

```cpp
for (int i = 0; i < batch_size; ++i) {
    // Prefetch next packet's headers into L1 cache
    if (i + 1 < batch_size) {
        __builtin_prefetch(packets[i + 1]->data, 0, 3);
    }
    parse_packet(packets[i]->data, packets[i]->length, &parsed[i]);
}
```

### 4.3 Classification Stage

Classification determines what to do with each packet: apply QoS, route to a specific handler, drop it, etc.

#### Flow Table Lookup

Most classification involves looking up the packet in a flow table:

```cpp
struct FlowKey {
    uint32_t src_ip;
    uint32_t dst_ip;
    uint16_t src_port;
    uint16_t dst_port;
    uint8_t protocol;
    uint8_t pad[3];
};

struct FlowEntry {
    FlowKey key;
    uint64_t packet_count;
    uint64_t byte_count;
    uint32_t action;        // FORWARD, DROP, RATE_LIMIT, etc.
    uint32_t output_port;
    uint64_t last_seen;
};
```

#### Hash Table Design for High Performance

A naive `std::unordered_map` won't cut it. We need:

1. **Open addressing with linear probing**: Better cache behavior than chaining
2. **Power-of-two size**: Modulo becomes bitwise AND
3. **Cache-line-aligned buckets**: Each bucket fits in one cache line
4. **Read-mostly optimization**: Use RCU for concurrent access

```cpp
class FlowTable {
    static constexpr size_t BUCKET_SIZE = 64;  // Cache line size
    static constexpr size_t ENTRIES_PER_BUCKET = BUCKET_SIZE / sizeof(FlowEntry*);
    
    struct alignas(64) Bucket {
        std::atomic<FlowEntry*> entries[ENTRIES_PER_BUCKET];
    };
    
    Bucket* buckets;
    size_t num_buckets;  // Power of 2
    size_t bucket_mask;
    
public:
    FlowEntry* lookup(const FlowKey& key) {
        size_t hash = hash_flow_key(key);
        size_t bucket_idx = hash & bucket_mask;
        
        Bucket& bucket = buckets[bucket_idx];
        
        // Check all entries in the bucket
        for (size_t i = 0; i < ENTRIES_PER_BUCKET; ++i) {
            FlowEntry* entry = bucket.entries[i].load(std::memory_order_acquire);
            if (entry && memcmp(&entry->key, &key, sizeof(FlowKey)) == 0) {
                return entry;
            }
        }
        
        // Linear probing to next bucket
        // ... (simplified for brevity)
        
        return nullptr;  // Not found
    }
};
```

#### Rule Matching (ACLs, Firewall Rules)

For complex rule matching (source/dest IP ranges, port ranges, etc.), we might use:

1. **Tuple Space Search**: Multiple hash tables indexed by different field combinations
2. **Decision Trees**: HyperCuts, EffiCuts algorithms
3. **Hardware Offload**: Modern NICs support flow classification in hardware

### 4.4 Transformation Stage

This stage modifies packets: NAT, encapsulation, encryption, etc.

#### NAT Example

```cpp
void apply_snat(ParsedPacket* pkt, uint32_t new_src_ip, uint16_t new_src_port) {
    // Update IP header
    uint32_t old_src_ip = pkt->ip->src_addr;
    pkt->ip->src_addr = new_src_ip;
    
    // Incremental checksum update (RFC 1624)
    update_checksum_incremental(&pkt->ip->checksum, old_src_ip, new_src_ip);
    
    // Update L4 header
    if (pkt->protocol == 6) {  // TCP
        uint16_t old_port = pkt->l4.tcp->src_port;
        pkt->l4.tcp->src_port = new_src_port;
        update_checksum_incremental(&pkt->l4.tcp->checksum, old_src_ip, new_src_ip);
        update_checksum_incremental(&pkt->l4.tcp->checksum, old_port, new_src_port);
    } else if (pkt->protocol == 17) {  // UDP
        // Similar for UDP
    }
}
```

#### Key Insight: Incremental Checksum

Recomputing the entire checksum is expensive. The incremental update formula from RFC 1624 allows O(1) updates:

```
new_checksum = ~(~old_checksum + ~old_value + new_value)
```

This is much faster than summing all bytes.

### 4.5 Forwarding/Transmission Stage

Finally, we send packets out.

#### Transmit Ring Buffers

Similar to receive, we use ring buffers for transmission:

```cpp
void tx_thread(int port_id, int queue_id, LockFreeQueue<rte_mbuf*>& tx_queue) {
    rte_mbuf* packets[BURST_SIZE];
    
    while (running) {
        // Dequeue packets from the processing pipeline
        size_t count = 0;
        while (count < BURST_SIZE) {
            rte_mbuf* pkt;
            if (!tx_queue.try_dequeue(pkt)) break;
            packets[count++] = pkt;
        }
        
        if (count > 0) {
            // Send burst to NIC
            uint16_t sent = rte_eth_tx_burst(port_id, queue_id, packets, count);
            
            // Handle packets that couldn't be sent (buffer full)
            if (sent < count) {
                for (uint16_t i = sent; i < count; ++i) {
                    // Either retry, drop, or re-queue
                    rte_pktmbuf_free(packets[i]);
                    stats.tx_drops++;
                }
            }
        }
    }
}
```

## 5. Memory Management Strategy

Memory management is critical at 10M pps. We cannot call `malloc()` for each packet.

### Memory Pools (mbufs in DPDK)

Pre-allocate a large pool of fixed-size buffers:

```cpp
class PacketPool {
    struct PoolBlock {
        uint8_t data[PACKET_BUFFER_SIZE];  // e.g., 2048 bytes
    };
    
    PoolBlock* pool;
    LockFreeStack<PoolBlock*> free_list;
    size_t total_count;
    
public:
    PacketPool(size_t count) : total_count(count) {
        // Allocate from huge pages for TLB efficiency
        pool = static_cast<PoolBlock*>(
            mmap(nullptr, count * sizeof(PoolBlock),
                 PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB,
                 -1, 0)
        );
        
        // Initialize free list
        for (size_t i = 0; i < count; ++i) {
            free_list.push(&pool[i]);
        }
    }
    
    PoolBlock* allocate() {
        PoolBlock* block;
        if (free_list.pop(block)) {
            return block;
        }
        return nullptr;  // Pool exhausted
    }
    
    void deallocate(PoolBlock* block) {
        free_list.push(block);
    }
};
```

### Per-Core Memory Pools

To avoid contention, each core has its own pool:

```cpp
class PerCorePacketPool {
    struct alignas(64) CorePool {
        LockFreeStack<PoolBlock*> local_free;
        std::atomic<size_t> local_count;
    };
    
    CorePool per_core_pools[MAX_CORES];
    PacketPool shared_pool;  // Global backup
    
public:
    PoolBlock* allocate(int core_id) {
        // Try local pool first (no contention)
        PoolBlock* block;
        if (per_core_pools[core_id].local_free.pop(block)) {
            return block;
        }
        
        // Local pool empty, refill from shared pool
        refill_local_pool(core_id);
        
        if (per_core_pools[core_id].local_free.pop(block)) {
            return block;
        }
        
        return nullptr;  // All pools exhausted
    }
    
    void deallocate(PoolBlock* block, int core_id) {
        per_core_pools[core_id].local_free.push(block);
        
        // If local pool too large, return some to shared pool
        if (per_core_pools[core_id].local_count > HIGH_WATERMARK) {
            drain_to_shared_pool(core_id);
        }
    }
};
```

### NUMA-Aware Allocation

Memory should be allocated on the NUMA node where it will be used:

```cpp
PacketPool* create_numa_aware_pool(int numa_node, size_t count) {
    // Bind allocation to specific NUMA node
    numa_set_preferred(numa_node);
    
    // Or use explicit NUMA allocation
    void* memory = numa_alloc_onnode(count * sizeof(PoolBlock), numa_node);
    
    return new PacketPool(memory, count);
}
```

## 6. Threading Model

### Option 1: Run-to-Completion

Each RX core processes packets through ALL stages:

```
Core 0: [RX] → [Parse] → [Classify] → [Transform] → [TX]
Core 1: [RX] → [Parse] → [Classify] → [Transform] → [TX]
Core 2: [RX] → [Parse] → [Classify] → [Transform] → [TX]
...
```

**Pros:**
- No inter-core communication (no queues between stages)
- Packet data stays in one core's cache
- Simple to reason about

**Cons:**
- All stages must fit in the time budget
- If one stage is slow, you can't add more cores to just that stage
- Work imbalance if some packets need more processing

### Option 2: Pipeline Model

Different cores handle different stages:

```
Core 0-3:   [RX + Parse]     ────►  Queue A  ────►
Core 4-7:   [Classify]       ────►  Queue B  ────►
Core 8-11:  [Transform]      ────►  Queue C  ────►
Core 12-15: [TX]
```

**Pros:**
- Can scale stages independently
- Stages can be specialized

**Cons:**
- Queue overhead between stages
- Cache pollution (packet data accessed by multiple cores)
- Complex load balancing

### Option 3: Hybrid Model (Recommended)

Combine both approaches:

```cpp
// Each RX core does parsing (run-to-completion for early stages)
void rx_worker(int core_id, int port, int queue) {
    pin_to_core(core_id);
    PacketPool* pool = get_numa_local_pool(core_id);
    
    while (running) {
        rte_mbuf* packets[BURST_SIZE];
        uint16_t nb_rx = rte_eth_rx_burst(port, queue, packets, BURST_SIZE);
        
        for (uint16_t i = 0; i < nb_rx; ++i) {
            ParsedPacket parsed;
            if (!parse_packet(packets[i]->data, packets[i]->length, &parsed)) {
                drop_packet(packets[i]);
                continue;
            }
            
            // Use flow hash to select processing core (maintains ordering)
            int target_core = parsed.flow_hash % num_processing_cores;
            processing_queues[target_core].enqueue(parsed);
        }
    }
}

// Processing cores do classify, transform, and enqueue for TX
void processing_worker(int core_id) {
    pin_to_core(core_id);
    auto& my_queue = processing_queues[core_id];
    
    while (running) {
        ParsedPacket pkt;
        if (my_queue.try_dequeue(pkt)) {
            FlowEntry* flow = flow_table.lookup(pkt.flow_key());
            
            if (flow) {
                apply_action(flow->action, &pkt);
                
                int tx_queue = determine_tx_queue(&pkt);
                tx_queues[tx_queue].enqueue(pkt);
            }
        }
    }
}
```

### Thread Pinning

Pinning threads to cores is essential to avoid:
- Context switch overhead
- Cache pollution from thread migration
- NUMA performance penalties

```cpp
void pin_to_core(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
}
```

## 7. Queue Design Between Stages

The queues between pipeline stages are critical to performance.

### Requirements

1. **High throughput**: Millions of operations per second
2. **Low latency**: Ideally < 100ns per enqueue/dequeue
3. **Lock-free**: Avoid blocking and priority inversion
4. **Bounded**: Prevent memory exhaustion
5. **MPMC or SPSC**: Depending on the pipeline design

### SPSC (Single Producer, Single Consumer) Queue

The simplest and fastest queue when you have exactly one producer and one consumer:

```cpp
template<typename T, size_t Capacity>
class SPSCQueue {
    static_assert((Capacity & (Capacity - 1)) == 0, "Capacity must be power of 2");
    
    struct alignas(64) {
        std::atomic<size_t> head{0};
        char pad1[64 - sizeof(std::atomic<size_t>)];
        std::atomic<size_t> tail{0};
        char pad2[64 - sizeof(std::atomic<size_t>)];
    } indices;
    
    alignas(64) T buffer[Capacity];
    
public:
    bool try_enqueue(const T& item) {
        size_t tail = indices.tail.load(std::memory_order_relaxed);
        size_t next_tail = (tail + 1) & (Capacity - 1);
        
        if (next_tail == indices.head.load(std::memory_order_acquire)) {
            return false;  // Queue full
        }
        
        buffer[tail] = item;
        indices.tail.store(next_tail, std::memory_order_release);
        return true;
    }
    
    bool try_dequeue(T& item) {
        size_t head = indices.head.load(std::memory_order_relaxed);
        
        if (head == indices.tail.load(std::memory_order_acquire)) {
            return false;  // Queue empty
        }
        
        item = buffer[head];
        indices.head.store((head + 1) & (Capacity - 1), std::memory_order_release);
        return true;
    }
};
```

**Key optimizations:**
- **Cache line padding**: `head` and `tail` on separate cache lines to avoid false sharing
- **Power-of-2 size**: Modulo becomes bitwise AND
- **Relaxed memory ordering** where safe, acquire-release for synchronization points

### MPMC (Multi-Producer, Multi-Consumer) Queue

More complex, but necessary when multiple threads produce or consume:

```cpp
template<typename T, size_t Capacity>
class MPMCQueue {
    static_assert((Capacity & (Capacity - 1)) == 0, "Capacity must be power of 2");
    
    struct Cell {
        std::atomic<size_t> sequence;
        T data;
    };
    
    alignas(64) Cell buffer[Capacity];
    alignas(64) std::atomic<size_t> enqueue_pos{0};
    alignas(64) std::atomic<size_t> dequeue_pos{0};
    
public:
    MPMCQueue() {
        for (size_t i = 0; i < Capacity; ++i) {
            buffer[i].sequence.store(i, std::memory_order_relaxed);
        }
    }
    
    bool try_enqueue(const T& item) {
        Cell* cell;
        size_t pos = enqueue_pos.load(std::memory_order_relaxed);
        
        while (true) {
            cell = &buffer[pos & (Capacity - 1)];
            size_t seq = cell->sequence.load(std::memory_order_acquire);
            intptr_t diff = static_cast<intptr_t>(seq) - static_cast<intptr_t>(pos);
            
            if (diff == 0) {
                // Slot is available for writing
                if (enqueue_pos.compare_exchange_weak(pos, pos + 1, std::memory_order_relaxed)) {
                    break;  // We claimed this slot
                }
            } else if (diff < 0) {
                return false;  // Queue is full
            } else {
                // Another thread is writing to this slot, try next
                pos = enqueue_pos.load(std::memory_order_relaxed);
            }
        }
        
        cell->data = item;
        cell->sequence.store(pos + 1, std::memory_order_release);
        return true;
    }
    
    bool try_dequeue(T& item) {
        Cell* cell;
        size_t pos = dequeue_pos.load(std::memory_order_relaxed);
        
        while (true) {
            cell = &buffer[pos & (Capacity - 1)];
            size_t seq = cell->sequence.load(std::memory_order_acquire);
            intptr_t diff = static_cast<intptr_t>(seq) - static_cast<intptr_t>(pos + 1);
            
            if (diff == 0) {
                // Slot has data ready for reading
                if (dequeue_pos.compare_exchange_weak(pos, pos + 1, std::memory_order_relaxed)) {
                    break;
                }
            } else if (diff < 0) {
                return false;  // Queue is empty
            } else {
                pos = dequeue_pos.load(std::memory_order_relaxed);
            }
        }
        
        item = cell->data;
        cell->sequence.store(pos + Capacity, std::memory_order_release);
        return true;
    }
};
```

## 8. Handling Backpressure

What happens when packets arrive faster than we can process them?

### Detection

Monitor queue depths:

```cpp
class QueueMonitor {
    std::atomic<size_t> high_watermark_events{0};
    
public:
    void check_queue(const MPMCQueue<T>& queue) {
        size_t depth = queue.size();
        
        if (depth > HIGH_WATERMARK) {
            high_watermark_events.fetch_add(1, std::memory_order_relaxed);
            
            // Trigger backpressure response
            activate_backpressure();
        }
    }
};
```

### Response Strategies

**1. Tail Drop**: Simply drop new packets when queue is full

```cpp
bool enqueue_with_drop(const Packet& pkt) {
    if (!queue.try_enqueue(pkt)) {
        stats.drops++;
        return false;
    }
    return true;
}
```

**2. Random Early Detection (RED)**: Probabilistically drop packets as queue fills

```cpp
bool should_accept_packet(size_t queue_depth) {
    if (queue_depth < min_threshold) {
        return true;  // Always accept
    }
    if (queue_depth > max_threshold) {
        return false;  // Always drop
    }
    
    // Linear probability between thresholds
    double drop_prob = (queue_depth - min_threshold) / 
                       (double)(max_threshold - min_threshold);
    return (rand() / (double)RAND_MAX) > drop_prob;
}
```

**3. Explicit Congestion Notification (ECN)**: Mark packets instead of dropping

```cpp
void mark_congestion(ParsedPacket* pkt) {
    // Set ECN bits in IP header
    pkt->ip->tos |= 0x03;  // CE (Congestion Experienced)
    
    // Recalculate checksum
    update_ip_checksum(pkt->ip);
}
```

**4. Upstream Signaling**: Tell the NIC to pause sending

```cpp
void enable_flow_control(int port_id) {
    struct rte_eth_fc_conf fc_conf;
    memset(&fc_conf, 0, sizeof(fc_conf));
    
    fc_conf.mode = RTE_FC_FULL;  // Both RX and TX pause
    fc_conf.pause_time = 0xFFFF;
    fc_conf.high_water = 0x8000;
    fc_conf.low_water = 0x4000;
    
    rte_eth_dev_flow_ctrl_set(port_id, &fc_conf);
}
```

## 9. Performance Optimizations

### 9.1 Batch Processing

Process packets in groups rather than one at a time:

```cpp
void process_batch(ParsedPacket* packets, size_t count) {
    // Prefetch all packets into cache
    for (size_t i = 0; i < count; ++i) {
        __builtin_prefetch(packets[i].raw_data, 0, 1);
    }
    
    // Process in batches
    for (size_t i = 0; i < count; ++i) {
        classify_packet(&packets[i]);
    }
    
    for (size_t i = 0; i < count; ++i) {
        transform_packet(&packets[i]);
    }
}
```

**Benefits:**
- Amortizes function call overhead
- Better instruction cache utilization (same code runs repeatedly)
- Enables prefetching

### 9.2 Prefetching

Explicitly load data into cache before you need it:

```cpp
// Software prefetch
__builtin_prefetch(address, 0, 3);  // 0 = read, 3 = high temporal locality

// Prefetch flow table entry while parsing
void process_packet(ParsedPacket* pkt) {
    // Compute hash and prefetch flow entry
    size_t hash = compute_flow_hash(pkt);
    FlowEntry* predicted_entry = &flow_table.buckets[hash & mask];
    __builtin_prefetch(predicted_entry, 0, 2);
    
    // Continue parsing (meanwhile, prefetch is happening)
    finish_parsing(pkt);
    
    // Now access flow entry (hopefully in cache)
    FlowEntry* entry = flow_table.lookup(pkt);
}
```

### 9.3 Branch Prediction Hints

Help the CPU predict branches:

```cpp
if (__builtin_expect(pkt->ip->version == 4, 1)) {
    // IPv4 path - expected (likely)
    process_ipv4(pkt);
} else {
    // IPv6 path - unexpected (unlikely)
    process_ipv6(pkt);
}
```

### 9.4 SIMD Processing

Use vector instructions to process multiple packets simultaneously:

```cpp
#include <immintrin.h>

// Parse 4 packet lengths at once using AVX
void parse_lengths_simd(uint16_t* lengths, uint8_t** packets, int count) {
    for (int i = 0; i < count; i += 4) {
        // Load 4 length fields
        __m128i len = _mm_set_epi16(
            0, 0, 0, 0,
            ntohs(*(uint16_t*)(packets[i+3] + 2)),
            ntohs(*(uint16_t*)(packets[i+2] + 2)),
            ntohs(*(uint16_t*)(packets[i+1] + 2)),
            ntohs(*(uint16_t*)(packets[i+0] + 2))
        );
        
        _mm_storeu_si128((__m128i*)(lengths + i), len);
    }
}
```

### Graceful Degradation

When overloaded, shed load intelligently:

```cpp
class LoadShedder {
    std::atomic<int> load_level{0};  // 0 = normal, higher = more shedding
    
public:
    bool should_process(ParsedPacket* pkt) {
        int level = load_level.load(std::memory_order_relaxed);
        
        if (level == 0) return true;  // Normal operation
        
        // Prioritize important traffic
        if (pkt->priority >= HIGH_PRIORITY) return true;
        
        // Shed low-priority traffic based on load level
        if (level >= 3 && pkt->priority == LOW_PRIORITY) return false;
        if (level >= 5) return false;  // Extreme: drop most traffic
        
        return true;
    }
    
    void update_load_level(size_t avg_queue_depth) {
        if (avg_queue_depth > CRITICAL_THRESHOLD) {
            load_level.store(5, std::memory_order_relaxed);
        } else if (avg_queue_depth > HIGH_THRESHOLD) {
            load_level.store(3, std::memory_order_relaxed);
        } else if (avg_queue_depth > LOW_THRESHOLD) {
            load_level.store(1, std::memory_order_relaxed);
        } else {
            load_level.store(0, std::memory_order_relaxed);
        }
    }
};
```

## 11. Complete Code Architecture

Here's how all the pieces fit together:

```cpp
class PacketProcessor {
    // Configuration
    Config config;
    
    // Memory pools (per NUMA node)
    std::vector<PacketPool*> packet_pools;
    
    // Queues between stages
    std::vector<MPMCQueue<PacketBatch*>> parse_to_classify_queues;
    std::vector<MPMCQueue<PacketBatch*>> classify_to_transform_queues;
    std::vector<SPSCQueue<PacketBatch*>> transform_to_tx_queues;
    
    // Data structures
    FlowTable flow_table;
    RuleEngine rule_engine;
    
    // Statistics and monitoring
    PerCoreStats stats[MAX_CORES];
    HealthMonitor health_monitor;
    MetricsExporter metrics_exporter;
    LoadShedder load_shedder;
    
    // Worker threads
    std::vector<std::thread> rx_threads;
    std::vector<std::thread> worker_threads;
    std::vector<std::thread> tx_threads;
    
    std::atomic<bool> running{true};
    
public:
    void initialize() {
        // Initialize DPDK
        init_dpdk();
        
        // Create NUMA-aware memory pools
        for (int node = 0; node < numa_num_configured_nodes(); ++node) {
            packet_pools.push_back(create_numa_pool(node, POOL_SIZE));
        }
        
        // Initialize flow table
        flow_table.initialize(FLOW_TABLE_SIZE);
        
        // Load rules
        rule_engine.load_rules(config.rule_file);
        
        // Create queues
        create_queues();
        
        // Start worker threads
        start_threads();
    }
    
    void start_threads() {
        // RX threads - one per RX queue
        for (int i = 0; i < config.num_rx_queues; ++i) {
            rx_threads.emplace_back([this, i]() {
                rx_worker(i);
            });
        }
        
        // Processing threads - one per processing core
        for (int i = 0; i < config.num_worker_cores; ++i) {
            worker_threads.emplace_back([this, i]() {
                process_worker(i);
            });
        }
        
        // TX threads - one per TX queue
        for (int i = 0; i < config.num_tx_queues; ++i) {
            tx_threads.emplace_back([this, i]() {
                tx_worker(i);
            });
        }
    }
    
    void rx_worker(int queue_id) {
        int core_id = config.rx_core_map[queue_id];
        pin_to_core(core_id);
        
        int numa_node = numa_node_of_cpu(core_id);
        PacketPool* pool = packet_pools[numa_node];
        
        rte_mbuf* rx_pkts[BURST_SIZE];
        PacketBatch* batch = allocate_batch(pool);
        
        while (running.load(std::memory_order_relaxed)) {
            uint16_t nb_rx = rte_eth_rx_burst(config.port_id, queue_id, rx_pkts, BURST_SIZE);
            
            for (uint16_t i = 0; i < nb_rx; ++i) {
                if (batch->count >= BATCH_SIZE) {
                    // Batch full, send to processing
                    int target = batch->packets[0].flow_hash % config.num_worker_cores;
                    parse_to_classify_queues[target].enqueue(batch);
                    batch = allocate_batch(pool);
                }
                
                // Parse packet
                if (parse_packet(rte_pktmbuf_mtod(rx_pkts[i], uint8_t*),
                                rte_pktmbuf_pkt_len(rx_pkts[i]),
                                &batch->packets[batch->count])) {
                    batch->packets[batch->count].mbuf = rx_pkts[i];
                    batch->count++;
                } else {
                    stats[core_id].parse_errors++;
                    rte_pktmbuf_free(rx_pkts[i]);
                }
            }
            
            health_monitor.heartbeat(core_id);
        }
    }
    
    void process_worker(int worker_id) {
        int core_id = config.worker_core_map[worker_id];
        pin_to_core(core_id);
        
        while (running.load(std::memory_order_relaxed)) {
            PacketBatch* batch;
            
            if (parse_to_classify_queues[worker_id].try_dequeue(batch)) {
                for (size_t i = 0; i < batch->count; ++i) {
                    ParsedPacket* pkt = &batch->packets[i];
                    
                    // Load shedding check
                    if (!load_shedder.should_process(pkt)) {
                        stats[core_id].drops++;
                        rte_pktmbuf_free(pkt->mbuf);
                        continue;
                    }
                    
                    // Classify
                    FlowEntry* flow = flow_table.lookup(pkt->flow_key());
                    if (!flow) {
                        flow = flow_table.create_flow(pkt);
                    }
                    
                    // Apply rules
                    Action action = rule_engine.match(pkt, flow);
                    
                    // Transform
                    apply_action(action, pkt, flow);
                    
                    // Update stats
                    flow->packet_count++;
                    flow->byte_count += pkt->raw_length;
                    flow->last_seen = get_timestamp();
                }
                
                // Forward to TX
                int tx_queue = determine_tx_queue(batch);
                transform_to_tx_queues[tx_queue].enqueue(batch);
                
                stats[core_id].packets_processed += batch->count;
            }
            
            health_monitor.heartbeat(core_id);
        }
    }
    
    void tx_worker(int queue_id) {
        int core_id = config.tx_core_map[queue_id];
        pin_to_core(core_id);
        
        rte_mbuf* tx_pkts[BURST_SIZE];
        
        while (running.load(std::memory_order_relaxed)) {
            PacketBatch* batch;
            
            if (transform_to_tx_queues[queue_id].try_dequeue(batch)) {
                size_t count = 0;
                
                for (size_t i = 0; i < batch->count; ++i) {
                    tx_pkts[count++] = batch->packets[i].mbuf;
                }
                
                uint16_t sent = rte_eth_tx_burst(config.port_id, queue_id, tx_pkts, count);
                
                // Handle unsent packets
                for (uint16_t i = sent; i < count; ++i) {
                    rte_pktmbuf_free(tx_pkts[i]);
                    stats[core_id].tx_drops++;
                }
                
                stats[core_id].tx_packets += sent;
                
                // Return batch to pool
                free_batch(batch);
            }
            
            health_monitor.heartbeat(core_id);
        }
    }
    
    void shutdown() {
        running.store(false, std::memory_order_relaxed);
        
        for (auto& t : rx_threads) t.join();
        for (auto& t : worker_threads) t.join();
        for (auto& t : tx_threads) t.join();
        
        // Cleanup
        cleanup_dpdk();
    }
};
```

## 12. Trade-offs and Alternatives

### DPDK vs Kernel Networking

| Aspect | DPDK | Standard Linux |
|--------|------|----------------|
| Latency | <10µs | >50µs |
| Throughput | 10M+ pps | ~1M pps |
| Complexity | High | Low |
| Kernel integration | None (bypass) | Full |
| Debugging | Difficult | Standard tools work |
| CPU usage | Dedicated cores (100%) | On-demand |

**When to use standard Linux**: Lower throughput requirements, need kernel features (firewall, routing), simpler deployment.

### XDP (eXpress Data Path)

An alternative to DPDK that runs eBPF programs in the kernel:

**Pros:**
- No dedicated cores (interrupt-driven)
- Integrates with kernel networking
- Easier deployment

**Cons:**
- Slightly higher latency than DPDK
- Limited programming model (eBPF restrictions)

### Hardware Offload

Modern SmartNICs can offload packet processing:

- **Flow classification**: Matching rules in NIC hardware
- **Encryption/Decryption**: AES-GCM in hardware
- **Checksum calculation**: IP/TCP/UDP checksums
- **RSS**: Receive-side scaling

Consider hardware offload for:
- Encryption/decryption (CPU-intensive)
- Simple flow matching
- Checksum operations

Designing a 10M pps packet processing pipeline requires:

1. **Kernel bypass** (DPDK) to eliminate syscall overhead
2. **Lock-free data structures** for inter-thread communication

4. **Careful threading** with core pinning and cache optimization

- Cache misses
- Lock contention
- Unnecessary data copies

This design achieves high performance through careful attention to all these factors, creating a system that can sustain 10 million packets per second with predictable, low latency.

## 13. Deep Dive: Locking, Contention, and Work Partitioning

This section addresses three critical follow-up questions that interviewers often ask after the initial design presentation.

### 13.1 Where Locks Exist (and Why)

In a high-performance packet processing system, we aim to be **lock-free on the fast path** (packet processing) but may accept locks on the **slow path** (configuration, statistics aggregation, rare events). Let's analyze every potential locking point in our design.

#### Fast Path: Lock-Free Design

The fast path—the journey of a packet from NIC to processing to transmission—should be completely lock-free. Here's why and how:

**1. Inter-Stage Queues: Lock-Free**

```cpp
// NO LOCKS HERE - uses atomic CAS operations
class MPMCQueue {
    std::atomic<size_t> enqueue_pos;
    std::atomic<size_t> dequeue_pos;
    // ...
};
```

**Why no locks?** At 10M pps, even a single `std::mutex` acquisition (typically 15-25ns uncontended, potentially microseconds when contended) would consume a significant portion of our 100ns budget. Lock-free queues use atomic compare-and-swap (CAS) operations that complete in a few nanoseconds.

**2. Memory Pool Allocation: Lock-Free (Per-Core)**

```cpp
// Each core has its own pool - no contention
PoolBlock* allocate(int core_id) {
    return per_core_pools[core_id].local_free.pop();  // Lock-free stack
}
```

**Why no locks?** Memory allocation happens for every packet. By giving each core its own pool, we eliminate all contention. The lock-free stack uses atomic operations.

**3. Flow Table Lookup: Lock-Free Reads (RCU Pattern)**

```cpp
// Read path - no locks
FlowEntry* lookup(const FlowKey& key) {
    size_t idx = hash(key) & mask;
    FlowEntry* entry = buckets[idx].load(std::memory_order_acquire);
    // ... traverse and match
    return entry;
}
```

**Why no locks for reads?** 99%+ of flow table operations are lookups. Using Read-Copy-Update (RCU) semantics, readers never block. Writers create a new version of the data and atomically swap pointers.

**4. Statistics Updates: Lock-Free Atomics**

```cpp
// Per-core stats - no contention
stats[core_id].packets_processed.fetch_add(1, std::memory_order_relaxed);
```

**Why no locks?** Each core updates only its own statistics counters. `std::memory_order_relaxed` is sufficient because we don't need ordering guarantees for statistics.

---

#### Slow Path: Where Locks ARE Acceptable

Some operations happen rarely (once per second, or once per minute) and can tolerate locking:

**1. Flow Table Insertion (Writes)**

```cpp
class FlowTable {
    std::shared_mutex table_mutex;  // Reader-writer lock
    
    FlowEntry* create_flow(const FlowKey& key) {
        // First try lock-free lookup (common case: flow exists)
        FlowEntry* existing = lookup(key);
        if (existing) return existing;
        
        // Flow doesn't exist - need write lock
        std::unique_lock<std::shared_mutex> lock(table_mutex);
        
        // Double-check (another thread might have created it)
        existing = lookup(key);
        if (existing) return existing;
        
        // Actually create the flow
        FlowEntry* new_flow = allocate_flow_entry();
        // ... initialize and insert
        return new_flow;
    }
};
```

**Why accept a lock here?** New flows are created relatively rarely (once per connection, not once per packet). A 10M pps system might handle 100K new flows/sec—a 100:1 ratio means most packets hit existing flows.

**Alternative: Lock-Free Insertion**

For even higher performance, you can use lock-free insertion with CAS:

```cpp
FlowEntry* create_flow_lockfree(const FlowKey& key) {
    FlowEntry* new_flow = allocate_flow_entry();
    initialize_flow(new_flow, key);
    
    size_t idx = hash(key) & mask;
    FlowEntry* expected = nullptr;
    
    // CAS loop to insert
    while (!buckets[idx].compare_exchange_weak(expected, new_flow)) {
        if (expected && keys_match(expected->key, key)) {
            // Someone else inserted this flow
            free_flow_entry(new_flow);
            return expected;
        }
        // Collision - linear probe to next bucket
        idx = (idx + 1) & mask;
        expected = nullptr;
    }
    
    return new_flow;
}
```

**2. Configuration Updates**

```cpp
class RuleEngine {
    std::shared_mutex rules_mutex;
    std::vector<Rule> rules;
    
    void reload_rules(const std::string& filename) {
        std::vector<Rule> new_rules = parse_rules(filename);
        
        std::unique_lock<std::shared_mutex> lock(rules_mutex);
        rules = std::move(new_rules);
    }
    
    Action match(const ParsedPacket* pkt) {
        std::shared_lock<std::shared_mutex> lock(rules_mutex);
        // ... match against rules
    }
};
```

**Why accept a lock here?** Configuration changes might happen once per hour or less. The shared_mutex allows concurrent readers (packet matching) while blocking only during the brief moment rules are updated.

**Better Alternative: RCU for Rules**

```cpp
class RuleEngine {
    std::atomic<RuleSet*> current_rules;
    
    void reload_rules(const std::string& filename) {
        RuleSet* new_rules = new RuleSet(parse_rules(filename));
        
        RuleSet* old_rules = current_rules.exchange(new_rules, std::memory_order_acq_rel);
        
        // Defer deletion until all readers are done (grace period)
        schedule_deferred_delete(old_rules);
    }
    
    Action match(const ParsedPacket* pkt) {
        RuleSet* rules = current_rules.load(std::memory_order_acquire);
        return rules->match(pkt);  // No lock!
    }
};
```

**3. Statistics Aggregation**

```cpp
class MetricsExporter {
    std::mutex export_mutex;  // Only one export at a time
    
    Metrics collect_and_export() {
        std::lock_guard<std::mutex> lock(export_mutex);
        
        Metrics m;
        for (int i = 0; i < num_cores; ++i) {
            // Reading atomic values - no lock needed for each read
            m.total_packets += stats[i].packets_processed.load(std::memory_order_relaxed);
        }
        
        export_to_prometheus(m);
        return m;
    }
};
```

**Why accept a lock here?** Metrics export happens once per second or less. The lock ensures consistent snapshots and prevents multiple export threads from racing.

|-----------|-----------|-----------|---------------|

### 13.2 How Contention Is Avoided

Contention occurs when multiple threads try to access the same resource simultaneously. In our design, we use multiple strategies to eliminate or minimize contention.

#### Strategy 1: Data Partitioning by Core

The most effective way to avoid contention is to ensure threads don't share data at all.

```
┌─────────────────────────────────────────────────────────────┐
│                     Memory Layout                            │
├─────────────────────────────────────────────────────────────┤
│  Core 0 Private    │  Core 1 Private    │  Core 2 Private   │
│  ┌──────────────┐  │  ┌──────────────┐  │  ┌──────────────┐ │
│  │ Packet Pool  │  │  │ Packet Pool  │  │  │ Packet Pool  │ │
│  │ Stats        │  │  │ Stats        │  │  │ Stats        │ │
│  │ Work Queue   │  │  │ Work Queue   │  │  │ Work Queue   │ │
│  │ Scratch Mem  │  │  │ Scratch Mem  │  │  │ Scratch Mem  │ │
│  └──────────────┘  │  └──────────────┘  │  └──────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

**What's partitioned:**

1. **Memory Pools**: Each core allocates from its own pool
2. **Statistics Counters**: Each core has its own counters (aggregated on read)
3. **Work Queues**: Each processing core has its own input queue
4. **Scratch Memory**: Temporary buffers for parsing, etc.

```cpp
struct alignas(64) PerCoreData {
    // Everything a core needs - on separate cache lines from other cores
    PacketPool* local_pool;
    PerCoreStats stats;
    MPMCQueue<PacketBatch*>* input_queue;
    uint8_t scratch_buffer[SCRATCH_SIZE];
    
    // Padding to prevent false sharing with next core's data
    char padding[64 - (sizeof(void*) * 2 + sizeof(PerCoreStats) + SCRATCH_SIZE) % 64];
};

PerCoreData core_data[MAX_CORES];
```

#### Strategy 2: Flow Affinity (Consistent Hashing)

Packets from the same flow always go to the same core. This eliminates contention on flow state.

```cpp
void rx_worker(int queue_id) {
    while (running) {
        rte_mbuf* packets[BURST_SIZE];
        uint16_t nb_rx = rte_eth_rx_burst(port, queue_id, packets, BURST_SIZE);
        
        for (uint16_t i = 0; i < nb_rx; ++i) {
            ParsedPacket parsed;
            parse_packet(packets[i], &parsed);
            
            // Hash determines which core processes this flow
            uint32_t flow_hash = hash_5tuple(
                parsed.ip->src_addr, parsed.ip->dst_addr,
                parsed.l4.tcp->src_port, parsed.l4.tcp->dst_port,
                parsed.protocol
            );
            
            int target_core = flow_hash % num_processing_cores;
            
            // This flow ALWAYS goes to the same core
            processing_queues[target_core].enqueue(parsed);
        }
    }
}
```

**Why this works:**

- All packets from flow (10.0.0.1:5000 → 192.168.1.1:80) go to, say, Core 3
- Core 3 owns the flow state for this connection
- No other core ever touches this flow's state
- Zero contention on flow table entries

**Bonus: Ordering preserved** - Packets within a flow are processed in order since they go to a single core's queue.

#### Strategy 3: Lock-Free Data Structures

When cores must share data, we use lock-free structures that use atomic CAS instead of locks.

```cpp
// Lock-free queue avoids blocking
bool try_enqueue(const T& item) {
    // Uses compare_exchange, not mutex
    while (!enqueue_pos.compare_exchange_weak(...)) {
        // Retry - no sleeping, no blocking
    }
}
```

**Contention still exists** (multiple cores might CAS the same variable), but the critical difference:

- **With locks**: One thread wins, others **sleep** (context switch overhead)
- **Lock-free**: One thread wins, others **retry immediately** (few nanoseconds)

#### Strategy 4: Batching to Reduce Contention Frequency

Instead of enqueuing packets one at a time, we enqueue batches.

```cpp
// BAD: One queue operation per packet
for (int i = 0; i < 32; ++i) {
    queue.enqueue(packets[i]);  // 32 contentious operations
}

// GOOD: One queue operation per batch
PacketBatch batch;
batch.count = 32;
memcpy(batch.packets, packets, 32 * sizeof(Packet));
queue.enqueue(&batch);  // 1 contentious operation
```

**Result**: 32x fewer contentious operations on shared queues.

#### Strategy 5: Reader-Optimized Data Structures

For read-heavy workloads (like flow table lookup), we optimize for readers.

```cpp
class FlowTable {
    // Option 1: RCU - readers never block
    std::atomic<FlowEntry*> buckets[NUM_BUCKETS];
    
    FlowEntry* lookup(const FlowKey& key) {
        // Readers: just an atomic load, never blocks
        FlowEntry* entry = buckets[hash(key)].load(std::memory_order_acquire);
        // ... search
    }
    
    void insert(FlowEntry* entry) {
        // Writers: use CAS, might retry but doesn't block readers
        FlowEntry* expected = nullptr;
        while (!buckets[idx].compare_exchange_weak(expected, entry)) {
            // Handle collision
        }
    }
};
```

**Read:Write ratio matters**: If 99% of operations are reads, optimizing reads (even at the cost of slower writes) is the right trade-off.

#### Strategy 6: Cache Line Alignment (Avoid False Sharing)

Even without logical sharing, cores can contend on the same cache line.

```cpp
// BAD: Adjacent counters share cache line
struct Stats {
    uint64_t core0_packets;  // Bytes 0-7
    uint64_t core1_packets;  // Bytes 8-15 - SAME CACHE LINE!
};

// GOOD: Each counter on its own cache line
struct alignas(64) CoreStats {
    uint64_t packets;
    char padding[56];  // Fill to 64 bytes
};
CoreStats stats[NUM_CORES];
```

**False sharing** causes cache line ping-pong between cores, even though they're accessing different variables.

#### Contention Avoidance Summary

| Technique | Contention Reduction | Trade-off |
|-----------|---------------------|-----------|
| Per-core partitioning | Eliminates | Memory duplication |
| Flow affinity | Eliminates for flows | Load imbalance possible |
| Lock-free structures | Minimizes impact | Complexity |
| Batching | Reduces frequency | Latency (batching delay) |
| Reader optimization (RCU) | Eliminates for reads | Complex memory reclamation |
| Cache line alignment | Eliminates false sharing | Memory usage |

### 13.3 How Work Is Partitioned Across Cores

Work partitioning is the art of dividing the total workload so that each core has roughly equal work, minimal shared state, and good cache behavior.

#### Partitioning Strategy: Hierarchical Flow Distribution

Our system uses a three-level partitioning scheme:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        LEVEL 1: NIC Hardware RSS                        │
│   NIC hashes (src_ip, dst_ip, src_port, dst_port) → RX Queue 0-N       │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
┌───────────────┐           ┌───────────────┐           ┌───────────────┐
│  RX Queue 0   │           │  RX Queue 1   │           │  RX Queue 2   │
│  (Core 0)     │           │  (Core 1)     │           │  (Core 2)     │
└───────┬───────┘           └───────┬───────┘           └───────┬───────┘
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    │
┌───────────────────────────────────┴─────────────────────────────────────┐
│                    LEVEL 2: Software Flow Hashing                        │
│   RX cores re-hash flows → Processing Core 0-M                          │
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
┌───────────────┐           ┌───────────────┐           ┌───────────────┐
│ Process Core 0│           │ Process Core 1│           │ Process Core 2│
│ Flows: A,D,G  │           │ Flows: B,E,H  │           │ Flows: C,F,I  │
└───────┬───────┘           └───────┬───────┘           └───────┬───────┘
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    │
┌───────────────────────────────────┴─────────────────────────────────────┐
│                    LEVEL 3: TX Queue Selection                          │
│   Based on output port/interface                                        │
└─────────────────────────────────────────────────────────────────────────┘
```

#### Level 1: Hardware RSS (Receive Side Scaling)

The NIC itself distributes incoming packets across multiple RX queues.

```cpp
// Configure RSS in DPDK
struct rte_eth_conf port_conf = {
    .rxmode = {
        .mq_mode = ETH_MQ_RX_RSS,
    },
    .rx_adv_conf = {
        .rss_conf = {
            .rss_key = rss_key,  // 40-byte key
            .rss_hf = ETH_RSS_IP | ETH_RSS_TCP | ETH_RSS_UDP,
        },
    },
};
```

**How it works:**
1. NIC computes hash: `hash = toeplitz(src_ip, dst_ip, src_port, dst_port)`
2. NIC selects queue: `queue = hash % num_rx_queues`
3. Packet DMA'd directly to that queue's ring buffer

**Benefits:**
- Zero CPU overhead for distribution (hardware does it)
- Flows naturally stay together (same hash → same queue)
- Perfect for 1:1 RX queue to core mapping

#### Level 2: Software Flow Distribution

RX cores may redistribute to processing cores for more flexibility.

```cpp
void rx_worker(int rx_core_id) {
    while (running) {
        // Receive from my RX queue
        nb_rx = rte_eth_rx_burst(port, rx_queue, pkts, BURST_SIZE);
        
        // Group packets by target processing core
        PacketBatch* batches[NUM_PROC_CORES] = {0};
        
        for (int i = 0; i < nb_rx; ++i) {
            ParsedPacket parsed;
            parse_packet(pkts[i], &parsed);
            
            // Determine target core based on flow hash
            int target = parsed.flow_hash % num_proc_cores;
            
            // Add to appropriate batch
            if (!batches[target]) {
                batches[target] = allocate_batch();
            }
            batches[target]->add(parsed);
        }
        
        // Enqueue batches to processing cores
        for (int c = 0; c < NUM_PROC_CORES; ++c) {
            if (batches[c]) {
                proc_queues[c].enqueue(batches[c]);
            }
        }
    }
}
```

**Why redistribute?**
- RX cores might be fewer than processing cores
- Can apply custom distribution logic (priority-based, etc.)
- Decouple RX parallelism from processing parallelism

#### Level 3: TX Queue Selection

Packets are directed to TX queues based on output interface.

```cpp
int determine_tx_queue(ParsedPacket* pkt) {
    // Option 1: Based on flow hash (load balance)
    return pkt->flow_hash % num_tx_queues;
    
    // Option 2: Based on output port (if multiple NICs)
    return pkt->output_port;
    
    // Option 3: Same as processing core (minimize cross-core traffic)
    return current_core_id;
}
```

#### Core Assignment and NUMA Awareness

```cpp
/*
 * Example: 2 NUMA nodes, 16 cores each
 * 
 * NUMA Node 0 (Cores 0-15):          NUMA Node 1 (Cores 16-31):
 *   - Cores 0-3: RX (Port 0)           - Cores 16-19: RX (Port 1)
 *   - Cores 4-11: Processing           - Cores 20-27: Processing
 *   - Cores 12-15: TX (Port 0)         - Cores 28-31: TX (Port 1)
 *   - Memory Pool 0                    - Memory Pool 1
 *   - Flow Table Shard 0               - Flow Table Shard 1
 */

struct SystemLayout {
    struct NUMANode {
        int node_id;
        std::vector<int> rx_cores;
        std::vector<int> proc_cores;
        std::vector<int> tx_cores;
        PacketPool* pool;
        FlowTableShard* flow_shard;
    };
    
    NUMANode nodes[MAX_NUMA_NODES];
};

void initialize_layout() {
    for (int node = 0; node < num_numa_nodes; ++node) {
        // Get cores on this NUMA node
        std::vector<int> node_cores = get_cores_on_numa_node(node);
        
        // Assign roles
        int idx = 0;
        for (int i = 0; i < NUM_RX_CORES_PER_NODE; ++i)
            layout.nodes[node].rx_cores.push_back(node_cores[idx++]);
        for (int i = 0; i < NUM_PROC_CORES_PER_NODE; ++i)
            layout.nodes[node].proc_cores.push_back(node_cores[idx++]);
        for (int i = 0; i < NUM_TX_CORES_PER_NODE; ++i)
            layout.nodes[node].tx_cores.push_back(node_cores[idx++]);
        
        // Allocate memory on this NUMA node
        numa_set_preferred(node);
        layout.nodes[node].pool = new PacketPool(POOL_SIZE);
        layout.nodes[node].flow_shard = new FlowTableShard(TABLE_SIZE);
    }
}
```

#### Load Balancing Considerations

**Problem**: Some flows might be "elephant flows" (very high packet rate), causing imbalance.

```
Ideal:     Core 0: 2.5M pps, Core 1: 2.5M pps, Core 2: 2.5M pps, Core 3: 2.5M pps
Actual:    Core 0: 5M pps,   Core 1: 2M pps,   Core 2: 2M pps,   Core 3: 1M pps
                    ↑
            Elephant flow!
```

**Solutions:**

**1. Work Stealing**

Overloaded cores can have work stolen by idle cores:

```cpp
PacketBatch* get_work(int my_core) {
    // Try my own queue first
    PacketBatch* batch;
    if (my_queue.try_dequeue(batch)) {
        return batch;
    }
    
    // My queue empty - try stealing from others
    for (int i = 1; i < num_cores; ++i) {
        int victim = (my_core + i) % num_cores;
        if (other_queues[victim].try_steal_from_back(batch)) {
            return batch;
        }
    }
    
    return nullptr;  // No work available
}
```

**2. Elephant Flow Detection and Splitting**

```cpp
void detect_and_handle_elephants() {
    for (auto& flow : flow_table) {
        if (flow.packet_rate > ELEPHANT_THRESHOLD) {
            // Mark for special handling
            flow.is_elephant = true;
            
            // Option: Split across multiple cores
            // (Breaks ordering - only if acceptable)
        }
    }
}
```

**3. Weighted Distribution**

```cpp
int select_processing_core(uint32_t flow_hash) {
    // Static: simple modulo
    // return flow_hash % num_cores;
    
    // Dynamic: consider current load
    int base_core = flow_hash % num_cores;
    
    if (core_load[base_core] > HIGH_LOAD_THRESHOLD) {
        // Find least loaded core
        int min_load_core = find_min_load_core();
        if (core_load[min_load_core] < core_load[base_core] * 0.7) {
            return min_load_core;
        }
    }
    
    return base_core;
}
```

#### Work Partitioning Summary

| Level | Mechanism | Granularity | Ordering |
|-------|-----------|-------------|----------|
| NIC RSS | Hardware hash | Per-packet | Per-flow preserved |
| RX→Processing | Software hash | Per-batch | Per-flow preserved |
| Processing→TX | Queue selection | Per-batch | Per-flow preserved |
| Work stealing | Queue theft | Per-batch | May break ordering |

### Q1: "How would you handle a flow table that doesn't fit in memory?"

**Answer:**

This is a common challenge in large-scale systems. Several approaches:

**1. Flow Aging/Eviction**

```cpp
class FlowTable {
    void evict_expired_flows() {
        uint64_t now = get_timestamp();
        
        for (auto& bucket : buckets) {
            FlowEntry* entry = bucket.load();
            while (entry) {
                if (now - entry->last_seen > FLOW_TIMEOUT) {
                    evict(entry);
                }
                entry = entry->next;
            }
        }
    }
};
```

Typical timeouts: TCP established = 5 minutes, UDP = 30 seconds, other = 60 seconds.

**2. LRU Eviction**

When table is full, evict least-recently-used flows:

```cpp
void insert_with_eviction(FlowEntry* new_flow) {
    if (current_size >= max_size) {
        FlowEntry* victim = lru_list.pop_oldest();
        remove(victim);
    }
    insert(new_flow);
    lru_list.touch(new_flow);
}
```

**3. Bloom Filter for Negative Caching**

Before doing expensive lookup, check a Bloom filter:

```cpp
FlowEntry* lookup(const FlowKey& key) {
    // Fast negative check - if not in Bloom filter, definitely not in table
    if (!bloom_filter.might_contain(key)) {
        return nullptr;
    }
    
    // Might be in table - do full lookup
    return full_lookup(key);
}
```

**4. Tiered Storage**

Hot flows in fast hash table, cold flows in slower storage:

```
┌─────────────────────┐
│   Hot Flow Cache    │ ← Fast (hash table in RAM)
│    (10K flows)      │
└──────────┬──────────┘
           │ Miss
           ▼
┌─────────────────────┐
│  Warm Flow Table    │ ← Medium (larger hash table)
│   (100K flows)      │
└──────────┬──────────┘
           │ Miss
           ▼
┌─────────────────────┐
│  Cold Flow Store    │ ← Slow (memory-mapped file or SSD)
│    (1M+ flows)      │
└─────────────────────┘
```

### Q2: "What happens if a processing core crashes?"

**Answer:**

We need to design for graceful degradation:

**1. Detection**

```cpp
void health_monitor_thread() {
    while (running) {
        for (int i = 0; i < num_cores; ++i) {
            uint64_t last_heartbeat = core_heartbeats[i].load();
            uint64_t now = get_timestamp_ns();
            
            if (now - last_heartbeat > HEARTBEAT_TIMEOUT_NS) {
                handle_core_failure(i);
            }
        }
        sleep_ms(HEALTH_CHECK_INTERVAL_MS);
    }
}
```

**2. Work Redistribution**

```cpp
void handle_core_failure(int failed_core) {
    log_error("Core {} failed, redistributing work", failed_core);
    
    // Stop sending new work to failed core
    core_active[failed_core] = false;
    
    // Drain failed core's queue to other cores
    PacketBatch* batch;
    while (proc_queues[failed_core].try_dequeue(batch)) {
        int new_target = select_healthy_core(batch->flow_hash);
        proc_queues[new_target].enqueue(batch);
    }
    
    // Update flow affinity - rehash to remaining cores
    redistribute_flows(failed_core);
    
    // Alert operations team
    send_alert("Core failure", failed_core);
}
```

**3. Flow State Recovery**

Flows owned by the failed core need their state migrated:

```cpp
void redistribute_flows(int failed_core) {
    for (auto& flow : flow_table) {
        if (flow.owning_core == failed_core) {
            // Recalculate owner among healthy cores
            flow.owning_core = rehash_flow(flow.key, active_cores);
        }
    }
}
```

**4. Capacity Planning**

Design with N+1 or N+2 redundancy. If you need 10 cores for 10M pps, deploy 12 cores so 2 can fail without impacting throughput.

### Q3: "How would you add encryption (TLS/IPsec) to the pipeline?"

**Answer:**

Encryption is CPU-intensive and changes the architecture significantly:

**1. Hardware Offload (Preferred)**

Modern NICs support inline encryption:

```cpp
// Configure IPsec offload in DPDK
struct rte_security_session_conf sess_conf = {
    .action_type = RTE_SECURITY_ACTION_TYPE_INLINE_CRYPTO,
    .protocol = RTE_SECURITY_PROTOCOL_IPSEC,
    .ipsec = {
        .mode = RTE_SECURITY_IPSEC_SA_MODE_TUNNEL,
        .proto = RTE_SECURITY_IPSEC_SA_PROTO_ESP,
        // ... crypto algorithms
    },
};
```

With hardware offload, encryption happens in the NIC with minimal CPU impact.

**2. Dedicated Crypto Cores**

If hardware offload isn't available, dedicate specific cores to encryption:

```
RX → Parse → Classify → [Crypto Cores] → Transform → TX
                              │
                    ┌─────────┴─────────┐
                    │ Cores 8-11:       │
                    │ AES-GCM encrypt   │
                    │ (CPU-intensive)   │
                    └───────────────────┘
```

**3. Async Crypto with Look-Ahead**

Use Intel QAT or similar:

```cpp
void crypto_worker() {
    while (running) {
        // Dequeue batch needing encryption
        PacketBatch* batch = crypto_queue.dequeue();
        
        // Submit all to crypto accelerator
        for (auto& pkt : batch->packets) {
            submit_async_encrypt(pkt.payload, pkt.length, &pkt.crypto_op);
        }
        
        // Poll for completions
        while (batch->pending_ops > 0) {
            int completed = poll_crypto_completions(completions, MAX_POLL);
            batch->pending_ops -= completed;
        }
        
        // Forward completed batch
        tx_queue.enqueue(batch);
    }
}
```

**4. Performance Impact**

AES-GCM in software: ~2-5 Gbps per core (depending on packet size)

For 40 Gbps line rate, you'd need 8-20 cores just for crypto. This is why hardware offload is essential for high-speed encrypted traffic.

### Q4: "How do you handle packet reordering?"

**Answer:**

Reordering is problematic for TCP (causes retransmissions) and some UDP applications.

**1. Preserve Ordering with Flow Affinity**

Our design already preserves ordering by sending all packets from a flow to the same core:

```cpp
// All packets with same flow_hash go to same core
int target = flow_hash % num_cores;
```

As long as packets enter and exit a single-threaded processing path, ordering is preserved.

**2. Sequence Tracking (When Needed)**

If ordering might be disrupted (e.g., work stealing), add sequence numbers:

```cpp
struct PacketMetadata {
    uint64_t sequence;  // Per-flow sequence number
    uint32_t flow_id;
};

class Reorderer {
    std::map<uint32_t, uint64_t> expected_seq;  // Per-flow
    std::map<uint32_t, std::priority_queue<Packet>> held;  // Out-of-order packets
    
    void handle_packet(Packet& pkt) {
        if (pkt.sequence == expected_seq[pkt.flow_id]) {
            // In order - process immediately
            forward(pkt);
            expected_seq[pkt.flow_id]++;
            
            // Release any held packets that are now in order
            release_held(pkt.flow_id);
        } else {
            // Out of order - hold
            held[pkt.flow_id].push(pkt);
            
            // Timeout: release after max delay
            schedule_release(pkt.flow_id, MAX_REORDER_DELAY);
        }
    }
};
```

**3. Accept Reordering (UDP/Stateless)**

For stateless processing or UDP traffic that tolerates reordering, skip the complexity:

```cpp
if (can_reorder(pkt)) {
    // Process without ordering guarantees - faster
    process_stateless(pkt);
} else {
    // Must preserve order
    process_with_ordering(pkt);
}
```

```cpp
        auto end = rdtsc();
        
        uint64_t cycles = end - start;
        histogram.record(cycles_to_ns(cycles));
    }
    
    std::cout << "P50 latency: " << histogram.percentile(50) << " ns\n";
    std::cout << "P99 latency: " << histogram.percentile(99) << " ns\n";
    std::cout << "P99.9 latency: " << histogram.percentile(99.9) << " ns\n";
}
```

**6. Stress Tests**

- Run at 120% of target rate to find breaking points
- Inject failures (kill cores, corrupt packets, exhaust memory)
- Long-duration tests (24-72 hours) to find memory leaks

### Q7: "How would this design change for 100M pps?"

**Answer:**

At 100M pps (10ns per packet, ~20-40 CPU cycles), we're pushing the limits of what's possible even with DPDK:

**1. Hardware Offload Becomes Mandatory**

Move more processing to the NIC:
- Flow classification in NIC hardware
- Header parsing in NIC
- Simple transformations (VLAN push/pop) in NIC

```cpp
// Use rte_flow for hardware-accelerated flow matching
struct rte_flow_attr attr = {
    .ingress = 1,
};

struct rte_flow_item pattern[] = {
    { .type = RTE_FLOW_ITEM_TYPE_IPV4, .spec = &ipv4_spec },
    { .type = RTE_FLOW_ITEM_TYPE_TCP, .spec = &tcp_spec },
    { .type = RTE_FLOW_ITEM_TYPE_END },
};

struct rte_flow_action actions[] = {
    { .type = RTE_FLOW_ACTION_TYPE_QUEUE, .conf = &queue_action },
    { .type = RTE_FLOW_ACTION_TYPE_END },
};

rte_flow_create(port_id, &attr, pattern, actions, &error);
```

**2. Multiple NICs**

Single NIC might not handle 100M pps. Use multiple:
- 4x 40GbE NICs, each handling 25M pps
- Or 2x 100GbE NICs

**3. Extreme Batching**

Increase batch sizes to amortize overhead:

```cpp
#define BURST_SIZE 256  // Instead of 32
```

**4. Simplified Processing**

Remove any processing that isn't absolutely necessary:
- Skip full parsing; extract only needed fields
- Use table lookups instead of computation
- Eliminate all conditional branches if possible

**5. SmartNIC / DPU**

Offload entire pipeline to a Data Processing Unit:
- NVIDIA BlueField
- Intel IPU
- AMD Pensando

These have dedicated ARM cores and custom ASICs for packet processing.

**6. FPGA Acceleration**

For ultimate performance, implement critical path in FPGA:
- Xilinx Alveo NICs
- Intel PAC

FPGAs can process 1 packet per clock cycle (hundreds of Mpps).

### Q8: "Compare this to how cloud providers handle similar problems."

**Key Patterns:**

2. **Kernel Bypass**: SR-IOV, DPDK-like techniques
3. **Hardware Offload**: Encryption, encapsulation, flow tracking
4. **Disaggregated Architecture**: Separate networking from compute

## Summary of Key Interview Points

When discussing this design, emphasize:

1. **Locks are avoided on the fast path** through per-core partitioning, lock-free data structures, and flow affinity

2. **Contention is minimized** by partitioning data, using batching, and carefully aligning cache lines

3. **Work is partitioned hierarchically** using hardware RSS, software hashing, and NUMA-aware assignment

4. **Trade-offs are explicit**: We trade memory (duplication) and complexity (lock-free code) for throughput

5. **Measurement is critical**: At this scale, you must measure everything—assumptions are dangerous

6. **Hardware matters**: At extreme performance levels, software optimization isn't enough; hardware offload is required
