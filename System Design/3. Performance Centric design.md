# Performance-Centric Design in C++

## Introduction

Performance-centric design is about making conscious architectural decisions that optimize for speed, latency, and throughput from the ground up. Unlike premature optimization of micro-details, this involves understanding how modern hardware works and structuring your code to work *with* the hardware rather than against it.

This document covers five critical concepts that separate high-performance systems from ordinary code.

## 1. Hot Path vs Cold Path

### What Are Hot and Cold Paths?

**Hot Path**: The code that executes most frequently—the "fast path" that handles the common case. This is where 90%+ of your execution time is spent.

**Cold Path**: The code that executes rarely—error handling, edge cases, configuration changes, startup/shutdown. This might be executed once per million operations.

```
┌─────────────────────────────────────────────────────────────────┐
│                    REQUEST PROCESSING                            │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │  Valid Request? │
                    └────────┬────────┘
                             │
           ┌─────────────────┴─────────────────┐
           │ YES (99.9%)                       │ NO (0.1%)
           ▼                                   ▼
    ┌──────────────┐                   ┌──────────────┐
    │   HOT PATH   │                   │  COLD PATH   │
    │              │                   │              │
    │ • Fast       │                   │ • Slow OK    │
    │ • Optimized  │                   │ • Readable   │
    │ • Inlined    │                   │ • Detailed   │
    │ • No allocs  │                   │ • Logging    │
    └──────────────┘                   └──────────────┘
```

### Why This Matters

The Pareto Principle applies to code: **20% of your code runs 80% of the time** (often more extreme: 1% runs 99% of the time).

| Optimization Target | Impact |
|---------------------|--------|
| Hot path (1% of code) | 90%+ of performance gains |
| Cold path (99% of code) | <10% of performance gains |

**Key Insight**: You should optimize ruthlessly on the hot path, and prioritize readability/maintainability on the cold path.

### Identifying Hot and Cold Paths

**Use profilers to find hot paths:**
```bash
# Linux perf
perf record -g ./your_program
perf report

# Valgrind/Callgrind
valgrind --tool=callgrind ./your_program
kcachegrind callgrind.out.*

# Google's gperftools
CPUPROFILE=profile.out ./your_program
pprof --text ./your_program profile.out
```

**Common hot paths in systems:**
- Packet/message processing loops
- Database query execution
- Serialization/deserialization
- Hash table lookups
- Memory allocation (if not pooled)

### Designing for Hot/Cold Separation

#### Technique 1: Move Cold Code Out of Line

```cpp
// BAD: Cold code (error handling) pollutes the hot path
void process_message(const Message& msg) {
    if (!validate_header(msg)) {
        // Error handling bloats the hot function
        log_error("Invalid header");
        increment_counter(INVALID_HEADER);
        notify_monitoring_system(msg);
        throw InvalidMessageException(msg);
    }
    
    // Hot path continues...
    parse_payload(msg);
    route_message(msg);
}

// GOOD: Cold code moved to separate function
void process_message(const Message& msg) {
    if (!validate_header(msg)) [[unlikely]] {
        handle_invalid_header(msg);  // Cold - don't inline
        return;
    }
    
    // Hot path is tight and focused
    parse_payload(msg);
    route_message(msg);
}

// Mark as noinline to keep it out of hot path
[[gnu::noinline]] void handle_invalid_header(const Message& msg) {
    log_error("Invalid header");
    increment_counter(INVALID_HEADER);
    notify_monitoring_system(msg);
    throw InvalidMessageException(msg);
}
```

#### Technique 2: Use `[[likely]]` and `[[unlikely]]` (C++20)

```cpp
void process_order(const Order& order) {
    if (order.is_valid()) [[likely]] {
        // Hot path - compiler optimizes for this
        execute_order(order);
    } else [[unlikely]] {
        // Cold path - compiler deprioritizes this
        reject_order(order);
    }
}
```

#### Technique 3: Template Specialization for Hot Cases

```cpp
// Generic handler for any message type
template<MessageType T>
void handle_message(const Message& msg) {
    // General implementation
}

// Specialized hot-path handler for the most common type
template<>
void handle_message<MessageType::TRADE>(const Message& msg) {
    // Highly optimized implementation for trades
    // This is the hot path - 80% of all messages
}
```

#### Technique 4: Separate Hot and Cold Data

```cpp
// BAD: Cold data mixed with hot data
struct Connection {
    // Hot data (accessed every packet)
    int socket_fd;
    uint32_t sequence_number;
    
    // Cold data (accessed rarely)
    std::string client_name;
    std::string client_address;
    std::vector<std::string> connection_history;
    std::chrono::time_point<std::chrono::system_clock> connected_at;
};

// GOOD: Separate hot and cold data
struct ConnectionHot {
    int socket_fd;
    uint32_t sequence_number;
    ConnectionCold* cold_data;  // Pointer to cold data
};

struct ConnectionCold {
    std::string client_name;
    std::string client_address;
    std::vector<std::string> connection_history;
    std::chrono::time_point<std::chrono::system_clock> connected_at;
};
```

This keeps the hot data compact, improving cache utilization.

### Real-World Example: Packet Router

```cpp
class PacketRouter {
public:
    void route_packet(Packet* pkt) {
        // === HOT PATH START ===
        
        // Fast hash lookup for known flows (99% of packets)
        uint32_t flow_id = compute_flow_hash(pkt);
        auto* entry = flow_table_.lookup(flow_id);
        
        if (entry) [[likely]] {
            // Direct forwarding - most common case
            forward_to_port(pkt, entry->output_port);
            return;
        }
        
        // === HOT PATH END ===
        
        // Cold path: unknown flow, need to do full classification
        handle_unknown_flow(pkt);
    }

private:
    // Keep in hot path - called for every packet
    inline void forward_to_port(Packet* pkt, int port) {
        output_queues_[port].enqueue(pkt);
    }
    
    // Cold path - don't inline, don't optimize aggressively
    [[gnu::noinline]] [[gnu::cold]]
    void handle_unknown_flow(Packet* pkt) {
        // Expensive classification
        auto classification = classify_packet(pkt);
        
        // Install new flow entry
        FlowEntry entry;
        entry.output_port = compute_output_port(classification);
        flow_table_.insert(compute_flow_hash(pkt), entry);
        
        // Log for debugging
        log_new_flow(pkt, classification);
        
        // Finally forward
        forward_to_port(pkt, entry.output_port);
    }
};
```

## 2. Branch Prediction & Cache Locality

### Understanding Modern CPU Architecture

Modern CPUs are **pipelined** and **superscalar**, meaning they:
1. Execute multiple instructions simultaneously
2. Start executing future instructions before current ones complete
3. **Predict** which branch will be taken and speculatively execute

```
Traditional Execution:
  Fetch → Decode → Execute → Memory → Writeback
    │        │         │         │         │
   Inst 1   Inst 1    Inst 1    Inst 1    Inst 1
            Inst 2    Inst 2    Inst 2    Inst 2
                      Inst 3    Inst 3    Inst 3

Pipeline keeps all stages busy simultaneously!
```

### Branch Prediction

**The Problem**: When the CPU encounters a branch (if/else, loop condition), it doesn't know which path to take until the condition is evaluated. But it can't wait—it needs to keep the pipeline full.

**The Solution**: Branch predictor—a hardware unit that guesses which way branches will go.

```
if (condition) {
    path_a();  // Prediction: condition is true
} else {
    path_b();
}
```

**Branch Misprediction Cost**: 10-20 CPU cycles flushed

At 3 GHz, that's **3-7 nanoseconds** wasted per misprediction.

### How Branch Predictors Work

Modern branch predictors are sophisticated, using:

1. **Static Prediction**: Backward branches (loops) predicted taken, forward branches predicted not taken
2. **Dynamic Prediction**: History-based, learns from previous executions
3. **Two-Level Adaptive**: Tracks patterns (e.g., TTTNTTTN...)

| Pattern | Prediction Accuracy |
|---------|---------------------|
| Always true | ~100% |
| Always false | ~100% |
| Alternating (T,F,T,F) | ~100% (pattern detected) |
| Random 50/50 | ~50% (worst case!) |

### Writing Branch-Prediction-Friendly Code

#### Technique 1: Sort Data to Create Predictable Patterns

```cpp
// BAD: Random access pattern - 50% misprediction rate
void sum_large_values(const std::vector<int>& data) {
    int sum = 0;
    for (int x : data) {
        if (x > threshold) {  // Unpredictable!
            sum += x;
        }
    }
    return sum;
}

// GOOD: Sort first - branches become predictable
void sum_large_values_fast(std::vector<int>& data) {
    std::sort(data.begin(), data.end());
    
    int sum = 0;
    for (int x : data) {
        if (x > threshold) {  // Predictable! All false, then all true
            sum += x;
        }
    }
    return sum;
}
```

**Real benchmark** (from Stack Overflow's famous question):
- Unsorted: ~11 seconds
- Sorted: ~2 seconds (5x faster!)

#### Technique 2: Replace Branches with Arithmetic

```cpp
// BAD: Branch
int max_branched(int a, int b) {
    if (a > b) return a;
    else return b;
}

// GOOD: Branchless (compiler may do this automatically)
int max_branchless(int a, int b) {
    return a ^ ((a ^ b) & -(a < b));
}

// Or use the conditional move that compilers generate:
int max_cmov(int a, int b) {
    return (a > b) ? a : b;  // Compiler uses CMOV instruction
}
```

#### Technique 3: Use Lookup Tables Instead of Switches

```cpp
// BAD: Many branches
int get_priority(MessageType type) {
    switch (type) {
        case MessageType::HEARTBEAT: return 0;
        case MessageType::STATUS: return 1;
        case MessageType::DATA: return 2;
        case MessageType::CONTROL: return 3;
        case MessageType::URGENT: return 4;
        default: return -1;
    }
}

// GOOD: Table lookup - no branches
constexpr int PRIORITY_TABLE[] = {0, 1, 2, 3, 4};

int get_priority_fast(MessageType type) {
    auto idx = static_cast<size_t>(type);
    return (idx < std::size(PRIORITY_TABLE)) 
           ? PRIORITY_TABLE[idx] 
           : -1;
}
```

#### Technique 4: Use `[[likely]]`/`[[unlikely]]` Hints

```cpp
void process(Event& e) {
    if (e.type == EventType::DATA) [[likely]] {
        // Compiler arranges code so this path is predicted
        handle_data(e);
    } else [[unlikely]] {
        handle_other(e);
    }
}
```

### Cache Locality

**The Memory Hierarchy**:

```
┌─────────────────────────────────────────────────────────────┐
│                      CPU REGISTERS                          │
│                    Access: < 1 ns                           │
│                    Size: ~1 KB                              │
├─────────────────────────────────────────────────────────────┤
│                      L1 CACHE                               │
│                    Access: ~1 ns (3-4 cycles)              │
│                    Size: 32-64 KB per core                  │
├─────────────────────────────────────────────────────────────┤
│                      L2 CACHE                               │
│                    Access: ~3-10 ns (10-20 cycles)         │
│                    Size: 256-512 KB per core                │
├─────────────────────────────────────────────────────────────┤
│                      L3 CACHE                               │
│                    Access: ~10-40 ns (40-75 cycles)        │
│                    Size: 8-64 MB shared                     │
├─────────────────────────────────────────────────────────────┤
│                      MAIN MEMORY (RAM)                      │
│                    Access: ~60-100 ns (200+ cycles)        │
│                    Size: 16-512 GB                          │
└─────────────────────────────────────────────────────────────┘
```

**Key Insight**: L1 cache hit is **100x faster** than main memory access.

### Types of Cache Locality

**Temporal Locality**: If you access data now, you'll likely access it again soon.
```cpp
// GOOD temporal locality
for (int i = 0; i < 1000; ++i) {
    sum += data[0];  // Same address accessed repeatedly
}
```

**Spatial Locality**: If you access data at address X, you'll likely access X+1, X+2, etc.
```cpp
// GOOD spatial locality
for (int i = 0; i < N; ++i) {
    sum += array[i];  // Sequential access
}

// BAD spatial locality
for (int i = 0; i < N; ++i) {
    sum += array[random_index()];  // Random access
}
```

### Cache Lines

Memory is loaded in **cache lines** (typically 64 bytes on x86).

```
Cache Line (64 bytes):
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │
└────┴────┴────┴────┴────┴────┴────┴────┘

When you access array[0], the CPU loads array[0] through array[7] (if 8-byte elements)
```

### Cache-Friendly Patterns

#### Technique 1: Sequential Access

```cpp
// GOOD: Sequential access - ~1 cache miss per 8 elements
for (int i = 0; i < N; ++i) {
    process(array[i]);
}

// BAD: Strided access - more cache misses
for (int i = 0; i < N; i += 16) {
    process(array[i]);  // Skip 15 elements each time
}

// TERRIBLE: Random access - cache miss on almost every access
for (int i = 0; i < N; ++i) {
    process(array[random_indices[i]]);
}
```

#### Technique 2: Avoid Pointer Chasing

```cpp
// BAD: Linked list - pointer chasing, terrible cache behavior
struct Node {
    int data;
    Node* next;  // Could be anywhere in memory!
};

void sum_linked_list(Node* head) {
    int sum = 0;
    for (Node* p = head; p; p = p->next) {
        sum += p->data;  // Cache miss on every node
    }
    return sum;
}

// GOOD: Contiguous array
void sum_array(const std::vector<int>& data) {
    int sum = 0;
    for (int x : data) {
        sum += x;  // Great cache behavior
    }
    return sum;
}
```

**Benchmark comparison**:
- Linked list traversal: ~100 ns per element (cache misses)
- Array traversal: ~0.3 ns per element (cache hits)

That's **300x faster**!

#### Technique 3: Prefetching

Tell the CPU to load data before you need it:

```cpp
void process_array(int* data, size_t N) {
    constexpr size_t PREFETCH_DISTANCE = 8;  // 8 cache lines ahead
    
    for (size_t i = 0; i < N; ++i) {
        // Prefetch future data
        if (i + PREFETCH_DISTANCE * 8 < N) {
            __builtin_prefetch(&data[i + PREFETCH_DISTANCE * 8], 0, 3);
        }
        
        process(data[i]);
    }
}
```

#### Technique 4: Block/Tile Processing for Matrices

```cpp
// BAD: Column-major access of row-major array
for (int j = 0; j < N; ++j) {
    for (int i = 0; i < N; ++i) {
        sum += matrix[i][j];  // Stride of N elements - terrible!
    }
}

// GOOD: Row-major access of row-major array
for (int i = 0; i < N; ++i) {
    for (int j = 0; j < N; ++j) {
        sum += matrix[i][j];  // Sequential access
    }
}

// BETTER: Block processing for matrix multiplication
constexpr size_t BLOCK_SIZE = 64;  // Fits in L1 cache

void matrix_multiply_blocked(float* A, float* B, float* C, size_t N) {
    for (size_t i0 = 0; i0 < N; i0 += BLOCK_SIZE) {
        for (size_t j0 = 0; j0 < N; j0 += BLOCK_SIZE) {
            for (size_t k0 = 0; k0 < N; k0 += BLOCK_SIZE) {
                // Process block - all data fits in cache
                for (size_t i = i0; i < std::min(i0 + BLOCK_SIZE, N); ++i) {
                    for (size_t j = j0; j < std::min(j0 + BLOCK_SIZE, N); ++j) {
                        float sum = C[i * N + j];
                        for (size_t k = k0; k < std::min(k0 + BLOCK_SIZE, N); ++k) {
                            sum += A[i * N + k] * B[k * N + j];
                        }
                        C[i * N + j] = sum;
                    }
                }
            }
        }
    }
}
```

## 3. Memory Layout: SoA vs AoS

### Array of Structures (AoS)

The traditional, object-oriented approach:

```cpp
// AoS: Each particle is a contiguous object
struct Particle {
    float x, y, z;      // Position (12 bytes)
    float vx, vy, vz;   // Velocity (12 bytes)
    float mass;         // Mass (4 bytes)
    int id;             // ID (4 bytes)
};  // Total: 32 bytes

std::vector<Particle> particles(N);

// Memory layout:
// [x,y,z,vx,vy,vz,mass,id] [x,y,z,vx,vy,vz,mass,id] [x,y,z,vx,vy,vz,mass,id]
//        Particle 0              Particle 1              Particle 2
```

### Structure of Arrays (SoA)

The data-oriented approach:

```cpp
// SoA: Each property is a contiguous array
struct Particles {
    std::vector<float> x, y, z;      // Positions
    std::vector<float> vx, vy, vz;   // Velocities
    std::vector<float> mass;         // Masses
    std::vector<int> id;             // IDs
    
    size_t size() const { return x.size(); }
    
    void resize(size_t n) {
        x.resize(n); y.resize(n); z.resize(n);
        vx.resize(n); vy.resize(n); vz.resize(n);
        mass.resize(n); id.resize(n);
    }
};

Particles particles;
particles.resize(N);

// Memory layout:
// [x0, x1, x2, ...] [y0, y1, y2, ...] [z0, z1, z2, ...] [vx0, vx1, vx2, ...]
//     All X             All Y             All Z             All VX
```

### Visual Comparison

```
AoS Memory Layout:
┌───────────────────────────────────────────────────────────────────────────┐
│ P0: x,y,z,vx,vy,vz,m,id │ P1: x,y,z,vx,vy,vz,m,id │ P2: x,y,z,vx,vy,vz,m,id │
└───────────────────────────────────────────────────────────────────────────┘
   └── 32 bytes ──┘          └── 32 bytes ──┘          └── 32 bytes ──┘

SoA Memory Layout:
┌─────────────────────────┬─────────────────────────┬─────────────────────────┐
│      All X values       │      All Y values       │      All Z values       │
│   x0, x1, x2, x3, ...   │   y0, y1, y2, y3, ...   │   z0, z1, z2, z3, ...   │
└─────────────────────────┴─────────────────────────┴─────────────────────────┘
```

### When SoA Wins: Streaming Operations

When you process one or two fields across all elements:

```cpp
// Update all X positions by their X velocities

// AoS: Loads 32 bytes per particle, uses only 8 bytes (25% utilization)
void update_positions_aos(std::vector<Particle>& particles, float dt) {
    for (auto& p : particles) {
        p.x += p.vx * dt;  // Cache line loads: x,y,z,vx,vy,vz,mass,id
    }                      // Only x and vx are used!
}

// SoA: Loads only the data needed (100% utilization)
void update_positions_soa(Particles& p, float dt) {
    for (size_t i = 0; i < p.size(); ++i) {
        p.x[i] += p.vx[i] * dt;  // Only loads x[] and vx[] arrays
    }
}
```

**Cache efficiency comparison**:

| Layout | Data Loaded | Data Used | Efficiency |
|--------|-------------|-----------|------------|
| AoS | 32 bytes/particle | 8 bytes | 25% |
| SoA | 8 bytes/particle | 8 bytes | 100% |

**SoA can be 4x faster** for this operation!

### When SoA Wins: SIMD Vectorization

SoA enables SIMD (Single Instruction, Multiple Data) processing:

```cpp
// SoA + SIMD: Process 8 particles at once with AVX
#include <immintrin.h>

void update_positions_simd(Particles& p, float dt) {
    __m256 dt_vec = _mm256_set1_ps(dt);
    
    for (size_t i = 0; i < p.size(); i += 8) {
        // Load 8 x values
        __m256 x = _mm256_loadu_ps(&p.x[i]);
        // Load 8 vx values
        __m256 vx = _mm256_loadu_ps(&p.vx[i]);
        
        // x += vx * dt (8 particles at once!)
        x = _mm256_fmadd_ps(vx, dt_vec, x);
        
        // Store 8 results
        _mm256_storeu_ps(&p.x[i], x);
    }
}
```

This is **8x throughput** compared to scalar processing!

### When AoS Wins: Entity-Centric Operations

When you frequently access all fields of one entity:

```cpp
// Render a single particle - need all its data
void render_particle_aos(const Particle& p) {
    // All data in one cache line (or two)
    draw_sphere(p.x, p.y, p.z, p.mass);
    draw_velocity_arrow(p.x, p.y, p.z, p.vx, p.vy, p.vz);
}

void render_particle_soa(const Particles& p, size_t i) {
    // Data scattered across 8 different arrays!
    draw_sphere(p.x[i], p.y[i], p.z[i], p.mass[i]);
    draw_velocity_arrow(p.x[i], p.y[i], p.z[i], 
                        p.vx[i], p.vy[i], p.vz[i]);
}
```

### Hybrid Approach: AoSoA (Array of Structures of Arrays)

Best of both worlds for some use cases:

```cpp
// AoSoA: Group 8 particles together (fits SIMD width)
struct ParticleBlock {
    // 8 particles' worth of each field
    float x[8], y[8], z[8];
    float vx[8], vy[8], vz[8];
    float mass[8];
    int id[8];
};

std::vector<ParticleBlock> particle_blocks(N / 8);

// Memory layout:
// [8x's, 8y's, 8z's, 8vx's, ...] [8x's, 8y's, 8z's, 8vx's, ...] ...
//        Block 0                         Block 1
```

**Benefits**:
- SIMD-friendly (8 floats = 256 bits = AVX register)
- Better cache locality than pure SoA
- Entity data still reasonably close together

### Decision Matrix

| Access Pattern | Best Layout |
|----------------|-------------|
| Process 1-2 fields across all entities | **SoA** |
| SIMD vectorization | **SoA** or **AoSoA** |
| Access all fields of one entity | **AoS** |
| Random access to single entities | **AoS** |
| Mixed access patterns | **AoSoA** |

### Real-World Example: Game Engine ECS

Entity Component System (ECS) architectures often use SoA:

```cpp
// Components stored in SoA fashion
class World {
    // Position components (SoA)
    std::vector<float> position_x;
    std::vector<float> position_y;
    std::vector<float> position_z;
    
    // Velocity components (SoA)
    std::vector<float> velocity_x;
    std::vector<float> velocity_y;
    std::vector<float> velocity_z;
    
    // Health components (SoA)
    std::vector<int> health;
    
    // Not all entities have all components - use bitmask
    std::vector<uint64_t> component_mask;
    
public:
    // System that processes position + velocity
    void physics_system(float dt) {
        for (size_t i = 0; i < entity_count; ++i) {
            if (has_components(i, POSITION | VELOCITY)) {
                position_x[i] += velocity_x[i] * dt;
                position_y[i] += velocity_y[i] * dt;
                position_z[i] += velocity_z[i] * dt;
            }
        }
    }
};
```

## 4. Avoiding Virtual Calls in Hot Paths

### The Cost of Virtual Functions

Virtual function calls have overhead:

1. **Pointer indirection**: Load vtable pointer from object
2. **Table lookup**: Load function pointer from vtable
3. **Indirect call**: Call through function pointer
4. **No inlining**: Compiler can't inline virtual calls (usually)

```
Regular Function Call:
    call process_data     ; Direct call, address known at compile time

Virtual Function Call:
    mov rax, [rdi]        ; Load vtable pointer from object
    mov rax, [rax + 16]   ; Load function pointer from vtable slot
    call rax              ; Indirect call through register
```

### Cost Analysis

| Call Type | Approximate Cost |
|-----------|------------------|
| Inlined function | 0 ns (code embedded) |
| Direct function call | 1-2 ns |
| Virtual function call | 5-15 ns |
| Virtual call (cache miss on vtable) | 50-100 ns |

At 10M calls/second, virtual calls add **50-150 ms overhead** compared to inlined code.

### Why Virtual Calls Prevent Inlining

```cpp
class Handler {
public:
    virtual void process(Data& d) = 0;
};

void hot_loop(Handler* h, std::vector<Data>& items) {
    for (auto& d : items) {
        h->process(d);  // Compiler doesn't know which process() to call
                        // Can't inline - could be any derived class!
    }
}
```

### Technique 1: CRTP (Curiously Recurring Template Pattern)

Static polymorphism - resolved at compile time:

```cpp
// Base class template
template<typename Derived>
class Handler {
public:
    void process(Data& d) {
        // Call derived class implementation - known at compile time!
        static_cast<Derived*>(this)->process_impl(d);
    }
};

// Derived class
class FastHandler : public Handler<FastHandler> {
public:
    void process_impl(Data& d) {
        // Actual implementation - can be inlined!
        d.value *= 2;
    }
};

// Usage - compiler knows exact type
template<typename H>
void hot_loop(H& handler, std::vector<Data>& items) {
    for (auto& d : items) {
        handler.process(d);  // Inlined! No virtual call.
    }
}
```

### Technique 2: std::variant + std::visit

Replace inheritance hierarchy with variant:

```cpp
// Instead of virtual handler hierarchy
class TextProcessor { 
public:
    void process(std::string& s) { /* ... */ }
};

class JsonProcessor { 
public:
    void process(std::string& s) { /* ... */ }
};

class XmlProcessor { 
public:
    void process(std::string& s) { /* ... */ }
};

// Use variant
using Processor = std::variant<TextProcessor, JsonProcessor, XmlProcessor>;

void hot_loop(Processor& proc, std::vector<std::string>& items) {
    for (auto& s : items) {
        std::visit([&s](auto& p) { 
            p.process(s);  // Compiler generates switch, can inline each case
        }, proc);
    }
}
```

**Advantage**: `std::visit` generates a switch statement or jump table - can be faster than vtable lookup and allows inlining.

### Technique 3: Type Erasure with Manual Dispatch

Hand-craft the vtable for minimal overhead:

```cpp
class FastCallback {
    using FnPtr = void(*)(void*, Data&);
    
    void* object_;
    FnPtr function_;
    
public:
    template<typename T>
    FastCallback(T& obj) 
        : object_(&obj)
        , function_([](void* o, Data& d) {
            static_cast<T*>(o)->process(d);
          })
    {}
    
    void invoke(Data& d) {
        function_(object_, d);  // Single indirection, no vtable
    }
};
```

### Technique 4: Devirtualization via Final

Help the compiler devirtualize:

```cpp
class BaseHandler {
public:
    virtual void process(Data& d) = 0;
};

// Mark as final - compiler knows no further derivation
class ConcreteHandler final : public BaseHandler {
public:
    void process(Data& d) override {
        d.value *= 2;
    }
};

void hot_loop(ConcreteHandler& h, std::vector<Data>& items) {
    for (auto& d : items) {
        h.process(d);  // Compiler can devirtualize - knows exact type!
    }
}
```

### Technique 5: Template-Based Strategy Pattern

```cpp
// Traditional (virtual) strategy
class Strategy {
public:
    virtual int compute(int x) = 0;
};

class DoubleStrategy : public Strategy {
public:
    int compute(int x) override { return x * 2; }
};

// Template-based strategy (no virtual)
template<typename Strategy>
class Processor {
    Strategy strategy_;
    
public:
    void process(std::vector<int>& data) {
        for (int& x : data) {
            x = strategy_.compute(x);  // Inlined!
        }
    }
};

// Usage
struct DoubleStrategyFast {
    int compute(int x) { return x * 2; }
};

Processor<DoubleStrategyFast> proc;
proc.process(data);
```

### Technique 6: Hoist Virtual Calls Out of Loops

If you must use virtual calls, call once, not N times:

```cpp
// BAD: Virtual call per element
void process_all_bad(Handler* h, std::vector<Data>& items) {
    for (auto& d : items) {
        h->process(d);  // N virtual calls
    }
}

// GOOD: Virtual call once, loop inside
class Handler {
public:
    virtual void process_batch(std::vector<Data>& items) = 0;
};

class ConcreteHandler : public Handler {
public:
    void process_batch(std::vector<Data>& items) override {
        for (auto& d : items) {
            d.value *= 2;  // Tight loop, no virtual calls inside
        }
    }
};

void process_all_good(Handler* h, std::vector<Data>& items) {
    h->process_batch(items);  // 1 virtual call total
}
```

### Benchmark: Virtual vs Non-Virtual

```cpp

#include <vector>
#include <iostream>

struct Data { int value; };

// Virtual version
class VirtualProcessor {
public:
    virtual void process(Data& d) { d.value *= 2; }

// Non-virtual version
struct DirectProcessor {

// CRTP version
template<typename Derived>
class CRTPBase {
public:

    }
};

class CRTPProcessor : public CRTPBase<CRTPProcessor> {
public:
    void process_impl(Data& d) { d.value *= 2; }
};

int main() {
    constexpr size_t N = 100'000'000;
    std::vector<Data> data(N, {1});
    
    // Virtual
    {
        VirtualProcessor proc;
        VirtualProcessor* ptr = &proc;  // Pointer to prevent devirtualization

        for (auto& d : data) ptr->process(d);
        auto end = std::chrono::high_resolution_clock::now();

    }
    
    // Direct
    {
        DirectProcessor proc;
        
        auto start = std::chrono::high_resolution_clock::now();
        for (auto& d : data) proc.process(d);
        auto end = std::chrono::high_resolution_clock::now();
        
        auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(end - start);
        std::cout << "Direct: " << ms.count() << " ms\n";
    }
    
    // CRTP
    {
        CRTPProcessor proc;

        for (auto& d : data) proc.process(d);
        auto end = std::chrono::high_resolution_clock::now();
```

## 5. Batching vs Per-Event Processing

### Per-Event Processing

Process each event immediately as it arrives:

```cpp
void per_event_processing(EventQueue& queue) {
    while (running) {
        Event e;
        if (queue.try_pop(e)) {
            process(e);     // Process one event
            commit(e);      // Commit one event
            notify(e);      // Notify one event
        }
    }
}
```

### Batched Processing

Collect multiple events, process them together:

```cpp
void batched_processing(EventQueue& queue) {
    constexpr size_t BATCH_SIZE = 64;
    Event batch[BATCH_SIZE];
    
    while (running) {
        // Collect batch
        size_t count = 0;
        while (count < BATCH_SIZE && queue.try_pop(batch[count])) {
            ++count;
        }
        
        if (count > 0) {
            process_batch(batch, count);  // Process N events
            commit_batch(batch, count);   // Commit N events
            notify_batch(batch, count);   // Notify N events
        }
    }
}
```

### Why Batching Improves Performance

#### 1. Amortized Overhead

Fixed costs are paid once per batch, not once per event:

```
Per-Event:
  [Lock] [Process] [Unlock] [Lock] [Process] [Unlock] [Lock] [Process] [Unlock]
    │                          │                          │
   10ns                       10ns                       10ns
   
   Total for 3 events: 30ns overhead + 3 × process time

Batched:
  [Lock] [Process] [Process] [Process] [Unlock]
    │                                      │
   10ns                                   10ns
   
   Total for 3 events: 20ns overhead + 3 × process time
```

#### 2. Better Cache Utilization

Batching keeps related data in cache:

```cpp
// Per-event: Metadata evicted from cache between events
void per_event(Event& e) {
    load_config();        // Cache miss - config not in cache
    load_routing_table(); // Cache miss
    process(e);
    // ... next event - cache is cold again
}

// Batched: Metadata stays hot
void batched(Event* events, size_t count) {
    load_config();        // Cache miss once
    load_routing_table(); // Cache miss once
    
    for (size_t i = 0; i < count; ++i) {
        process(events[i]);  // Config & routing table still in cache!
    }
}
```

#### 3. Vectorization Opportunities

Batching enables SIMD processing:

```cpp
// Per-event: Can't vectorize
for (;;) {
    Event e = queue.pop();
    e.value = e.value * scale + offset;  // Scalar operation
}

// Batched: Can vectorize
void process_batch(Event* events, size_t count) {
    // Compiler can auto-vectorize, or use explicit SIMD
    for (size_t i = 0; i < count; i += 8) {
        __m256 vals = _mm256_loadu_ps(&events[i].value);
        vals = _mm256_fmadd_ps(vals, scale_vec, offset_vec);
        _mm256_storeu_ps(&events[i].value, vals);
    }
}
```

#### 4. Reduced Synchronization

Less contention on shared resources:

```cpp
// Per-event: Lock acquired N times
void per_event_commit(Database& db, std::vector<Event>& events) {
    for (auto& e : events) {
        std::lock_guard<std::mutex> lock(db.mutex);  // N locks!
        db.write(e);
    }
}

// Batched: Lock acquired once
void batched_commit(Database& db, std::vector<Event>& events) {
    std::lock_guard<std::mutex> lock(db.mutex);  // 1 lock
    for (auto& e : events) {
        db.write(e);  // No locking overhead
    }
}
```

#### 5. I/O Efficiency

Batched I/O is dramatically more efficient:

```cpp
// Per-event: Many small writes
for (auto& e : events) {
    file.write(&e, sizeof(e));  // System call per event!
}

// Batched: One large write
file.write(events.data(), events.size() * sizeof(Event));  // One system call
```

| Approach | System Calls | Throughput |
|----------|--------------|------------|
| Per-event (1M events) | 1,000,000 | ~10K/sec |
| Batched (1M events, batch=1000) | 1,000 | ~1M/sec |

**100x improvement** from batching I/O!

### Optimal Batch Size

Too small = overhead not amortized  
Too large = latency suffers, memory wasted

**Factors to consider:**
1. **Cache size**: Batch should fit in L2/L3 cache
2. **Latency requirements**: Larger batches = higher latency
3. **Throughput requirements**: Larger batches = higher throughput
4. **SIMD width**: Batch size should be multiple of SIMD width (4, 8, 16)

**Rule of thumb**: Start with 64-256 elements, tune based on benchmarks.

```cpp
// Adaptive batch sizing
class AdaptiveBatcher {
    size_t batch_size_ = 64;
    static constexpr size_t MIN_BATCH = 16;
    static constexpr size_t MAX_BATCH = 1024;
    
public:
    void adjust_batch_size(double current_latency_ms, double target_latency_ms) {
        if (current_latency_ms > target_latency_ms * 1.2) {
            // Latency too high, reduce batch size
            batch_size_ = std::max(MIN_BATCH, batch_size_ / 2);
        } else if (current_latency_ms < target_latency_ms * 0.5) {
            // Latency headroom, increase batch size for throughput
            batch_size_ = std::min(MAX_BATCH, batch_size_ * 2);
        }
    }
};
```

### Trade-offs

| Aspect | Per-Event | Batched |
|--------|-----------|---------|
| Latency | Lower (immediate) | Higher (wait for batch) |
| Throughput | Lower | Higher |
| Code Complexity | Simpler | More complex |
| Memory Usage | Lower | Higher (batch buffer) |
| Error Handling | Easier | More complex |
| SIMD Potential | None | High |

### Real-World Example: Network Packet Processing

```cpp
class PacketProcessor {
    static constexpr size_t BATCH_SIZE = 64;
    Packet batch_[BATCH_SIZE];
    
public:
    void run(NetworkInterface& nic) {
        while (running_) {
            // Receive batch of packets
            size_t count = nic.receive_burst(batch_, BATCH_SIZE);
            
            if (count > 0) {
                // Batch process: parse all headers
                parse_headers_batch(batch_, count);
                
                // Batch process: lookup routing table
                lookup_routes_batch(batch_, count);
                
                // Batch process: apply transformations
                transform_batch(batch_, count);
                
                // Batch transmit
                nic.transmit_burst(batch_, count);
            }
        }
    }
    
private:
    void parse_headers_batch(Packet* pkts, size_t count) {
        // Prefetch future packets while parsing current
        for (size_t i = 0; i < count; ++i) {
            if (i + 4 < count) {
                __builtin_prefetch(pkts[i + 4].data, 0, 3);
            }
            parse_header(pkts[i]);
        }
    }
    
    void lookup_routes_batch(Packet* pkts, size_t count) {
        // Batch lookup amortizes hash table overhead
        for (size_t i = 0; i < count; ++i) {
            pkts[i].route = routing_table_.lookup(pkts[i].dst_ip);
        }
    }
};
```

### When to Use Each Approach

**Use Per-Event when:**
- Ultra-low latency is critical (microsecond responses)
- Events are rare (not worth batching overhead)
- Processing is simple (no fixed costs to amortize)
- Ordering must be strictly preserved

**Use Batching when:**
- High throughput is the goal
- I/O is involved (disk, network)
- SIMD processing is beneficial
- Fixed costs per operation are high
- Latency requirements are relaxed (milliseconds OK)

## Summary

| Concept | Key Takeaway |
|---------|--------------|
| **Hot/Cold Path** | Identify and optimize the 1% of code that runs 99% of the time |
| **Branch Prediction** | Keep branches predictable; use `[[likely]]`, sorting, or branchless code |
| **Cache Locality** | Sequential access is 100x faster than random; keep data compact |
| **SoA vs AoS** | Use SoA for streaming operations, AoS for entity-centric access |
| **Virtual Calls** | Avoid in hot paths; use CRTP, templates, or `std::variant` instead |
| **Batching** | Amortize overhead; enable SIMD; reduce synchronization |

### Performance Optimization Checklist

1. **Profile first** - Find the real hot paths
2. **Reduce memory access** - Stay in cache
3. **Eliminate branches** - Or make them predictable
4. **Avoid allocations** - Use pools, pre-allocation
5. **Batch operations** - Amortize fixed costs
6. **Enable vectorization** - Use SoA, alignment, simple loops
7. **Eliminate virtual calls** - In hot paths only
8. **Measure after** - Verify improvements
