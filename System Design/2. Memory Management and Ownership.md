## 1. Stack vs Heap Tradeoffs

Understanding where your data lives is fundamental to writing high-performance C++. The stack and heap are two fundamentally different memory regions with different performance characteristics, lifetimes, and use cases.

### 1.1 The Stack: Fast, Automatic, Limited

The stack is a region of memory that follows a strict Last-In-First-Out (LIFO) discipline. When you call a function, a "stack frame" is pushed onto the stack containing local variables, return addresses, and saved registers. When the function returns, the frame is popped.

#### How the Stack Works

```cpp
void foo() {
    int x = 10;           // x lives on foo's stack frame
    double y = 3.14;      // y lives right after x
    bar();                // bar's frame is pushed on top
}                         // x and y are automatically destroyed

void bar() {
    char buffer[100];     // 100 bytes on bar's stack frame
}                         // buffer is destroyed when bar returns
```

Memory layout during execution:

```
Stack grows downward (on most architectures)
┌────────────────────────┐ High addresses
│   main()'s frame       │
├────────────────────────┤
│   foo()'s frame        │
│   - int x              │
│   - double y           │
├────────────────────────┤
│   bar()'s frame        │
│   - char buffer[100]   │
├────────────────────────┤ ← Stack pointer (current top)
│   (free stack space)   │
│          ↓             │
└────────────────────────┘ Low addresses
```

#### Why the Stack is Fast

1. **No allocation overhead**: Allocating on the stack just means moving the stack pointer. It's a single instruction (`sub rsp, N` on x86-64).

2. **No fragmentation**: The LIFO discipline means memory is always contiguous and there's no need to search for free blocks.

3. **Cache locality**: The top of the stack is almost always in L1 cache because it's accessed so frequently.

4. **No bookkeeping**: Unlike heap allocators, there's no need to track which blocks are free or maintain metadata.

```cpp
// Stack allocation: ~1-2 CPU cycles
int x = 42;

// Heap allocation: ~50-500+ CPU cycles
int* p = new int(42);
```

#### Stack Limitations

1. **Fixed size**: Stack size is typically 1-8 MB (OS-dependent). Exceed it, and you get a stack overflow.

```cpp
void recursive_disaster(int n) {
    char buffer[1024 * 1024];  // 1 MB per call!
    if (n > 0) recursive_disaster(n - 1);  // Stack overflow after ~8 calls
}
```

2. **Automatic lifetime only**: Objects on the stack are destroyed when the function returns. You can't return a pointer to a local variable.

```cpp
int* bad_idea() {
    int x = 42;
    return &x;  // UNDEFINED BEHAVIOR: x is destroyed after return
}
```

3. **Size must be known at compile time**: You can't allocate variable-length arrays on the stack in standard C++ (though some compilers support VLAs as an extension).

```cpp
void process(int n) {
    // int arr[n];  // Not standard C++ (VLA extension)
    std::vector<int> arr(n);  // Use heap instead
}
```

### 1.2 The Heap: Flexible, Shared, Expensive

The heap (or "free store" in C++ parlance) is a large pool of memory from which you can allocate and free blocks of arbitrary size at any time.

#### How the Heap Works

When you call `new` or `malloc`, the memory allocator:

1. Searches its data structures for a free block of sufficient size
2. Possibly splits a larger block or requests more memory from the OS
3. Marks the block as allocated
4. Returns a pointer to the usable memory

When you call `delete` or `free`:

1. The allocator marks the block as free
2. Possibly coalesces adjacent free blocks
3. The memory may or may not be returned to the OS

```cpp
void example() {
    int* p = new int(42);    // Allocate on heap
    // ... use p ...
    delete p;                 // Free the memory
}
```

#### Why the Heap is Slower

1. **Search overhead**: Finding a suitable free block requires searching data structures (free lists, trees, etc.).

2. **Synchronization**: In multi-threaded programs, the heap must be protected by locks (or use complex lock-free algorithms).

3. **Fragmentation**: Over time, the heap becomes fragmented, making searches slower and wasting memory.

4. **System calls**: If the allocator needs more memory, it must ask the OS (via `sbrk`, `mmap`, etc.), which is very expensive.

#### Heap Advantages

1. **Dynamic size**: Allocate as much as you need, when you need it.

2. **Arbitrary lifetime**: Objects live until you explicitly delete them (or the program exits).

3. **Sharing**: Heap objects can be accessed from any function, thread, or scope.

```cpp
std::vector<int>* create_large_data() {
    // Vector's internal storage is on the heap
    auto* data = new std::vector<int>(1000000);
    return data;  // Safe: data persists after function returns
}
```

### 1.3 Practical Tradeoffs

| Aspect | Stack | Heap |
|--------|-------|------|
| Allocation speed | ~1-2 cycles | ~50-500+ cycles |
| Deallocation speed | ~1 cycle (automatic) | ~50-500+ cycles |
| Size limit | 1-8 MB typical | Limited by RAM |
| Thread safety | Per-thread (no sync needed) | Requires synchronization |
| Fragmentation | None | Can be severe |
| Lifetime | Automatic (scope-based) | Manual or smart pointers |
| Locality | Excellent | Depends on allocation pattern |

#### When to Use Stack

- Small, fixed-size objects
- Objects with clearly scoped lifetimes
- Performance-critical hot paths
- Temporary buffers

```cpp
void process_packet(const uint8_t* data, size_t len) {
    // Stack buffer for small packets (fast)
    uint8_t local_buffer[1500];
    
    if (len <= sizeof(local_buffer)) {
        memcpy(local_buffer, data, len);
        process(local_buffer, len);
    } else {
        // Fall back to heap for jumbo packets
        std::vector<uint8_t> heap_buffer(data, data + len);
        process(heap_buffer.data(), heap_buffer.size());
    }
}
```

#### When to Use Heap

- Large objects
- Objects with dynamic size
- Objects that outlive their creating scope
- Objects shared between threads

### 1.4 Stack Allocation Tricks

#### alloca() - Dynamic Stack Allocation

```cpp
#include <alloca.h>

void dynamic_stack(int n) {
    // Allocates n bytes on the stack (non-standard but widely supported)
    char* buffer = (char*)alloca(n);
    // buffer is automatically freed when function returns
}
```

**Warning**: `alloca()` can cause stack overflow if `n` is too large. Never use with untrusted input.

#### Small Buffer Optimization (SBO)

Many standard library types use SBO to avoid heap allocation for small data:

```cpp
// Conceptual implementation of std::string with SBO
class small_string {
    union {
        char* heap_data;
        char stack_data[16];  // Small strings stored here
    };
    size_t size;
    size_t capacity;
    
    bool is_small() const { return capacity <= 15; }
    
public:
    const char* data() const {
        return is_small() ? stack_data : heap_data;
    }
};
```

This is why `std::string` for short strings is nearly as fast as a `char` array.

## 2. Custom Allocators (Slab, Pool, Arena)

The general-purpose allocator (`malloc`/`new`) is designed for versatility, not maximum performance. When you know your allocation patterns in advance, custom allocators can be dramatically faster and eliminate fragmentation.

### 2.1 Why Custom Allocators?

The standard allocator must handle:
- Allocations of any size (1 byte to gigabytes)
- Allocations in any order
- Thread safety for all threads
- Minimizing fragmentation for all patterns

This generality comes at a cost. If you know your specific pattern, you can optimize:

| Allocation Pattern | Custom Allocator | Benefit |
|-------------------|------------------|---------|
| Many same-size objects | Pool/Slab | O(1) alloc, zero fragmentation |
| Many objects freed together | Arena | O(1) bulk free |
| Temporary allocations | Linear/Bump | Fastest possible |
| Per-thread allocations | Thread-local pools | No synchronization |

### 2.2 Pool Allocator

A pool allocator pre-allocates a large block of memory and divides it into fixed-size chunks. All allocations are the same size.

#### How It Works

```
Pool of 64-byte blocks:
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ Free │ Used │ Used │ Free │ Free │ Used │ Free │ Free │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
    ↓           ↓                              ↓
    └───────────┴──────────────────────────────┘
                    Free list
```

Free blocks are linked together in a free list. Allocation pops from the list; deallocation pushes onto it.

#### Implementation

```cpp
template<typename T, size_t PoolSize = 1024>
class PoolAllocator {
    // Each block stores either an object or a pointer to the next free block
    union Block {
        T object;
        Block* next_free;
    };
    
    Block pool[PoolSize];
    Block* free_list;
    
public:
    PoolAllocator() {
        // Link all blocks into the free list
        free_list = &pool[0];
        for (size_t i = 0; i < PoolSize - 1; ++i) {
            pool[i].next_free = &pool[i + 1];
        }
        pool[PoolSize - 1].next_free = nullptr;
    }
    
    T* allocate() {
        if (!free_list) {
            throw std::bad_alloc();  // Pool exhausted
        }
        
        Block* block = free_list;
        free_list = block->next_free;
        return &block->object;
    }
    
    void deallocate(T* ptr) {
        Block* block = reinterpret_cast<Block*>(ptr);
        block->next_free = free_list;
        free_list = block;
    }
};
```

#### Usage Example

```cpp
struct Packet {
    uint32_t src_ip;
    uint32_t dst_ip;
    uint16_t src_port;
    uint16_t dst_port;
    uint8_t data[1500];
};

// Pre-allocate pool of 10000 packets
PoolAllocator<Packet, 10000> packet_pool;

void receive_packet() {
    Packet* pkt = packet_pool.allocate();  // O(1), no lock if single-threaded
    // ... process packet ...
    packet_pool.deallocate(pkt);           // O(1)
}
```

#### Performance

- **Allocation**: O(1) - just pop from free list
- **Deallocation**: O(1) - just push to free list
- **Fragmentation**: Zero (all blocks are same size)
- **Memory overhead**: Very low (no per-block headers)

### 2.3 Slab Allocator

A slab allocator is an extension of pool allocation, commonly used in operating system kernels (first introduced in Solaris). It maintains multiple pools ("slabs") for different object sizes or types.

#### How It Works

```
Slab Allocator
├── Slab for 32-byte objects
│   ├── Slab page 1: [████░░░░░░]  (partially used)
│   ├── Slab page 2: [██████████]  (full)
│   └── Slab page 3: [░░░░░░░░░░]  (empty)
│
├── Slab for 64-byte objects
│   ├── Slab page 1: [██████░░░░]
│   └── Slab page 2: [░░░░░░░░░░]
│
└── Slab for 128-byte objects
    └── Slab page 1: [████░░░░░░]
```

#### Implementation Concepts

```cpp
class SlabAllocator {
    // Different size classes
    static constexpr size_t SIZE_CLASSES[] = {8, 16, 32, 64, 128, 256, 512, 1024};
    
    struct Slab {
        void* memory;
        size_t object_size;
        size_t capacity;
        void* free_list;
    };
    
    std::vector<Slab> slabs_by_size[sizeof(SIZE_CLASSES) / sizeof(SIZE_CLASSES[0])];
    
    int find_size_class(size_t size) {
        for (int i = 0; i < sizeof(SIZE_CLASSES) / sizeof(SIZE_CLASSES[0]); ++i) {
            if (SIZE_CLASSES[i] >= size) return i;
        }
        return -1;  // Too large, use regular allocator
    }
    
public:
    void* allocate(size_t size) {
        int size_class = find_size_class(size);
        if (size_class < 0) {
            return ::malloc(size);  // Fall back to system allocator
        }
        
        // Find a slab with free space, or create a new one
        for (auto& slab : slabs_by_size[size_class]) {
            if (slab.free_list) {
                return pop_from_free_list(slab);
            }
        }
        
        // Create new slab
        return allocate_new_slab(size_class);
    }
};
```

#### Object Caching

The key insight of slab allocation is **object caching**. For complex objects, construction and destruction can be expensive. Slabs can keep objects in an initialized state:

```cpp
template<typename T>
class ObjectCache {
    PoolAllocator<T> pool;
    std::stack<T*> constructed_cache;  // Pre-constructed objects
    
public:
    T* acquire() {
        if (!constructed_cache.empty()) {
            T* obj = constructed_cache.top();
            constructed_cache.pop();
            return obj;  // Already constructed!
        }
        
        // Allocate and construct new object
        T* ptr = pool.allocate();
        new (ptr) T();  // Placement new
        return ptr;
    }
    
    void release(T* obj) {
        // Don't destruct - just reset and cache
        obj->reset();  // Custom reset method
        constructed_cache.push(obj);
    }
};
```

This is particularly valuable for objects like:
- Database connections
- SSL contexts
- Thread handles
- Complex data structures

### 2.4 Arena Allocator (Linear/Bump Allocator)

An arena allocator is the simplest and fastest allocator. It allocates memory by simply incrementing a pointer. Individual deallocations are not supported—you free everything at once.

#### How It Works

```
Arena (4KB):
┌──────────────────────────────────────────────────────────────────┐
│████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
└──────────────────────────────────────────────────────────────────┘
                     ↑                                             ↑
                     current pointer                               end

Allocation: just move the pointer forward
Reset: move pointer back to start (frees everything)
```

#### Implementation

```cpp
class Arena {
    uint8_t* memory;
    size_t capacity;
    size_t offset;
    
public:
    Arena(size_t size) : capacity(size), offset(0) {
        memory = static_cast<uint8_t*>(std::aligned_alloc(alignof(std::max_align_t), size));
    }
    
    ~Arena() {
        std::free(memory);
    }
    
    void* allocate(size_t size, size_t alignment = alignof(std::max_align_t)) {
        // Align the current offset
        size_t aligned_offset = (offset + alignment - 1) & ~(alignment - 1);
        
        if (aligned_offset + size > capacity) {
            throw std::bad_alloc();  // Arena exhausted
        }
        
        void* ptr = memory + aligned_offset;
        offset = aligned_offset + size;
        return ptr;
    }
    
    template<typename T, typename... Args>
    T* create(Args&&... args) {
        void* ptr = allocate(sizeof(T), alignof(T));
        return new (ptr) T(std::forward<Args>(args)...);
    }
    
    void reset() {
        // Free everything at once - no destructors called!
        offset = 0;
    }
    
    size_t used() const { return offset; }
    size_t remaining() const { return capacity - offset; }
};
```

#### Usage Example

```cpp
void process_request(const Request& req) {
    Arena arena(64 * 1024);  // 64KB arena for this request
    
    // All allocations are lightning fast
    auto* parsed = arena.create<ParsedRequest>(req);
    auto* intermediate = arena.create<IntermediateData>();
    
    std::vector<Result, ArenaAllocator<Result>> results(arena);
    
    for (const auto& item : parsed->items) {
        results.push_back(process_item(item, arena));
    }
    
    send_response(results);
    
}  // Arena destroyed - all memory freed at once, no individual deletes

```

#### When to Use Arenas

- **Request handling**: Each request gets its own arena; freed when request completes
- **Compilation phases**: Parser allocates into arena; freed after code generation
- **Game frames**: Per-frame allocations freed at end of frame
- **Parsing/AST building**: Tree nodes allocated from arena; freed after processing

#### Arena Performance

```cpp
// Benchmark comparison
void benchmark() {
    const int N = 1000000;
    
    // Standard allocator
    auto start = now();
    for (int i = 0; i < N; ++i) {
        auto* p = new int(i);
        delete p;
    }
    auto standard_time = now() - start;
    
    // Arena allocator
    Arena arena(N * sizeof(int) + 1024);
    start = now();
    for (int i = 0; i < N; ++i) {
        arena.create<int>(i);
    }
    arena.reset();  // All freed at once
    auto arena_time = now() - start;
    
    // Arena is typically 10-50x faster
}
```

### 2.5 Thread-Local Allocators

For multi-threaded applications, the standard allocator's synchronization is a major bottleneck. Thread-local allocators eliminate this.

```cpp
class ThreadLocalPool {
    static thread_local PoolAllocator<Packet, 1000> local_pool;
    static thread_local Arena local_arena;
    
public:
    static Packet* allocate_packet() {
        return local_pool.allocate();  // No synchronization needed
    }
    
    static void* arena_alloc(size_t size) {
        return local_arena.allocate(size);  // No synchronization needed
    }
};

// Each thread has its own pool
thread_local PoolAllocator<Packet, 1000> ThreadLocalPool::local_pool;
thread_local Arena ThreadLocalPool::local_arena{1024 * 1024};
```

### 2.6 Integrating with STL

C++ allows custom allocators with standard containers:

```cpp
template<typename T>
class ArenaAllocator {
    Arena* arena;
    
public:
    using value_type = T;
    
    ArenaAllocator(Arena& a) : arena(&a) {}
    
    template<typename U>
    ArenaAllocator(const ArenaAllocator<U>& other) : arena(other.arena) {}
    
    T* allocate(size_t n) {
        return static_cast<T*>(arena->allocate(n * sizeof(T), alignof(T)));
    }
    
    void deallocate(T*, size_t) {
        // No-op: arena frees everything at once
    }
};

// Usage
Arena arena(1024 * 1024);
std::vector<int, ArenaAllocator<int>> vec(ArenaAllocator<int>(arena));
std::map<std::string, int, std::less<>, ArenaAllocator<std::pair<const std::string, int>>> 
    map(ArenaAllocator<std::pair<const std::string, int>>(arena));
```

## 3. Object Lifetime & Ownership Models

Understanding object lifetime and ownership is crucial for writing correct, leak-free C++. Unlike garbage-collected languages, C++ gives you complete control—and complete responsibility.

### 3.1 What is Ownership?

**Ownership** answers the question: "Who is responsible for destroying this object?"

- The **owner** of an object is responsible for ensuring it is properly destroyed
- There must always be exactly one owner (or a clear sharing scheme)
- When the owner's lifetime ends, it must destroy the owned object

### 3.2 Stack Ownership (Automatic)

The simplest ownership model: the stack frame owns local objects.

```cpp
void process() {
    std::string name = "Alice";  // Stack owns 'name'
    std::vector<int> data(100);  // Stack owns 'data'
    
    // Use name and data...
    
}  // Automatic destruction: ~vector called, then ~string called
```

**Lifetime rule**: Object lives from declaration until the closing `}` of its scope.

### 3.3 Unique Ownership (Exclusive)

One object exclusively owns another. When the owner is destroyed, the owned object is destroyed.

```cpp
class Engine {
    std::unique_ptr<Turbocharger> turbo;  // Engine exclusively owns turbo
    
public:
    Engine() : turbo(std::make_unique<Turbocharger>()) {}
    
    // When Engine is destroyed, turbo is automatically destroyed
};

class Car {
    Engine engine;  // Car exclusively owns engine
    
public:
    // When Car is destroyed, engine (and thus turbo) are destroyed
};
```

**Ownership chain**: Car → Engine → Turbocharger. Destroying the Car destroys everything.

### 3.4 Shared Ownership

Multiple owners share responsibility. The object is destroyed when the last owner is destroyed.

```cpp
class Document {
    std::shared_ptr<Image> logo;  // Document shares ownership of logo
};

// Multiple documents can share the same logo
auto shared_logo = std::make_shared<Image>("company_logo.png");
Document doc1, doc2, doc3;
doc1.logo = shared_logo;
doc2.logo = shared_logo;
doc3.logo = shared_logo;

// Logo is destroyed only when doc1, doc2, AND doc3 are all destroyed
```

**Warning**: Shared ownership is often overused. Prefer unique ownership when possible.

### 3.5 Non-Owning References

Sometimes you need to access an object without owning it. The key rule: the reference must not outlive the object.

```cpp
class Logger {
    std::ostream& output;  // Reference to stream (non-owning)
    
public:
    Logger(std::ostream& os) : output(os) {}
    // Logger doesn't own the stream; caller must ensure stream outlives Logger
};

void example() {
    std::ofstream file("log.txt");  // file owns the stream
    Logger logger(file);             // logger references but doesn't own
    
    logger.log("Hello");
    
}  // logger destroyed first, then file. Order matters!
```

### 3.6 Ownership Patterns in System Design

#### Pattern 1: Factory Creates, Caller Owns

```cpp
class ConnectionFactory {
public:
    std::unique_ptr<Connection> create(const std::string& host, int port) {
        auto conn = std::make_unique<Connection>();
        conn->connect(host, port);
        return conn;  // Ownership transferred to caller
    }
};

// Caller now owns the connection
auto conn = factory.create("localhost", 8080);
```

#### Pattern 2: Container Owns Elements

```cpp
class RequestQueue {
    std::queue<std::unique_ptr<Request>> requests;  // Queue owns all requests
    
public:
    void enqueue(std::unique_ptr<Request> req) {
        requests.push(std::move(req));  // Ownership transferred to queue
    }
    
    std::unique_ptr<Request> dequeue() {
        auto req = std::move(requests.front());
        requests.pop();
        return req;  // Ownership transferred to caller
    }
};
```

#### Pattern 3: Object Pool (Temporary Ownership Transfer)

```cpp
template<typename T>
class ObjectPool {
    std::vector<std::unique_ptr<T>> available;
    
public:
    // "Lease" an object - caller has temporary ownership
    std::unique_ptr<T, std::function<void(T*)>> acquire() {
        if (available.empty()) {
            return {new T(), [this](T* p) { this->release(p); }};
        }
        
        auto ptr = std::move(available.back());
        available.pop_back();
        return {ptr.release(), [this](T* p) { this->release(p); }};
    }
    
private:
    void release(T* obj) {
        obj->reset();  // Clean up for reuse
        available.push_back(std::unique_ptr<T>(obj));  // Return to pool
    }
};
```

#### Pattern 4: Parent Owns Children (Composite)

```cpp
class Widget {
    std::vector<std::unique_ptr<Widget>> children;  // Parent owns children
    Widget* parent = nullptr;  // Non-owning back-reference
    
public:
    Widget* addChild(std::unique_ptr<Widget> child) {
        child->parent = this;
        children.push_back(std::move(child));
        return children.back().get();
    }
    
    // When Widget is destroyed, all children are destroyed recursively
};
```

### 3.7 Lifetime Bugs and How to Avoid Them

#### Bug 1: Dangling Pointer

```cpp
int* dangling() {
    int x = 42;
    return &x;  // BUG: x is destroyed after return
}

// Fix: Return by value, or allocate on heap
int* fixed() {
    return new int(42);  // Caller must delete
}
```

#### Bug 2: Use After Free

```cpp
void use_after_free() {
    auto* p = new Widget();
    delete p;
    p->doSomething();  // BUG: p points to freed memory
}

// Fix: Use smart pointers
void fixed() {
    auto p = std::make_unique<Widget>();
    p.reset();  // Frees the widget
    // p->doSomething();  // Won't compile if p is null (with proper checks)
}
```

#### Bug 3: Double Free

```cpp
void double_free() {
    auto* p = new Widget();
    delete p;
    delete p;  // BUG: double free
}

// Fix: Smart pointers prevent this automatically
```

#### Bug 4: Reference to Temporary

```cpp
const std::string& bad() {
    return std::string("temporary");  // BUG: returns reference to temporary
}

// Fix: Return by value
std::string fixed() {
    return std::string("temporary");  // RVO/move makes this efficient
}
```

## 4. unique_ptr vs shared_ptr vs Raw Pointers

Choosing the right pointer type is one of the most important decisions in C++ design. Each type expresses different ownership semantics.

### 4.1 Raw Pointers: Non-Owning References

In modern C++, raw pointers should primarily be used for **non-owning references**—situations where you need to point to an object but don't control its lifetime.

```cpp
class Employee {
    Department* department;  // Employee doesn't own department
    
public:
    void setDepartment(Department* dept) {
        department = dept;  // Just observing, not owning
    }
    
    void printDepartment() {
        if (department) {
            std::cout << department->name() << "\n";
        }
    }
};
```

#### When to Use Raw Pointers

1. **Non-owning references to single objects** (alternative: `T&` reference)
2. **Optional non-owning references** (`T*` is nullable, `T&` is not)
3. **Interfacing with C APIs**
4. **Performance-critical code** where smart pointer overhead matters

#### Raw Pointer Rules

- Never `delete` a raw pointer unless you're absolutely certain you own it
- Document ownership clearly: "This function does NOT take ownership"
- Prefer references (`T&`) when nullability isn't needed

### 4.2 std::unique_ptr: Exclusive Ownership

`unique_ptr` represents exclusive ownership. There is exactly one `unique_ptr` pointing to an object, and when it's destroyed (or reset), the object is deleted.

#### Basic Usage

```cpp
// Creation
auto ptr = std::make_unique<Widget>(arg1, arg2);

// Transfer ownership
auto ptr2 = std::move(ptr);  // ptr is now null, ptr2 owns the Widget

// Release ownership (returns raw pointer, unique_ptr becomes null)
Widget* raw = ptr2.release();  // Now YOU must delete raw

// Reset (delete current object, optionally take new one)
ptr2.reset();               // Deletes and becomes null
ptr2.reset(new Widget());   // Deletes old, takes ownership of new

// Access
ptr->method();    // Like raw pointer
Widget& ref = *ptr;
Widget* raw_access = ptr.get();  // Get raw pointer (non-owning)
```

#### Custom Deleters

```cpp
// For resources that need special cleanup
auto file = std::unique_ptr<FILE, decltype(&fclose)>(
    fopen("data.txt", "r"),
    fclose
);

// Lambda deleter
auto ptr = std::unique_ptr<int, std::function<void(int*)>>(
    new int(42),
    [](int* p) {
        std::cout << "Custom delete!\n";
        delete p;
    }
);
```

#### unique_ptr in Containers

```cpp
std::vector<std::unique_ptr<Widget>> widgets;

widgets.push_back(std::make_unique<Widget>());
widgets.emplace_back(new Widget());  // Works but make_unique is preferred

// Iterate (access but don't transfer ownership)
for (const auto& w : widgets) {
    w->process();
}

// Transfer out
auto first = std::move(widgets.front());  // Now widgets[0] is null
widgets.erase(widgets.begin());           // Remove the null entry
```

#### unique_ptr Performance

`unique_ptr` has **zero overhead** compared to a raw pointer:
- Same size as a raw pointer (unless using a stateful custom deleter)
- Same dereference cost
- Destructor just calls `delete` (or custom deleter)

```cpp
static_assert(sizeof(std::unique_ptr<int>) == sizeof(int*));
```

### 4.3 std::shared_ptr: Shared Ownership

`shared_ptr` implements shared ownership through reference counting. Multiple `shared_ptr` instances can point to the same object, and the object is deleted when the last `shared_ptr` is destroyed.

#### How It Works

```
┌─────────────────────────────────────────────────────────────┐
│                     Control Block                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ Strong refs │  │ Weak refs   │  │ Deleter (optional)  │  │
│  │     3       │  │     1       │  │                     │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
                         │
                         │ points to
                         ▼
                 ┌───────────────┐
                 │    Object     │
                 │   (Widget)    │
                 └───────────────┘
                         ↑
           ┌─────────────┼─────────────┐
           │             │             │
    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │shared_ptr│  │shared_ptr│  │shared_ptr│
    │    A     │  │    B     │  │    C     │
    └──────────┘  └──────────┘  └──────────┘
```

Each `shared_ptr` contains two pointers:
1. Pointer to the managed object
2. Pointer to the control block (reference counts)

#### Basic Usage

```cpp
// Creation (prefer make_shared)
auto ptr = std::make_shared<Widget>(arg1, arg2);

// Copy (increases reference count)
auto ptr2 = ptr;  // Now refcount = 2

// Check reference count
std::cout << ptr.use_count();  // 2

// Reset (decreases refcount, deletes if last)
ptr.reset();  // refcount = 1, Widget still alive
ptr2.reset(); // refcount = 0, Widget destroyed
```

#### make_shared vs new

```cpp
// BAD: Two allocations (object + control block)
auto ptr = std::shared_ptr<Widget>(new Widget());

// GOOD: Single allocation (object and control block together)
auto ptr = std::make_shared<Widget>();
```

`make_shared` is more efficient because it allocates the object and control block in one contiguous memory block, improving cache locality and reducing allocation overhead.

#### shared_ptr Overhead

`shared_ptr` has significant overhead compared to raw pointers:

| Aspect | unique_ptr | shared_ptr |
|--------|------------|------------|
| Size | 8 bytes | 16 bytes (two pointers) |
| Allocation | Just object | Object + control block |
| Copy cost | N/A (move only) | Atomic increment |
| Destruction | Direct delete | Atomic decrement, conditional delete |
| Thread safety | None (just a pointer) | Reference count is thread-safe |

#### Circular References: The Achilles Heel

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;  // PROBLEM!
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;  // Circular reference!

// When a and b go out of scope:
// - a's refcount: 1 (held by b->prev)
// - b's refcount: 1 (held by a->next)
// Neither is ever destroyed! MEMORY LEAK!
```

### 4.4 std::weak_ptr: Breaking Cycles

`weak_ptr` is a non-owning observer of a `shared_ptr`-managed object. It doesn't affect the reference count, so it can break cycles.

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;  // Weak reference - doesn't own
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;  // Weak reference, doesn't increase refcount

// When a and b go out of scope:
// - a's refcount: 0 (b->prev is weak, doesn't count)
// - b's refcount: 0 (a is destroyed, a->next released)
// Both are properly destroyed!
```

#### Using weak_ptr

```cpp
std::shared_ptr<Widget> shared = std::make_shared<Widget>();
std::weak_ptr<Widget> weak = shared;

// Check if object still exists
if (!weak.expired()) {
    // Object exists, but this check is racy in multi-threaded code
}

// Safe access via lock()
if (auto locked = weak.lock()) {
    // locked is a shared_ptr; object guaranteed to exist
    locked->doSomething();
}  // locked destroyed, doesn't affect original shared

// Object destroyed
shared.reset();
auto locked = weak.lock();  // Returns empty shared_ptr
```

### 4.5 Choosing the Right Pointer

```
Start Here: Who owns this object?
                │
        ┌───────┴───────┐
        │               │
   One owner       Multiple owners
        │               │
        ▼               ▼
  unique_ptr        shared_ptr
        │               │
        │           Consider:
        │           - Do I really need shared ownership?
        │           - Can I restructure to use unique ownership?
        │
        ▼
  Need non-owning reference?
        │
   ┌────┴────┐
   │         │
  Yes       No
   │         │
   ▼         ▼
Optional? Is it to a shared_ptr-managed object?
   │              │
  ┌┴──┐      ┌────┴────┐
  │   │      │         │
 Yes  No    Yes       No
  │   │      │         │
  ▼   ▼      ▼         ▼
 T*  T&  weak_ptr    T* or T&
```

#### Quick Reference Table

| Scenario | Use |
|----------|-----|
| Exclusive ownership | `unique_ptr<T>` |
| Factory function returns | `unique_ptr<T>` |
| Shared ownership required | `shared_ptr<T>` |
| Cache/observer of shared object | `weak_ptr<T>` |
| Non-owning reference, always valid | `T&` |
| Non-owning reference, may be null | `T*` |
| C API interop | Raw pointer |
| High-performance hot path | Consider raw (carefully!) |

### 4.6 Performance Comparison


## 5. Avoiding Fragmentation

Memory fragmentation occurs when free memory is divided into small, non-contiguous blocks. Even if the total free memory is sufficient, allocations can fail because no single block is large enough.

### 5.1 Understanding Fragmentation

#### External Fragmentation

Free memory exists, but it's split into pieces too small to use.

```
Memory state after many allocations and frees:
┌────┬░░░░┬────┬░░░┬────┬░░░░░░┬────┬░░░░┬────┐
│Used│Free│Used│Fre│Used│ Free │Used│Free│Used│
│64B │32B │128B│16B│64B │ 48B  │32B │24B │64B │
└────┴░░░░┴────┴░░░┴────┴░░░░░░┴────┴░░░░┴────┘

Total free: 32+16+48+24 = 120 bytes
Largest free block: 48 bytes
Allocation request for 100 bytes: FAILS (no single block large enough)
```

#### Internal Fragmentation

Allocated blocks are larger than needed, wasting space inside the block.

```
Allocation request: 100 bytes
Allocator has 128-byte blocks (power of 2)
┌──────────────────────────────────────────────┐
│████████████████████████████████░░░░░░░░░░░░░░│
│        Used (100 bytes)        │Wasted (28B) │
└──────────────────────────────────────────────┘

28 bytes wasted due to internal fragmentation
```

### 5.2 Causes of Fragmentation

1. **Variable-size allocations**: Mixing small and large allocations
2. **Random allocation/deallocation order**: Unlike stack (LIFO), heap has random patterns
3. **Long-lived vs short-lived objects**: Long-lived objects "pin" memory between them
4. **Memory churn**: Continuous allocation and deallocation

```cpp
// Fragmentation-inducing pattern
std::vector<void*> ptrs;
for (int i = 0; i < 10000; ++i) {
    ptrs.push_back(malloc(rand() % 1000 + 1));  // Random sizes
}

// Free every other allocation
for (int i = 0; i < ptrs.size(); i += 2) {
    free(ptrs[i]);
    ptrs[i] = nullptr;
}

// Now memory looks like: [used][free][used][free][used][free]...
// Very fragmented!
```

### 5.3 Strategies to Avoid Fragmentation

#### Strategy 1: Fixed-Size Allocations (Pool Allocator)

If all allocations are the same size, fragmentation is impossible.

```cpp
// All packets are the same size - use a pool
PoolAllocator<Packet, 10000> packet_pool;

// All allocations and frees are O(1) with zero fragmentation
```

#### Strategy 2: Size Classes (Slab Allocator)

Group allocations into size classes. Fragmentation only occurs within a size class.

```cpp
// Allocations are rounded up to size classes
// 1-8 bytes → 8-byte pool
// 9-16 bytes → 16-byte pool
// 17-32 bytes → 32-byte pool
// etc.

class SizeClassAllocator {
    PoolAllocator<Block8>  pool_8;
    PoolAllocator<Block16> pool_16;
    PoolAllocator<Block32> pool_32;
    // ...
    
    void* allocate(size_t size) {
        if (size <= 8)  return pool_8.allocate();
        if (size <= 16) return pool_16.allocate();
        if (size <= 32) return pool_32.allocate();
        // ...
    }
};
```

Internal fragmentation is bounded: at most 50% waste (e.g., 17-byte request gets 32-byte block).

#### Strategy 3: Arena Allocation

Allocate related objects together; free them all at once.

```cpp
void process_request() {
    Arena arena(64 * 1024);
    
    // All request-related objects come from this arena
    auto* req = arena.create<Request>();
    auto* response = arena.create<Response>();
    auto* temp_data = arena.allocate(1000);
    
    // ... process ...
    
}  // Everything freed at once - no fragmentation buildup
```

#### Strategy 4: Object Reuse

Instead of freeing and reallocating, reuse objects.

```cpp
class ConnectionPool {
    std::stack<std::unique_ptr<Connection>> available;
    
public:
    std::unique_ptr<Connection> acquire() {
        if (available.empty()) {
            return std::make_unique<Connection>();
        }
        auto conn = std::move(available.top());
        available.pop();
        conn->reset();  // Reuse existing connection
        return conn;
    }
    
    void release(std::unique_ptr<Connection> conn) {
        available.push(std::move(conn));  // Don't delete - reuse later
    }
};
```

#### Strategy 5: Compaction (When Possible)

If you can move objects, you can compact memory. This requires indirection.

```cpp
class CompactingAllocator {
    std::vector<uint8_t> memory;
    std::vector<std::pair<size_t, size_t>> allocations;  // offset, size
    
    void compact() {
        // Move all allocations to the beginning, eliminating gaps
        size_t write_pos = 0;
        for (auto& [offset, size] : allocations) {
            if (offset != write_pos) {
                memmove(memory.data() + write_pos, memory.data() + offset, size);
                offset = write_pos;
            }
            write_pos += size;
        }
    }
};
```

**Limitation**: Compaction requires updating all pointers to moved objects. This is why handles or indices are often used instead of raw pointers.

#### Strategy 6: Memory Mapping

For very large allocations, use `mmap()` directly. When freed, memory returns to the OS immediately (no fragmentation in user space).

```cpp
void* allocate_large(size_t size) {
    void* ptr = mmap(nullptr, size, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (ptr == MAP_FAILED) throw std::bad_alloc();
    return ptr;
}

void deallocate_large(void* ptr, size_t size) {
    munmap(ptr, size);  // Immediately returned to OS
}
```

### 5.4 Measuring Fragmentation

```cpp
class FragmentationTracker {
    size_t total_allocated = 0;
    size_t total_requested = 0;
    size_t allocation_count = 0;
    size_t peak_allocated = 0;
    
public:
    void record_alloc(size_t requested, size_t actual) {
        total_requested += requested;
        total_allocated += actual;
        allocation_count++;
        peak_allocated = std::max(peak_allocated, total_allocated);
    }
    
    double internal_fragmentation() const {
        return 1.0 - (double)total_requested / total_allocated;
    }
    
    void print_stats() const {
        std::cout << "Allocations: " << allocation_count << "\n"
                  << "Requested: " << total_requested << " bytes\n"
                  << "Allocated: " << total_allocated << " bytes\n"
                  << "Internal fragmentation: " << internal_fragmentation() * 100 << "%\n"
                  << "Peak usage: " << peak_allocated << " bytes\n";
    }
};
```

### 5.5 Real-World Allocators

Modern allocators use sophisticated techniques to minimize fragmentation:

**jemalloc** (Facebook, Redis):
- Thread-local caches
- Size classes with low internal fragmentation
- Automatic arena management

**tcmalloc** (Google):
- Per-thread caches for small objects
- Central page heap for large objects
- Periodic cleanup and compaction

**mimalloc** (Microsoft):
- Segment-based design
- Free list sharding
- Optimized for modern hardware

```cpp

// No code changes needed - it replaces malloc/new

```

## 6. Zero-Copy Designs

Copying data is expensive. At 10 Gbps, you're moving 1.25 GB/sec. Every unnecessary copy halves your throughput. Zero-copy designs minimize or eliminate data movement.

### 6.1 The Cost of Copying

```cpp
// Traditional (with copies)
void process_network_data() {
    char kernel_buffer[4096];           // Data arrives here via DMA
    char user_buffer[4096];             // Copy 1: kernel → user
    memcpy(user_buffer, kernel_buffer, 4096);
    
    std::string data(user_buffer, 4096);  // Copy 2: buffer → string
    
    process(data);                      // Process the data
    
    char output_buffer[4096];
    memcpy(output_buffer, data.c_str(), data.size());  // Copy 3: string → buffer
    
    send(socket, output_buffer, data.size(), 0);  // Copy 4: user → kernel
}

// That's 16KB of copying for 4KB of data!
```

### 6.2 Zero-Copy Principles

1. **Don't copy if you can reference**: Pass pointers/views instead of copying data
2. **Allocate once, reuse**: Pre-allocate buffers and keep reusing them
3. **Let the hardware do it**: DMA can move data without CPU involvement
4. **Eliminate intermediate representations**: Parse in-place

### 6.3 String Views (std::string_view)

`string_view` is a non-owning reference to a string. It's just a pointer and a length—no allocation, no copying.

```cpp
// BAD: Creates substring copy
std::string get_extension(const std::string& filename) {
    size_t pos = filename.rfind('.');
    return filename.substr(pos);  // Allocates and copies!
}

// GOOD: Returns view into existing string
std::string_view get_extension(std::string_view filename) {
    size_t pos = filename.rfind('.');
    return filename.substr(pos);  // No allocation, just adjusts pointer
}

// Usage
std::string file = "document.pdf";
auto ext = get_extension(file);  // ext points into file's memory
```

#### string_view Gotchas

```cpp
std::string_view dangerous() {
    std::string temp = "hello";
    return temp;  // BUG: temp is destroyed, view is dangling!
}

std::string_view also_dangerous(const std::string& s) {
    return s.substr(0, 5);  // OK if s outlives the view
}

void usage() {
    auto view = also_dangerous(std::string("temporary"));  // BUG!
    // The temporary string is destroyed, view is dangling
}
```

**Rule**: The viewed string must outlive the `string_view`.

### 6.4 Span (std::span)

`span` is like `string_view` but for any contiguous sequence.

```cpp
// BAD: Copies vector
void process(std::vector<int> data) { /* ... */ }

// BETTER: Takes const reference
void process(const std::vector<int>& data) { /* ... */ }

// BEST: Takes span (works with vector, array, C array, etc.)
void process(std::span<const int> data) { /* ... */ }

// Usage
std::vector<int> vec = {1, 2, 3, 4, 5};
int arr[] = {1, 2, 3, 4, 5};
std::array<int, 5> stdarr = {1, 2, 3, 4, 5};

process(vec);      // Works
process(arr);      // Works
process(stdarr);   // Works
process({1,2,3});  // Works with initializer list
```

### 6.5 In-Place Parsing

Instead of copying data into parsed structures, point into the original buffer.

```cpp
// Traditional parsing (copies data)
struct ParsedPacket {
    std::string src_ip;
    std::string dst_ip;
    std::vector<uint8_t> payload;
};

ParsedPacket parse_traditional(const uint8_t* data, size_t len) {
    ParsedPacket pkt;
    pkt.src_ip = std::string(data + 12, 4);     // Copy
    pkt.dst_ip = std::string(data + 16, 4);     // Copy
    pkt.payload = std::vector(data + 20, data + len);  // Copy
    return pkt;
}

// Zero-copy parsing (pointers into original buffer)
struct ParsedPacketView {
    const uint8_t* raw;         // Pointer to original buffer
    size_t raw_len;
    
    // Views into raw buffer (no copies)
    const uint8_t* src_ip() const { return raw + 12; }
    const uint8_t* dst_ip() const { return raw + 16; }
    std::span<const uint8_t> payload() const { 
        return {raw + 20, raw_len - 20}; 
    }
};

ParsedPacketView parse_zerocopy(const uint8_t* data, size_t len) {
    return {data, len};  // Just stores pointers, no copying
}
```

### 6.6 Move Semantics

Move semantics allow transferring ownership of resources without copying.

```cpp
// Before C++11: Expensive copy
std::vector<int> create_large_vector() {
    std::vector<int> result(10000000);
    std::iota(result.begin(), result.end(), 0);
    return result;  // COPIES 10 million integers (before RVO)
}

// With move semantics: Cheap transfer
std::vector<int> create_large_vector() {
    std::vector<int> result(10000000);
    std::iota(result.begin(), result.end(), 0);
    return result;  // MOVES (or RVO) - just pointer swap
}

// Explicit move
std::vector<int> source = create_large_vector();
std::vector<int> dest = std::move(source);  // source is now empty
// Only moved 3 pointers (data, size, capacity), not 10M integers
```

#### Implementing Move Semantics

```cpp
class Buffer {
    uint8_t* data_;
    size_t size_;
    
public:
    // Move constructor
    Buffer(Buffer&& other) noexcept
        : data_(other.data_), size_(other.size_) {
        other.data_ = nullptr;  // Leave other in valid but empty state
        other.size_ = 0;
    }
    
    // Move assignment
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data_;           // Free our old data
            data_ = other.data_;      // Take other's data
            size_ = other.size_;
            other.data_ = nullptr;    // Leave other empty
            other.size_ = 0;
        }
        return *this;
    }
    
    // Copy operations deleted - buffer is move-only
    Buffer(const Buffer&) = delete;
    Buffer& operator=(const Buffer&) = delete;
};
```

### 6.7 Reference Counting with Copy-on-Write

For large data that's usually read but occasionally modified, copy-on-write defers copying until necessary.

```cpp
class CowString {
    struct Data {
        std::atomic<int> refcount{1};
        size_t size;
        char chars[];  // Flexible array member
    };
    
    Data* data_;
    
    void detach() {
        if (data_->refcount > 1) {
            // Multiple owners - make our own copy
            Data* new_data = allocate(data_->size);
            memcpy(new_data->chars, data_->chars, data_->size);
            data_->refcount--;
            data_ = new_data;
        }
    }
    
public:
    CowString(const CowString& other) : data_(other.data_) {
        data_->refcount++;  // Share, don't copy
    }
    
    char& operator[](size_t i) {
        detach();  // Copy only when modifying
        return data_->chars[i];
    }
    
    const char& operator[](size_t i) const {
        return data_->chars[i];  // No copy needed for read
    }
};
```

**Note**: Modern `std::string` implementations typically don't use COW due to thread-safety overhead.

### 6.8 Memory-Mapped I/O

Memory mapping lets you access file contents as if they were in memory, with the OS handling the actual I/O.

```cpp
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

class MemoryMappedFile {
    void* data_;
    size_t size_;
    int fd_;
    
public:
    MemoryMappedFile(const char* path) {
        fd_ = open(path, O_RDONLY);
        
        // Get file size
        struct stat st;
        fstat(fd_, &st);
        size_ = st.st_size;
        
        // Map file into memory
        data_ = mmap(nullptr, size_, PROT_READ, MAP_PRIVATE, fd_, 0);
    }
    
    ~MemoryMappedFile() {
        munmap(data_, size_);
        close(fd_);
    }
    
    std::span<const uint8_t> view() const {
        return {static_cast<uint8_t*>(data_), size_};
    }
};

// Usage
MemoryMappedFile config("config.json");
auto data = config.view();  // No copying - directly access file contents
parse_json(data);           // Parse in-place
```

### 6.9 sendfile() and splice()

For network I/O, the kernel provides zero-copy system calls.

```cpp
#include <sys/sendfile.h>

// Traditional file→socket transfer
void send_file_traditional(int socket, int file) {
    char buffer[4096];
    ssize_t bytes;
    while ((bytes = read(file, buffer, sizeof(buffer))) > 0) {
        write(socket, buffer, bytes);  // Two copies: file→userspace→socket
    }
}

// Zero-copy file→socket transfer
void send_file_zerocopy(int socket, int file) {
    struct stat st;
    fstat(file, &st);
    sendfile(socket, file, nullptr, st.st_size);  // Kernel does it directly
}
```

With `sendfile()`:
- Data goes directly from file page cache to network buffer
- Never enters user space
- CPU does almost no work (DMA handles it)

### 6.10 Scatter-Gather I/O (vectored I/O)

Write multiple non-contiguous buffers in a single system call, avoiding the need to copy them into one contiguous buffer.

```cpp
#include <sys/uio.h>

void send_http_response(int socket, const char* status, const char* headers, 
                        const char* body, size_t body_len) {
    // Traditional: copy everything into one buffer, then send
    // Zero-copy: send multiple buffers in one call
    
    struct iovec iov[3];
    iov[0].iov_base = (void*)status;
    iov[0].iov_len = strlen(status);
    iov[1].iov_base = (void*)headers;
    iov[1].iov_len = strlen(headers);
    iov[2].iov_base = (void*)body;
    iov[2].iov_len = body_len;
    
    writev(socket, iov, 3);  // All three buffers sent, no copying
}
```

### 6.11 DPDK and Zero-Copy Networking

For ultimate performance, bypass the kernel entirely:

```cpp
// With DPDK, packets are DMA'd directly into user-space memory
// No kernel copies at all

void receive_packets() {
    rte_mbuf* packets[32];
    uint16_t nb_rx = rte_eth_rx_burst(port, queue, packets, 32);
    
    for (int i = 0; i < nb_rx; ++i) {
        // packets[i]->buf_addr points to packet data
        // This is the actual NIC DMA buffer - no copies!
        uint8_t* data = rte_pktmbuf_mtod(packets[i], uint8_t*);
        process_packet(data, packets[i]->data_len);
    }
}
```

### 6.12 Zero-Copy Design Patterns Summary

| Pattern | Technique | Use Case |
|---------|-----------|----------|
| View types | `string_view`, `span` | Passing substrings/subranges |
| In-place parsing | Pointers into buffer | Protocol parsing |
| Move semantics | `std::move` | Transferring ownership |
| Memory mapping | `mmap` | Large file access |
| Kernel bypass | DPDK, io_uring | Network/disk I/O |
| Scatter-gather | `writev`, `readv` | Multi-buffer I/O |
| sendfile | `sendfile`, `splice` | File→socket transfer |
| Reference counting | `shared_ptr`, COW | Shared read-only data |

## Summary

Memory management in C++ gives you power and responsibility:

1. **Stack vs Heap**: Use stack for speed and automatic lifetime; use heap for flexibility and sharing. Know the tradeoffs.

2. **Custom Allocators**: When the standard allocator is too slow or causes fragmentation, design your own: pools for fixed-size, slabs for size classes, arenas for bulk-free patterns.

3. **Ownership Models**: Be explicit about who owns what. Stack ownership for locals, unique ownership for exclusive control, shared ownership only when truly needed.

4. **Smart Pointers**: `unique_ptr` for single ownership (zero overhead), `shared_ptr` for shared ownership (reference counting overhead), raw pointers for non-owning references.

5. **Fragmentation**: Prevent it through fixed-size allocations, size classes, object reuse, and arena allocation. Measure it to know if you have a problem.

6. **Zero-Copy**: Every copy costs. Use views, in-place parsing, move semantics, and system-level zero-copy APIs to minimize data movement.

These concepts interconnect: a well-designed system uses arenas (custom allocator) that free together (ownership model) to process data in-place (zero-copy), avoiding both fragmentation and unnecessary copies.
