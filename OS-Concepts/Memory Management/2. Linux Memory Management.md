# 1. Big Picture: What Linux Memory Management Solves

Linux memory management must:

1. Give **each process the illusion of a private, contiguous address space**
2. Efficiently share physical memory between processes
3. Handle memory pressure (reclaim, swap, OOM)
4. Be fast (page cache, TLB, NUMA)
5. Be safe (isolation, permissions)

Linux achieves this using:

* **Virtual Memory**
* **Paging**
* **Demand allocation**
* **Page cache**
* **Reclaim mechanisms**

> **Interview one-liner**
> *Linux uses demand-paged virtual memory with per-process virtual address spaces backed by physical pages, managed through page tables and kernel reclaim mechanisms.*

---

# 2. Virtual Address Space (Very Important)

## Process Virtual Memory Layout (Typical)

```
High Address
+---------------------+
| Kernel Space        |  (shared, not accessible in user mode)
+---------------------+
| Stack               |  (grows downward)
+---------------------+
| Memory Mappings     |  (mmap, shared libs, files)
+---------------------+
| Heap                |  (grows upward)
+---------------------+
| BSS                 |  (zero-initialized globals)
+---------------------+
| Data                |  (initialized globals)
+---------------------+
| Text                |  (code, read-only)
+---------------------+
Low Address
```

### Key Points

* **Each process has its own virtual address space**
* Same virtual address ≠ same physical address
* Kernel space is mapped into every process (but protected)

> **Interview question**:
> *How does Linux isolate processes but still allow kernel access?*
> **Answer**: Through page table permissions (user vs supervisor mode).

---

# 3. Paging Basics

## Page Size

* Typically **4 KB**
* Huge pages: **2 MB, 1 GB**

## Why Paging?

* Avoid fragmentation
* Efficient swapping
* Fine-grained protection

## Page Table Hierarchy (x86-64)

```
PGD → PUD → PMD → PTE → Physical Page
```

Each level:

* Maps part of virtual address
* Helps reduce memory overhead

> **Interview favorite**:
> *Why multi-level page tables?*
> → Sparse address spaces without allocating huge contiguous tables.

---

# 4. Address Translation (Critical for Interviews)

### Virtual → Physical Translation Steps

1. CPU issues virtual address
2. **TLB lookup**
3. If miss → page table walk
4. PTE gives physical frame + permissions
5. Access physical memory

### TLB (Translation Lookaside Buffer)

* Cache of recent translations
* Extremely performance-critical

> **Interview trap**:
> *Why are TLB misses expensive?*
> → Multiple memory accesses + possible page faults.

---

# 5. Page Faults (Very Important)

## Types of Page Faults

### 1. Minor (Soft) Page Fault

* Page is in RAM but not mapped yet
* Example: first access to a malloc’d page

### 2. Major (Hard) Page Fault

* Page must be loaded from disk
* Example: mmap’d file or swapped page

### 3. Invalid Page Fault

* Accessing illegal memory → **SIGSEGV**

> **Interview Q**:
> *Does malloc allocate physical memory immediately?*
> **Answer**: No. Memory is allocated on first access (demand paging).

---

# 6. Heap, malloc, and brk vs mmap

## How `malloc()` Works

Small allocations:

* Uses **brk()** → grows heap

Large allocations:

* Uses **mmap()** → separate VM area

```
malloc(64 KB)  → heap (brk)
malloc(10 MB)  → mmap
```

### Freeing Memory

* `free()` does **not always return memory to OS**
* Freed memory stays in process heap

> **Interview trap**:
> *Why does RSS not decrease after free()?*
> → Memory returned to allocator, not kernel.

---

# 7. mmap() (Very Interview-Relevant)

### mmap Uses

* File-backed memory
* Shared memory
* Large allocations
* DPDK / zero-copy IO

### MAP_PRIVATE vs MAP_SHARED

| Flag        | Behavior                  |
| ----------- | ------------------------- |
| MAP_PRIVATE | Copy-on-Write             |
| MAP_SHARED  | Changes visible to others |

### Copy-on-Write (COW)

* After `fork()`, pages shared
* On write → page copied

> **Interview Q**:
> *Why is fork() cheap in Linux?*
> → Copy-on-write memory sharing.

# 9. Page Cache (EXTREMELY IMPORTANT)

## What is Page Cache?

* Cached file data in RAM
* Shared across processes

### Read Flow

```
read() → page cache → disk (if miss)
```

### Write Flow

```
write() → page cache → marked dirty → flushed later
```

> **Interview Q**:
> *Why is free memory not really free in Linux?*
> → Used for page cache.

Command:

```bash
free -h
```

Look at:

* **available**, not **free**

---

# 10. Memory Reclaim & Swapping

## When Memory is Low

1. Drop clean page cache
2. Reclaim anonymous pages
3. Swap out pages
4. OOM killer

### Swappiness

* `/proc/sys/vm/swappiness`
* Controls tendency to swap

> **Interview Q**:
> *What gets reclaimed first: page cache or heap?*
> → Clean page cache first.

---

# 11. OOM Killer (Classic Interview Topic)

* Triggered when kernel cannot allocate memory
* Scores processes based on:

  * RSS
  * oom_score_adj
* Kills “least important” process

Check:

```bash
cat /proc/<pid>/oom_score
```

> **Interview Q**:
> *Can OOM happen even if swap exists?*
> → Yes (fragmentation, limits, memcg).

# 12. NUMA (Important for High-Performance / Telecom)

* Non-Uniform Memory Access
* Memory closer to some CPUs

Commands:

```bash
numactl --hardware
numastat
```

> **Interview Q**:
> *Why is NUMA important for DPDK?*
> → Cross-node memory access is slower.

# 14. Memory Leaks vs Fragmentation

## Memory Leak

* Lost references
* RSS grows continuously

## Fragmentation

* Free memory exists but not contiguous

Tools:

* `valgrind`
* `heaptrack`
* `perf`
* `/proc/meminfo`

# 15. Common Interview Questions (With Sharp Answers)

### Q1: Why does Linux overcommit memory?

**A**: Allows better utilization; physical memory allocated on demand.

---

### Q2: What is Copy-on-Write?

**A**: Pages shared until written; then duplicated.

---

### Q3: Difference between anonymous and file-backed pages?

**A**:

* Anonymous → heap, stack
* File-backed → mmap’d files, shared libs

---

### Q4: What happens during `fork()`?

**A**:

* Page tables copied
* Physical pages shared (COW)

---

### Q5: Why is mmap preferred for large allocations?

**A**:

* Avoids heap fragmentation
* Can be returned to OS

---

# 16. Interview-Ready Summary (Memorize This)

> Linux uses demand-paged virtual memory. Each process has a private virtual address space mapped to physical pages via multi-level page tables. Memory is allocated lazily, shared via copy-on-write, cached aggressively using the page cache, and reclaimed under pressure through page reclaim, swapping, or OOM killing. Performance hinges on TLB efficiency, NUMA locality, and minimizing page faults.
