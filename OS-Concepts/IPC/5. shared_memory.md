# 1️⃣ What shared memory really is (intuition first)

> **Shared memory means two (or more) processes map the same physical memory pages into their virtual address spaces.**

So instead of:

```text
Process A → kernel → copy → Process B
```

You get:

```text
Process A ↔ same memory ↔ Process B
```

There is **no data copy once mapping is done**.

From the OS point of view:

* One physical memory region
* Multiple virtual mappings
* Same cache lines

---

# 2️⃣ Two ways to do shared memory in Linux

| Method                 | Status | Recommendation |
| ---------------------- | ------ | -------------- |
| SysV SHM (`shmget`)    | Legacy | ❌ Avoid        |
| POSIX SHM (`shm_open`) | Modern | ✅ Use this     |

We’ll use **POSIX shared memory**.

---

# 3️⃣ Necessary system calls (the minimal set)

### Creation & mapping

```c
shm_open()   // create or open shared memory object
ftruncate() // set size
mmap()      // map into virtual memory
```

### Cleanup

```c
munmap()
shm_unlink()
```

That’s it. Everything else (locks, queues, counters) is **your responsibility**.

# 4️⃣ Simple example: two processes sharing an integer

### 📌 Scenario

* Process A writes a number
* Process B reads it

⚠️ **This example intentionally skips synchronization first** so you see the core idea.

---

## 🔹 Writer process

```c
// shm_writer.c
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <stdio.h>

#define SHM_NAME "/demo_shm"

int main() {
    int fd = shm_open(SHM_NAME, O_CREAT | O_RDWR, 0666);
    ftruncate(fd, sizeof(int));

    int *shared = mmap(NULL, sizeof(int),
                       PROT_READ | PROT_WRITE,
                       MAP_SHARED, fd, 0);

    *shared = 42;
    printf("Writer wrote: %d\n", *shared);

    sleep(10); // keep mapping alive

    munmap(shared, sizeof(int));
    close(fd);
    return 0;
}
```

---

## 🔹 Reader process

```c
// shm_reader.c
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <stdio.h>

#define SHM_NAME "/demo_shm"

int main() {
    int fd = shm_open(SHM_NAME, O_RDONLY, 0666);

    int *shared = mmap(NULL, sizeof(int),
                       PROT_READ,
                       MAP_SHARED, fd, 0);

    printf("Reader read: %d\n", *shared);

    munmap(shared, sizeof(int));
    close(fd);

    shm_unlink(SHM_NAME); // cleanup
    return 0;
}
```

---

## 🔹 Build & run

```bash
gcc shm_writer.c -o writer
gcc shm_reader.c -o reader

./writer
./reader
```

# 5️⃣ The BIG missing piece: synchronization

> **Shared memory only shares bytes, not coordination.**

Without synchronization, you get:

* Race conditions
* Torn reads
* Cache incoherency bugs

---

## 🔐 Common synchronization options

| Mechanism                        | Use case          |
| -------------------------------- | ----------------- |
| `pthread_mutex` (process-shared) | General           |
| POSIX semaphores                 | Producer–consumer |
| Atomic variables                 | Counters, flags   |
| Futex                            | Advanced          |

### Example (process-shared mutex)

```c
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
```

In real systems:

> **Shared memory + mutex/lock is one design unit**

# 6️⃣ Why shared memory is fast (OS & CPU view)

* No kernel copies after setup
* CPU cache coherence does the work
* No syscalls per access
* No context switching

This is **the fastest IPC** available on Linux.

---

# 7️⃣ When shared memory is a good choice

### ✅ Ideal use cases

* High-throughput data
* Low-latency pipelines
* Media buffers (audio/video)
* Packet processing
* Stats aggregation

Examples:

* RTP media plane
* Audio recording buffers
* DPDK rings
* Producer–consumer queues

---

# 8️⃣ When shared memory is a bad idea

### ❌ Avoid when

* Data size is small
* Message semantics matter
* Debuggability matters
* Fault isolation is important
* You want simplicity

Shared memory:

* Is hard to debug
* Fails catastrophically on bugs
* Requires discipline

# 9️⃣ Shared memory vs other IPC mechanisms

### 🔹 Shared memory vs Unix Domain Sockets

| Aspect          | Shared Memory | UDS        |
| --------------- | ------------- | ---------- |
| Copies          | ❌ None        | ✅ Yes      |
| Speed           | 🔥 Fastest    | Fast       |
| Complexity      | High          | Medium     |
| Message framing | ❌ Manual      | ✅ Built-in |
| Safety          | Low           | High       |

👉 **UDS for control plane, SHM for data plane**

---

### 🔹 Shared memory vs Message Queues

| Aspect           | SHM  | MQ   |
| ---------------- | ---- | ---- |
| Throughput       | High | Low  |
| Message ordering | ❌    | ✅    |
| Persistence      | ❌    | ✅    |
| Ease of use      | Hard | Easy |

---

### 🔹 Shared memory vs Pipes

| Aspect    | SHM       | Pipe           |
| --------- | --------- | -------------- |
| Direction | Any       | One-way        |
| Speed     | Faster    | Slower         |
| Use case  | Bulk data | Simple streams |

# 🔟 Typical real-world pattern (important)

Shared memory is **never used alone**.

Typical design:

```text
Control channel (UDS)
   ↓
Shared memory region
   ↓
Sync primitives (mutex / semaphore)
```

This pattern is used in:

* Media servers
* Databases
* Browsers
* Game engines

---

# 1️⃣1️⃣ Key pitfalls you must remember

* Forgetting synchronization
* False sharing (cache line fights)
* No bounds checking
* Poor cleanup (`shm_unlink`)
* Versioning issues on struct layout

---

# 1️⃣2️⃣ Interview-grade summary

> Shared memory allows multiple processes to access the same physical memory, eliminating kernel data copies and achieving the highest IPC performance. However, it provides no synchronization or message semantics, making it complex and error-prone. It is best suited for high-throughput data paths and is typically paired with sockets or signals for control.

---

# Final takeaway (one sentence)

> **Shared memory is a performance weapon — powerful, dangerous, and worth using only when you truly need speed.**
