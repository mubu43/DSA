## The core problem condition variables solve

> **“One thread needs to wait until another thread makes something true — without wasting CPU and without races.”**

Key requirements:

1. Waiting must be **efficient** (no busy looping)
2. State must be **protected** (no races)
3. Wakeups must be **correct** (no missed signals)

A mutex alone cannot do this cleanly.

---

## A BAD approach (why condition variables exist)

### Scenario

* Thread A waits until `data_ready == true`
* Thread B sets `data_ready = true`

### Naive solution (busy waiting ❌)

```cpp
while (!data_ready) {
    // spin
}
```

Problems:

* Wastes CPU
* Still races without a mutex
* Unscalable

---

## A REALISTIC example: Bounded Producer–Consumer Queue

This example demonstrates:

* Why **mutex + condition variable** are both required
* Waiting on **two different conditions**
* Why `wait()` must re-check conditions

---

### Problem statement

* Producer thread produces messages
* Consumer thread consumes messages
* Queue size is limited (bounded buffer)

Conditions:

* Producer must wait if queue is full
* Consumer must wait if queue is empty

---

## Correct solution using condition variables

### Shared state

```cpp
#include <queue>
#include <mutex>
#include <condition_variable>

std::queue<int> q;
const size_t MAX_SIZE = 3;

std::mutex mtx;
std::condition_variable cv_not_empty;
std::condition_variable cv_not_full;
```

---

### Producer

```cpp
void producer() {
    for (int i = 1; i <= 10; ++i) {
        std::unique_lock<std::mutex> lock(mtx);

        cv_not_full.wait(lock, [] {
            return q.size() < MAX_SIZE;
        });

        q.push(i);
        std::cout << "Produced " << i << std::endl;

        cv_not_empty.notify_one();
    }
}
```

---

### Consumer

```cpp
void consumer() {
    for (int i = 1; i <= 10; ++i) {
        std::unique_lock<std::mutex> lock(mtx);

        cv_not_empty.wait(lock, [] {
            return !q.empty();
        });

        int val = q.front();
        q.pop();
        std::cout << "Consumed " << val << std::endl;

        cv_not_full.notify_one();
    }
}
```

---

## Let’s deeply understand what’s happening

### 1. Why `unique_lock` and not `lock_guard`?

* `cv.wait()` needs to:

  * Unlock the mutex while sleeping
  * Re-lock it when woken up

`lock_guard` **cannot unlock**, so it won’t work.

---

### 2. What `cv.wait(lock, predicate)` really does

Conceptually:

```cpp
while (!predicate()) {
    unlock(mtx);
    sleep();
    lock(mtx);
}
```

Important:

* Mutex is **released while waiting**
* Mutex is **re-acquired before returning**
* Predicate is checked **again**

---

### 3. Why the predicate is mandatory

#### Scenario: Spurious wakeup

* Thread wakes up
* Condition is still false
* Without re-check → bug

Hence:

```cpp
cv.wait(lock, condition);
```

is equivalent to:

```cpp
while (!condition) {
    cv.wait(lock);
}
```

---

### 4. Why notify happens *after* modifying state

Correct order:

1. Lock mutex
2. Modify shared state
3. Unlock mutex (or let scope end)
4. Notify waiting thread

This ensures:

* Woken thread sees **consistent state**
* No missed signals

## Timeline visualization

### Consumer waiting

```
Consumer:
  lock(mtx)
  queue empty → wait
  ├─ unlock(mtx)
  ├─ sleep
  └─ wake → lock(mtx)
```

### Producer producing

```
Producer:
  lock(mtx)
  push item
  unlock(mtx)
  notify consumer
```

---

## Why mutex alone cannot solve this

With mutex only:

* Consumer must poll
* Producer cannot wake consumer efficiently

Condition variable adds:

* **Sleep + wake**
* **No busy waiting**
* **Correct ordering**

---

## Very important mental model

> **Condition variable waits on *state*, not on events**

You don’t wait for “notify”.
You wait for “queue is not empty”.

That’s why this is correct:

```cpp
cv.wait(lock, [] { return !q.empty(); });
```

And this is wrong thinking:

```cpp
cv.wait(lock); // "wait for notify"
```

---

## Common mistakes (worth memorizing)

### ❌ Waiting without holding mutex

Undefined behavior.

### ❌ Using `if` instead of `while`

Breaks on spurious wakeups.

### ❌ Not protecting the condition with mutex

Race conditions.

### ❌ Calling `notify()` before changing state

Leads to missed wakeups.
