## 1. What problem do atomics solve?

Atomics solve **data races on small shared variables** *without using locks*.

A **data race** happens when:

* Two threads access the same variable
* At least one write
* No synchronization

Example race:

```cpp
int counter = 0;

void f() {
    counter++;  // NOT thread-safe
}
```

Two threads doing this can:

* Read the same value
* Write back the same incremented value
* Lose updates

---

## 2. What does “atomic” really mean?

An atomic operation is:

* **Indivisible** (cannot be observed halfway)
* **Synchronized** (visible correctly across threads)

### Important distinction

Atomic does NOT mean:

* Faster
* Lock-free in all cases
* No ordering issues automatically solved

Atomic means:

> “This read or write behaves as a single, well-defined operation across threads.”

## 3. Simple example: Atomic counter

```cpp
#include <atomic>
#include <thread>

std::atomic<int> counter{0};

void increment() {
    for (int i = 0; i < 1000; ++i) {
        counter++;
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);

    t1.join();
    t2.join();

    // Always 2000
    std::cout << counter.load() << std::endl;
}
```

Why this works:

* `counter++` is an atomic read-modify-write
* No lost updates
* No mutex needed

---

## 4. How atomics fix concurrency issues (under the hood)

Atomics give you **two guarantees**:

### 1. Atomicity

Operations like:

* `load`
* `store`
* `fetch_add`
  are indivisible.

No other thread can see an intermediate state.

---

### 2. Visibility

Writes done by one thread become **visible** to other threads in a well-defined way.

Without atomics, compilers and CPUs may:

* Reorder instructions
* Cache values in registers
* Never flush writes to memory

Atomics prevent these hazards.

## 5. Example: Atomic flag (very common)

### Problem

One thread signals another thread to stop.

### WRONG (data race)

```cpp
bool stop = false;

void worker() {
    while (!stop) {
        // work
    }
}
```

### CORRECT (atomic flag)

```cpp
std::atomic<bool> stop{false};

void worker() {
    while (!stop.load()) {
        // work
    }
}

void stop_worker() {
    stop.store(true);
}
```

Why this matters:

* Ensures visibility across cores
* Prevents infinite loops due to cached reads

## 6. Atomics vs mutex (this is critical)

### Atomics are good when:

* Shared data is **small** (int, pointer, flag)
* Operation is **simple** (increment, check, set)
* No complex invariants

### Mutex is required when:

* Multiple variables must be updated together
* You need consistency across a data structure
* You need blocking / waiting

### Example where atomic is NOT enough

```cpp
struct Session {
    int packets;
    int bytes;
};

Session s;
```

You cannot safely update both fields atomically together using atomics alone.

---

## 7. Performance myth: “Atomics are always faster”

Not always true.

* Atomics may use:

  * Cache line locks
  * Memory fences
* Heavy contention → worse than mutex
* Spin-based behavior → CPU burn

Rule of thumb:

> Use atomics for **low contention**, **simple state**.

---

## 8. Memory ordering (just enough to be useful)

By default, atomics use **sequential consistency**.

This means:

> All threads see atomic operations in the same order.

Example (default, safe):

```cpp
counter.store(1);
int x = counter.load();
```

You’ll often see:

```cpp
counter.store(1, std::memory_order_relaxed);
```

### When to use relaxed ordering?

Only when:

* You need atomicity
* You don’t care about ordering

Example: statistics counters

```cpp
packet_count.fetch_add(1, std::memory_order_relaxed);
```

## 9. Atomic pointer example (lock-free signaling)

```cpp
std::atomic<int*> ptr{nullptr};

void producer() {
    int* p = new int(42);
    ptr.store(p, std::memory_order_release);
}

void consumer() {
    int* p;
    while ((p = ptr.load(std::memory_order_acquire)) == nullptr) {
        // wait
    }
    std::cout << *p << std::endl;
}
```

This ensures:

* Memory written before `store` is visible after `load`

(This is how many lock-free structures work internally.)

---

## 10. Atomics vs condition variables

Atomics:

* Don’t block
* Spin or poll
* Best for **flags, counters**

Condition variables:

* Block efficiently
* Best for **waiting on state changes**

You often use them together:

* Atomic fast path
* Condition variable slow path

---

## 11. Real-world usage patterns (systems / telecom)

Common atomic use cases:

* Call counters
* Packet counters
* Reference counts
* State flags (`RUNNING`, `STOPPING`)
* Lock-free queues (advanced)

Common mutex use cases:

* Call/session objects
* Maps, vectors
* State machines

---

## Final mental model

> **Atomics protect individual variables.
> Mutexes protect invariants.
> Condition variables coordinate threads.**
