### 1. Concurrency vs Parallelism

🖥️ Intuitive Example: Using a Computer

Imagine you’re using your laptop:

    You’re streaming music (Spotify), browsing the web (Chrome), and writing a document (Word) all at once.

✅ Concurrency:
Even if your CPU has only one core, your operating system rapidly switches between these apps — giving each a tiny slice of time. To you, it feels like they’re all running together, but they’re actually taking turns. This is concurrency: managing multiple tasks that appear simultaneous but aren’t truly executing at the exact same instant.

✅ Parallelism:
If your CPU has 4 cores, Spotify might run on Core 1, Chrome on Core 2, and Word on Core 3 — all at the exact same time. That’s parallelism: true simultaneous execution.

    💡 Key Insight:  

        All parallelism is concurrent, but not all concurrency is parallel.  
        Concurrency = structure (handling multiple things); Parallelism = execution (doing multiple things at once).

| Aspect              | Concurrency                              | Parallelism                              |
|---------------------|------------------------------------------|------------------------------------------|
| Meaning             | **Dealing with** multiple tasks          | **Doing** multiple tasks **at the same time** |
| Core idea           | Make progress on multiple things         | Actually execute multiple things simultaneously |
| Requires            | Good task switching & time-sharing       | Multiple CPU cores / execution units     |
| Number of cores needed | Can be 1 core                           | Needs ≥ 2 cores to be true parallelism   |
| Real-world analogy  | One cook preparing 3 dishes              | Three cooks each preparing one dish      |

**Classic intuitive example (restaurant kitchen)**:

- **Concurrency only** (single-core chef):  
  The chef is stir-frying vegetables → quickly moves to check the soup → chops some herbs → flips the steak → adds salt to soup → etc.  
  → Multiple dishes are **in progress**, but only **one thing is actually cooking** at any instant.

- **Concurrency + Parallelism** (multi-core / multiple chefs):  
  Chef A is stir-frying, Chef B is grilling steak, Chef C is reducing sauce — all happening **truly at the same time**.

Most programs we write are **concurrent** programs.  
Only when we actually get speedup from using multiple cores do we have **parallelism**.

### 2. Processes vs Threads

| Property                        | Process                                      | Thread (within a process)                     |
|-------------------------------|----------------------------------------------|------------------------------------------------|
| OS entity                     | Independent heavyweight entity               | Lightweight entity owned by a process          |
| Has its own                   | Address space, file descriptors, signal handlers, etc. | Shares address space, file descriptors, etc. with other threads in same process |
| Memory overhead               | High (separate page tables, full copy of code+data+heap+stack) | Very low (just stack + thread control block) |
| Creation time                 | Slow (~1–10 ms)                              | Fast (~1–100 µs)                               |
| Context switch time           | Expensive                                    | Much cheaper                                   |
| Communication between them    | IPC (pipes, sockets, shared memory, message queues…) | Direct memory access (very fast)               |
| Failure impact                | One process crash usually doesn't kill others | One thread crash usually kills the whole process |
| Isolation                     | Strong (memory protected)                    | Weak (threads can corrupt each other’s memory) |

**How the OS sees them differently**  
- Process = independent scheduling entity + independent virtual memory context  
- Thread = scheduling entity that **shares** the virtual memory context of its parent process

**Data structure comparison** (simplified view of what kernel maintains)

| Field                          | Process Control Block (PCB) | Thread Control Block (TCB) |
|-------------------------------|-----------------------------|-----------------------------|
| Process / Thread ID           | Yes                         | Yes                         |
| CPU registers                 | Yes (when not running)      | Yes                         |
| Program counter               | Yes                         | Yes                         |
| Stack pointer                 | Yes                         | Yes (each thread has own)   |
| Virtual memory info (page tables) | Yes (per process)        | Shared                      |
| Open file table               | Yes                         | Shared                      |
| Heap pointer / malloc state   | Yes                         | Shared                      |
| Parent process pointer        | Yes                         | Usually points to process   |
| Scheduling priority / quantum | Yes                         | Yes (can be per-thread)     |
| Signal handlers               | Yes                         | Shared (usually)            |

**Bottom line memory picture**:

```
Process A
├── Address space
│   ├── Code
│   ├── Heap (shared)
│   ├── Global data (shared)
│   ├── File descriptors (shared)
│   └── ...
├── Thread 1 ── private stack + registers + TCB
├── Thread 2 ── private stack + registers + TCB
└── Thread 3 ── private stack + registers + TCB
```

### 3. Thread Creation and Management – Minimal Example (C++)

```cpp
#include <iostream>
#include <thread>
#include <chrono>

void worker(int id) {
    std::cout << "Worker " << id << " starting...\n";
    std::this_thread::sleep_for(std::chrono::milliseconds(1500));
    std::cout << "Worker " << id << " finished.\n";
}

int main() {
    std::cout << "Main starting\n";

    // Create threads (they start immediately in most implementations)
    std::thread t1(worker, 1);
    std::thread t2(worker, 2);

    std::cout << "Main created threads\n";

    // Wait for both to finish (join = "wait for me to complete")
    t1.join();
    t2.join();

    std::cout << "Main ending\n";
    return 0;
}
```

Typical output:
```
Main starting
Main created threads
Worker 1 starting...
Worker 2 starting...
Worker 1 finished.
Worker 2 finished.
Main ending
```

Quick cheat-sheet:

Operation       | C++                           |
----------------|-------------------------------|
Create          | `std::thread t(func)`         |
Start           | automatic on construction     |
Wait for finish | `t.join()`                    |
Detach (fire & forget) | `t.detach()`           |
Current thread  | `std::this_thread::get_id()`  |

### 4. Thread Lifecycle States

### Thread States

```
New → Runnable → Running → Blocked/Waiting → Runnable → Terminated
```

---

### State Descriptions

#### 1. New

* Thread object created
* Not yet scheduled

Example:

```cpp
std::thread t(worker); // New → Runnable
```

---

#### 2. Runnable

* Ready to run
* Waiting for CPU time

> OS scheduler decides *when* it runs

---

#### 3. Running

* Thread is actively executing on CPU

---

#### 4. Blocked / Waiting

* Thread cannot continue
* Waiting for:

  * I/O
  * Mutex / lock
  * Condition variable
  * `join()`

Example:

```cpp
t.join(); // main thread enters waiting state
```

---

#### 5. Terminated

* Thread function has completed
* Resources cleaned up (after join)

---

### Lifecycle Visualization

```
[New]
   ↓
[Runnable] ←─────────────┐
   ↓                     │
[Running] ──→ [Blocked] ─┘
   ↓
[Terminated]
```

---

Common states (POSIX / Java / .NET style):

State              | Meaning                                                                 | Can consume CPU?
-------------------|-----------------------------------------------------------------------|---------------
**New**            | Created but `start()` not yet called                                  | No
**Runnable**       | Ready to run, waiting in scheduler queue                              | No (but soon)
**Running**        | Currently executing on a CPU core                                     | Yes
**Blocked**        | Waiting for a resource (I/O, lock, mutex, condition variable…)        | No
**Waiting**        | Explicitly waiting (wait(), join(), sleep(), LockSupport.park()…)     | No
**Timed Waiting**  | Waiting with timeout (sleep(ms), wait(timeout), timed join…)          | No
**Terminated**     | Finished execution (returned from run() / thread function)            | No

Most common transitions people forget:

- `sleep()` → **Timed Waiting**
- `join()` → **Waiting**
- `wait()` on condition variable / monitor → **Waiting**
- Trying to acquire a contended lock → **Blocked**
- Thread finishes → **Terminated** (resources usually cleaned up after all references gone)

### 5. Multithreading Terminologies

1. **Critical Section**: A segment of code that accesses shared resources (memory, files, variables) and must not be executed by more than one thread at a time to prevent data inconsistency.
2. **Race Condition**: An undesirable situation where multiple threads attempt to access/modify shared data simultaneously, and the final outcome depends on the unpredictable timing of execution.
3. **Mutual Exclusion (Mutex)**: A locking mechanism that ensures only one thread can access a critical section or shared resource at a time.
4. **Semaphore**: A signaling mechanism using a counter to manage access to a shared resource. A Binary Semaphore (value 0 or 1) acts as a mutex, while a Counting Semaphore (value > 1) limits access to a pool of resources.
5. **Lock/Monitor**: A synchronization tool used to protect critical sections, often allowing only one thread to hold the lock at a time.

### 6. Common Concurrency Challenges

1. **Race Conditions**: Situations where multiple threads access and modify shared data simultaneously, leading to inconsistent output.
2. **Deadlocks**: Understanding the four necessary conditions (Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait) that cause threads to block each other indefinitely.
3. **Starvation and Livelock**: When a thread is perpetually denied access to resources or when two threads keep changing states in response to each other without progressing.
4. **Data Inconsistency and Visibility**: Learning how CPU caches can cause threads to see "stale" data.
