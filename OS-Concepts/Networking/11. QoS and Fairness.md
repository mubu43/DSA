## Introduction to Quality of Service

### The Problem

The Internet provides **best-effort service** — no guarantees on:
- Bandwidth
- Delay
- Jitter (delay variance)
- Packet loss

**Question:** Can we do better? Can we provide differentiated service quality to different traffic?

### QoS Goals

| Goal | Description |
|------|-------------|
| **Fairness** | Equitable sharing of resources |
| **Isolation** | Misbehaving flows don't affect others |
| **Guarantees** | Bounded delay, minimum bandwidth |
| **Efficiency** | High utilization of network resources |

## Measuring Fairness

### What is "Fair"?

When N flows share a link of capacity C, **equal sharing** means each gets C/N.

But how do we measure how close a real allocation is to fair?

### Jain's Fairness Index

A quantitative measure of fairness:

$$J(x_1, x_2, ..., x_n) = \frac{\left(\sum_{i=1}^{n} x_i\right)^2}{n \cdot \sum_{i=1}^{n} x_i^2}$$

Where $x_i$ is the allocation to flow $i$.

### Properties of Jain's Index

| Property | Value | Meaning |
|----------|-------|---------|
| **Perfect fairness** | J = 1 | All flows get equal share |
| **Complete unfairness** | J = 1/n | One flow gets everything |
| **Range** | $\frac{1}{n} \leq J \leq 1$ | Always between these bounds |
| **Population independence** | — | Can compare different n values |

### Examples

**Example 1:** Four flows with rates (25, 25, 25, 25)
$$J = \frac{100^2}{4 \times 2500} = \frac{10000}{10000} = 1.0$$ 
(Perfect fairness)

**Example 2:** Four flows with rates (40, 30, 20, 10)
$$J = \frac{100^2}{4 \times (1600+900+400+100)} = \frac{10000}{12000} = 0.833$$

**Example 3:** Four flows with rates (100, 0, 0, 0)
$$J = \frac{100^2}{4 \times 10000} = \frac{10000}{40000} = 0.25 = \frac{1}{4}$$
(Completely unfair)

## Max-Min Fairness

### Definition

An allocation is **max-min fair** if:
1. The minimum allocation is as large as possible
2. Given that, the second-minimum is as large as possible
3. And so on...

**Equivalently:** You cannot increase any flow's allocation without decreasing a flow that already has a smaller (or equal) allocation.

### Algorithm: Water-Filling

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Max-Min Fair Allocation (Water-Filling)               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Start: Equal share to all                                             │
│                                                                         │
│   Capacity ────────────────────────────────── C                        │
│            │                                                            │
│            │    Water level rises...                                    │
│            │    ════════════════════════                               │
│            │    │    │    │    │    │                                  │
│            │    │    │    │    │    │                                  │
│            │    │    │    │    │    │                                  │
│            │    │    │    │    │    │                                  │
│            └────────────────────────────                               │
│                 F1   F2   F3   F4   F5                                  │
│                                                                         │
│   1. Fill equally until some flow is "satisfied" (hits its demand)     │
│   2. Remove that flow, redistribute its excess to remaining flows      │
│   3. Repeat until all flows satisfied or capacity exhausted            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Example: Max-Min Allocation

**Setup:** Link capacity = 10 Gbps, Four flows with demands:
- Flow A: demands 2 Gbps
- Flow B: demands 4 Gbps
- Flow C: demands 5 Gbps
- Flow D: demands 8 Gbps

**Step-by-step:**

| Step | Action | A | B | C | D | Remaining |
|------|--------|---|---|---|---|-----------|
| 1 | Start: try 2.5 each | 2.5 | 2.5 | 2.5 | 2.5 | 0 |
| 2 | A only needs 2, redistribute 0.5 | **2** | 2.67 | 2.67 | 2.67 | 0 |
| 3 | All satisfied to their limit or equal share | **2** | **2.67** | **2.67** | **2.67** | 0 |

Wait, let's redo this more carefully:

| Step | Action | Allocation |
|------|--------|------------|
| 1 | Give each 10/4 = 2.5 | A=2.5, B=2.5, C=2.5, D=2.5 |
| 2 | A only wants 2, gives back 0.5 | A=2.0, extra=0.5 |
| 3 | Distribute 0.5 among B,C,D: +0.167 each | A=2.0, B=2.67, C=2.67, D=2.67 |
| 4 | B only wants 4, C wants 5, D wants 8 | All within limits ✓ |

**Final:** A=2.0, B=2.67, C=2.67, D=2.67 (Total = 10)

### Properties of Max-Min Fairness

| Property | Description |
|----------|-------------|
| **Pareto efficient** | Can't improve one without hurting another |
| **Satisfies small demands** | Flows with small demands get what they need |
| **Share residual** | Excess capacity shared fairly |
| **Unique** | Only one max-min fair allocation exists |

## Traffic Shaping: Token Bucket

### Purpose

**Traffic shaping** controls the rate and burstiness of traffic entering the network.

**Why?** 
- Enforce contracted rates
- Smooth bursty traffic
- Enable admission control and QoS guarantees

### Token Bucket Mechanism

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Token Bucket Model                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                    ┌─────────────────┐                                  │
│       Tokens       │                 │                                  │
│       arrive       │  ┌───────────┐  │                                  │
│       at rate R    │  │  Bucket   │  │                                  │
│          ↓         │  │           │  │  Bucket size = B tokens          │
│         ╔═╗        │  │  [token]  │  │                                  │
│         ║ ║───────►│  │  [token]  │  │                                  │
│         ╚═╝        │  │  [token]  │  │                                  │
│                    │  │  [token]  │  │                                  │
│                    │  └─────┬─────┘  │                                  │
│                    │        │        │                                  │
│                    │        ▼        │                                  │
│   ═════════════════│═══════╳════════│══════════════════►  Output       │
│   Incoming packets │   Gate: 1 token │                                  │
│   (rate can vary)  │   per packet    │                   (shaped)       │
│                    │                 │                                  │
│                    └─────────────────┘                                  │
│                                                                         │
│   • Tokens added at rate R (tokens/sec)                                │
│   • Bucket holds at most B tokens (excess discarded)                   │
│   • Each packet needs 1 token to pass (or 1 token per byte)            │
│   • No tokens? Packet waits or is dropped                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Token Bucket Parameters

| Parameter | Symbol | Description |
|-----------|--------|-------------|
| **Token rate** | R | Sustained rate (tokens/sec) |
| **Bucket size** | B | Maximum burst size (tokens) |
| **Peak rate** | P | Physical line rate (optional) |

### Traffic Characteristics

The token bucket allows:
- **Average rate** ≤ R (long-term)
- **Burst size** ≤ B (short-term peak)
- **Peak rate** ≤ P (if line rate limited)

### Maximum Burst Duration

If bucket is full (B tokens) and line rate is P:

$$Burst\_Duration = \frac{B}{P - R}$$

During burst:
- Tokens consumed at rate P
- Tokens added at rate R
- Net consumption at rate (P - R)

### Example Calculation

| Parameter | Value |
|-----------|-------|
| Token rate (R) | 100 Mbps |
| Bucket size (B) | 10 MB |
| Peak rate (P) | 1 Gbps |

**Maximum burst duration:**
$$\frac{10 \text{ MB}}{1000 - 100 \text{ Mbps}} = \frac{10 \text{ MB}}{900 \text{ Mbps}} = 0.089 \text{ sec} \approx 89 \text{ ms}$$

**Maximum burst volume at peak rate:**
$$B + R \times Burst\_Duration = 10 + 100 \times 0.089 = 18.9 \text{ MB}$$

## Router Scheduling Algorithms

### The Problem

Packets from multiple flows arrive at a router. In what order should they be transmitted?

The **scheduling discipline** determines:
- Which packet goes next
- Fairness between flows
- Delay characteristics
- QoS guarantees

### 1. FIFO (First-In, First-Out)

**Simplest approach:** Transmit in arrival order.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         FIFO Scheduling                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Arrivals:  [A1]──[B1]──[A2]──[B2]──[A3]──►                           │
│                                                                         │
│   Queue:     ┌────────────────────────────────┐                        │
│              │ [A1] [B1] [A2] [B2] [A3] ────► │                        │
│              └────────────────────────────────┘                        │
│                                                                         │
│   Output:    [A1]──[B1]──[A2]──[B2]──[A3]──►                           │
│              (same order as arrival)                                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

| Pros | Cons |
|------|------|
| Simple implementation | No isolation between flows |
| Low overhead | Bursty flow affects all others |
| Preserves order | No differentiated service |

### 2. Priority Queuing

**Multiple priority levels:** Higher priority always goes first.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Priority Queuing                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Arrivals classified into priority queues:                             │
│                                                                         │
│   High Priority:    ┌──────────────────┐                               │
│   (e.g., VoIP)      │ [H1] [H2] ────► │────┐                           │
│                     └──────────────────┘    │                           │
│                                             ├──► [H1][H2][H3][L1]...   │
│   Low Priority:     ┌──────────────────┐    │                           │
│   (e.g., email)     │ [L1] [L2] [L3] ► │────┘                           │
│                     └──────────────────┘                                │
│                                                                         │
│   Rule: Send from high queue if non-empty, else low queue              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

| Pros | Cons |
|------|------|
| Important traffic gets through | **Starvation** of low priority |
| Simple classification | Unfair if high priority abused |
| Low delay for high priority | No fairness within same priority |

### 3. Round Robin (RR)

**Cycle through flows:** Each flow gets a turn.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Round Robin Scheduling                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Flow A queue:  ┌──────────────────┐                                  │
│                  │ [A1] [A2] [A3] ► │──┐                               │
│                  └──────────────────┘  │                               │
│                                        │                                │
│   Flow B queue:  ┌──────────────────┐  ├──► [A1][B1][C1][A2][B2]...    │
│                  │ [B1] [B2] ────► │──┤                               │
│                  └──────────────────┘  │                               │
│                                        │                                │
│   Flow C queue:  ┌──────────────────┐  │                               │
│                  │ [C1] ─────────► │──┘                               │
│                  └──────────────────┘                                  │
│                                                                         │
│   Cycle: A → B → C → A → B → C → ...                                   │
│   Skip flow if queue empty                                              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

| Pros | Cons |
|------|------|
| No starvation | **Unfair if packet sizes differ** |
| Simple | Flow with bigger packets gets more bandwidth |
| Isolation | Fixed cycle, not work-conserving variant |

### 4. Fair Queuing (FQ) / Weighted Fair Queuing (WFQ)

**Goal:** Simulate bit-by-bit round robin (which is impossible in practice).

**Idea:** Compute the "finish time" of each packet if we were doing bit-by-bit RR, then serve in order of finish times.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      Fair Queuing Concept                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Bit-by-bit Round Robin (conceptual):                                  │
│                                                                         │
│   Flow A packet (100 bits): [──────────]                               │
│   Flow B packet (200 bits): [────────────────────]                     │
│                                                                         │
│   Time:  0    50   100  150  200                                       │
│          ├────┼────┼────┼────┤                                         │
│   A:     ▓▓▓▓▓▓▓▓▓▓                                                    │
│   B:     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓                                         │
│          (interleaved bit by bit)                                       │
│                                                                         │
│   A finishes at time 100, B finishes at time 200                       │
│   → Transmit A's packet first, then B's packet                        │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### Fair Queuing Algorithm

**Virtual time:** A reference clock that advances as packets are served.

For each packet:
- **Start time** = max(virtual time at arrival, finish time of previous packet in same flow)
- **Finish time** = start time + packet size

**Serve packet with smallest finish time.**

### Weighted Fair Queuing (WFQ)

Generalization where flows have different **weights**:

$$Finish\_Time = Start\_Time + \frac{Packet\_Size}{Weight}$$

| Flow | Weight | Share of Bandwidth |
|------|--------|-------------------|
| A | 2 | 2/(2+1+1) = 50% |
| B | 1 | 1/(2+1+1) = 25% |
| C | 1 | 1/(2+1+1) = 25% |

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Weighted Fair Queuing Example                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Flow A (weight 2): Gets 2x bandwidth of B or C                       │
│                                                                         │
│   Timeline (100 byte packets):                                          │
│                                                                         │
│   Time:     0         50        100       150       200                 │
│             ├─────────┼─────────┼─────────┼─────────┤                  │
│   Served:   [A1      ][B1      ][A2      ][C1      ]                   │
│                                                                         │
│   Finish times (with weights):                                          │
│   • A1: 0 + 100/2 = 50                                                 │
│   • B1: 0 + 100/1 = 100                                                │
│   • A2: 50 + 100/2 = 100  (but A1 already gave A head start)           │
│   • C1: 0 + 100/1 = 100                                                │
│                                                                         │
│   Tie-breaking and arrival times affect actual order                   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5. Deficit Round Robin (DRR)

**Problem with RR:** Unfair when packet sizes vary.

**Solution:** Track "deficit" — credit that carries over.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     Deficit Round Robin (DRR)                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│   Each flow gets a "quantum" Q per round (e.g., Q = 500 bytes)         │
│   Plus any "deficit" carried from previous round                        │
│                                                                         │
│   Algorithm per round for each flow:                                    │
│   1. Credit = Deficit + Quantum                                         │
│   2. While Credit ≥ size of head packet:                               │
│      - Dequeue and send packet                                          │
│      - Credit -= packet size                                            │
│   3. Deficit = Credit (save for next round)                            │
│                                                                         │
│   Example: Q = 500 bytes                                                │
│                                                                         │
│   ┌────────────────────────────────────────────────────────────────┐   │
│   │ Round │ Flow │ Deficit │ Quantum │ Head Pkt │ Sent? │ New Def │   │
│   ├───────┼──────┼─────────┼─────────┼──────────┼───────┼─────────┤   │
│   │   1   │  A   │    0    │   500   │   400    │  Yes  │   100   │   │
│   │   1   │  B   │    0    │   500   │   600    │  No   │   500   │   │
│   │   2   │  A   │  100    │   500   │   400    │  Yes  │   200   │   │
│   │   2   │  B   │  500    │   500   │   600    │  Yes  │   400   │   │
│   └────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│   • Flow B couldn't send in round 1 (pkt > credit)                     │
│   • Deficit accumulates, eventually allows large packet                 │
│   • Long-term fair despite packet size differences                     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### DRR Properties

| Property | Benefit |
|----------|---------|
| **O(1) per packet** | Very efficient |
| **Fair** | Equal bandwidth regardless of packet size |
| **Simple** | Easy to implement in hardware |
| **Configurable** | Different quanta for weighted sharing |

### Scheduling Comparison

| Algorithm | Fairness | Complexity | Isolation | Notes |
|-----------|----------|------------|-----------|-------|
| **FIFO** | Poor | O(1) | None | Simplest |
| **Priority** | N/A | O(k) | Partial | Risk of starvation |
| **Round Robin** | Packet-fair | O(1) | Good | Unfair with variable sizes |
| **Fair Queuing** | Bit-fair | O(log N) | Excellent | Complex to implement |
| **WFQ** | Weighted | O(log N) | Excellent | Supports differentiation |
| **DRR** | Bit-fair | O(1) | Good | Practical approximation |

## Summary

| Concept | Key Points |
|---------|------------|
| **Jain's Fairness Index** | $J = \frac{(\sum x_i)^2}{n \sum x_i^2}$, ranges from 1/n to 1 |
| **Max-Min Fairness** | Maximize minimum allocation, water-filling algorithm |
| **Token Bucket** | Rate R, burst B, controls traffic shape |
| **FIFO** | Simple, no isolation |
| **Priority Queuing** | High priority first, starvation risk |
| **Round Robin** | Cycle through flows, unfair with variable packet sizes |
| **Fair Queuing** | Simulates bit-by-bit RR, O(log N) |
| **DRR** | Deficit counter for fairness, O(1), practical |
