# Application Layer: Introduction to the Web

## Overview of the Application Layer

- The **application layer** consists of all the useful things we do with computer networks.
- Examples include:
  - Web browsing
  - Email
  - Audio/video streaming over the Internet
  - Voice/video calls over the Internet
  - File downloads from P2P applications
- The next several lectures study these applications in detail.

---

## Application Architectures

### Client–Server Model

- Most applications are structured as **client–server** applications.
- Example: Web browsing
  - **Client**: Web browser
  - **Server**: Web server
- Characteristics:
  - Server is always on and waiting for clients
  - Clients contact the server when needed
  - Servers are typically hosted in **data centers** or **server farms**

### Peer-to-Peer (P2P) Model

- In **P2P applications**, all peers are equal:
  - Any peer can join or leave at any time
- Often a **hybrid architecture** is used:
  - A centralized server facilitates peer discovery
- Example: **BitTorrent**
  - A centralized **tracker** provides IP addresses of peers
  - Actual file transfer happens in a P2P fashion

---

## Focus on Client–Server Applications

- This lecture focuses on **client–server architectures**
- A popular example: the **World Wide Web**
- The web consists of:
  - A **browser (client)**
  - A **web server**

---

## Network Applications and the Socket API

- Network applications are typically **user-space processes**
- The **transport layer and below** are usually implemented in the **operating system kernel**
- The kernel exposes a **socket API** to user-space applications
- Application developers use sockets to:
  - Send and receive **messages**
  - Example: client sends a message requesting a web page

**Analogy:**
- Sockets are like **post boxes**
- Application-layer messages are like **letters**
- The transport layer is like the **postal system**, handling delivery details

---

## Transport Layer Services

- **TCP (Transmission Control Protocol)**:
  - Connection-oriented
  - Reliable, in-order delivery of a byte stream
  - Suitable for file and text transfer
- **UDP (User Datagram Protocol)**:
  - No reliability guarantees
  - Just delivers messages
  - Preferred for some real-time applications where retransmissions add delay
- **Security add-ons**:
  - Example: **SSL (Secure Sockets Layer)**
  - Used to build secure applications like **HTTPS**
- Current Internet transport protocols:
  - Provide **best-effort** service
  - No guarantees on bandwidth or delay

---

## Port Numbers

- A machine may have multiple sockets open simultaneously
- IP addresses identify the **machine**, but not the specific socket
- **Port numbers** solve this problem:
  - 16-bit identifiers
  - Uniquely identify sockets on a machine
- More details are covered later

---

## The World Wide Web

- Developed by **Tim Berners-Lee** in the 1990s
- Considered the **killer application** of the Internet
- The web consists of:
  - **Web pages** connected by hyperlinks
- Before the web:
  - File transfer, text, and email already existed
- The key innovation:
  - Organizing information using **hyperlinks** for easy navigation

---

## Web Pages and URLs

- A **web page** is typically an **HTML file**
- May contain embedded:
  - Images
  - Videos
  - JavaScript
- Web pages are hosted on **web servers** (e.g., Apache)
- Web clients (browsers) request pages using a **URL**

### URL Structure

- Two main parts:
  1. **Domain name** of the server (resolved to an IP address)
  2. **Path** of the file on the server
- URLs may also include:
  - Data fields (e.g., form inputs)
  - Additional parameters interpreted by the server

---

## HTTP: HyperText Transfer Protocol

- Communication protocol used by web clients and servers
- Typical sequence:
  1. User types a URL or clicks a link
  2. Browser resolves domain name to IP address
  3. Browser opens a TCP connection
  4. Browser sends an HTTP **GET request**
  5. Server sends an HTTP **response** (e.g., 200 OK)
  6. Web page content is transferred
  7. Browser renders the HTML

- This request–response exchange defines the **HTTP protocol**
- Any compliant browser can communicate with any compliant server

---

## Embedded Objects and Parallelism

- A single HTML page often contains multiple **embedded objects**
- Each object requires a separate **GET request**
- Browsers handle this automatically
- Requests may be done:
  - **Serially**
  - **In parallel** (most common approach)

### Persistent and Parallel Connections

- Browsers typically:
  - Open multiple TCP connections (e.g., 4)
  - Send GET requests in parallel
  - Reuse connections for multiple requests (**persistent connections**)
- Reasons:
  - TCP connection setup has overhead
  - Reusing connections improves performance
  - Parallel connections improve bandwidth utilization

---

## Web Page Download Walkthrough

- Download behavior varies based on:
  - Persistent vs non-persistent connections
  - Serial vs parallel connections
- Examples illustrate performance differences (covered in lecture)

---

## HTTP Request Format

- Starts with a **request line**:
  - Method (e.g., GET, POST)
  - URL
  - HTTP version
- Followed by:
  - A variable number of **HTTP headers**
    - Examples: persistence preference, browser type, language
- Followed by:
  - An empty line
  - Optional **message body**

---

## HTTP Response Format

- Begins with a **response code**
- Followed by:
  - HTTP headers (metadata such as content length, last-modified time)
  - The actual requested data

### Common HTTP Response Codes

- **2xx**: Success (e.g., 200 OK)
- **3xx**: Redirection (e.g., 301 Moved Permanently)
- **4xx**: Client error (e.g., 400 Bad Request, 404 Not Found)
- **5xx**: Server error (e.g., 503 Service Unavailable)

---

## Protocol vs Data

- Important distinction:
  - **HTTP protocol** defines how requests and responses are exchanged
  - It does **not** define the content of the data
- Application data can be:
  - HTML
  - Text files
  - Images
  - Audio/video
- Data generation and encoding is a complex task handled by applications
- HTTP is **oblivious** to the content itself
- HTTP is only a small part of the broader **network application ecosystem**

---

## Statelessness of HTTP

- HTTP is a **stateless protocol**
- Each request is:
  - Independent
  - Self-contained
- Server does not maintain client state after responding

---

## HTTP Cookies

- Question: If HTTP is stateless, how do sites like Amazon or Google recognize users?
- Answer: **HTTP cookies**
- How cookies work:
  - On first visit, server generates a unique identifier (cookie)
  - Cookie is sent in the HTTP response
  - Browser stores the cookie locally
  - Subsequent requests include the cookie
- Cookies enable user identification and session management
- Cookie databases:
  - Small local database in the browser
  - Larger database at the server

---

## HTTP Caching

- Motivation:
  - Avoid repeatedly transferring the same page
- Solution:
  - **Proxy servers** cache web pages
- Proxy server behavior:
  - Parses HTTP request
  - Checks local cache
  - If found, serves page from cache
  - Otherwise, fetches from origin server
- Proxy server:
  - Splits HTTP/TCP connections into:
    - Client–proxy
    - Proxy–server
- Proxies may also perform:
  - Content filtering
  - Other optimizations

---

## Browser Caching

- Browsers also cache web content
- Browser checks cache before issuing a request

---

## Cache Control and Validation

- HTTP headers assist caching:
  - **Last-Modified**: when page was last changed
  - **Conditional GET**: client sends last-modified time it has
    - Server responds:
      - `304 Not Modified` if unchanged
      - New page if modified
  - **Expires**: indicates when cached content should expire
  - **ETag**: checksum-like identifier for content
    - Client sends ETag
    - Server resends content if modified

---

## FTP: A Precursor to HTTP

- **FTP (File Transfer Protocol)** is conceptually similar to HTTP
- Allows users to:
  - Connect to an FTP server
  - Get or put files
- Key differences from HTTP:
  1. Uses **separate TCP connections** for control and data
  2. Maintains **session state** (e.g., current working directory)
- HTTP has subsumed much of FTP’s basic functionality
